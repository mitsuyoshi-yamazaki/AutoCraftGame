# 4. マイルストーン

課題02, 03の分析に基づき、最終的なゲーム体験の実現に向けたマイルストーンを定義する。各マイルストーンは前段の達成を前提とする部分と、並行して進められる部分がある。

## 全体構造

```
MS-1 種間相互作用（攻撃と防御）
  ↓
MS-2 生態的ニッチの分化
  ↓
MS-3 観察体験の構築    ← MS-A プレイヤーインフラ（並行）
  ↓
MS-4 マルチプレイヤー
  ↓
MS-5 スケーリング
```

---

## MS-1: 種間相互作用の導入

### 目標

キャラクター同士が直接的に干渉できるようにし、「他者の存在を考慮した戦略」という新しい設計次元を開く。

### 達成基準

- 活性キャラクターに対するDISASSEMBLE（攻撃）が動作する
- 攻撃を回避する戦略（逃走・高耐久化）が実装可能
- 「採取者」と「略奪者」の2つの根本的に異なる生存戦略が共存する

### 必要な仕様変更

1. **DISASSEMBLEの対象拡張**: 残骸だけでなく活性/非活性キャラクターを対象にできるようにする
   - 対象の耐久値を削減し、耐久値が0になったら死亡（残骸化）
   - 1回のDISASSEMBLEで奪えるComponentは1個（現行の残骸DISASSEMBLEと同じ）
   - 対象が活性の場合、攻撃のエネルギーコストを高く設定

2. **SENSEによるキャラクター情報の拡充**: 他キャラクターの耐久値・エネルギー・Component数をSENSE結果に含める（現在のentry_amountに類似した仕組みの拡張、またはqueryの活用）

3. **防御の経済性**: Frame数増加による耐久値上昇がコストに見合うバランス調整

### このマイルストーンが開く戦略空間

- 略奪型: 他キャラクターを攻撃し、その残骸から資源を回収
- 防衛型: 高耐久（Frame多数）で攻撃を耐えながら活動
- 逃走型: Sensorで攻撃者を早期検知し、高速移動で逃走
- 共食い: 自種の弱った個体を分解して資源を回収

### リスクと対策

- **攻撃特化が支配戦略になる**: 攻撃のコスト（エネルギー、耐久値消耗、接近の必要性）を高く設定し、「採取の方が安定的」なバランスにする
- **全員が防御に走り攻撃が無意味になる**: 防御コスト（Frame増 → 代謝増 → 重量増 → 移動効率低下）により過剰防御が不利になるバランス

## MS-2: 生態的ニッチの分化

### 目標

根本的に異なる資源利用戦略が共存可能な環境を構築し、多種共存の構造的基盤を作る。

### 達成基準

- 少なくとも3つの独立したニッチが存在し、それぞれのニッチでの最適戦略が異なる
- 10種以上の祖先種を投入した際に、5種以上が長期共存可能

### 必要な仕様変更の方向性

以下のうち複数を組み合わせて実現する。具体的な仕様はMS-1の結果を踏まえて決定する。

1. **空間的不均質性**: 
   - 複数のバイオーム（Ore密集域、Crystal密集域、Energy密集域、混合域）
   - 地形（壁、移動コスト変動域）
   - 効果: 場所ごとに最適な身体構成・行動パターンが異なる

2. **資源パイプラインの分岐**:
   - 一部Componentを「Metalのみ」「Circuitのみ」で製造可能にする
   - Ore特化・Crystal特化の身体構成が実用的になる
   - 効果: 同一場所でも異なる資源を主に利用する種が共存可能

3. **栄養段階**:
   - MS-1の攻撃が実用的になれば、一次生産者（採取型）と二次消費者（略奪型）のニッチが自然に分化
   - 効果: 食物連鎖による多段階の生態系

4. **環境の時間変動**:
   - 資源生産量の周期変動（future_work_v1/04_environment.md の提案に沿う）
   - 効果: 特定資源への過度の特化が不利になり、汎用型にもニッチが生まれる

### このマイルストーンが開く設計空間

- Ore特化採取者 / Crystal特化採取者
- 肉食者（他キャラクターを捕食）
- Scavenger（残骸専門。MS-1により残骸が増えるため実用的に）
- 環境適応型（環境変動に応じて行動を変える）
- 軽量高速型 / 重厚防御型

---

## MS-3: 観察体験の構築

### 目標

プレイヤーが自分の種族の動態を理解し、設計を改善するためのフィードバックループを確立する。

### 達成基準

- 種族レベルの人口推移が時系列で確認できる
- 個体の死因・複製成功率が統計として見える
- Evolverのパラメータ変遷が世代を追って確認できる
- 系統情報（親子関係）が追跡可能

### 必要な実装

1. **データ収集基盤**:
   - イベントログの構造化（生、死、複製、攻撃等の全イベントをタイムスタンプ付きで記録）
   - 種族ごとの統計集計（人口、平均寿命、複製率、死因分布）

2. **時系列ビュー**:
   - 種族別の人口推移グラフ
   - 種族別の主要パラメータ（平均エネルギー、平均耐久値）推移

3. **系統ビュー**:
   - 親子関係のツリー表示（全系統は困難なので、選択した個体の祖先/子孫を表示）
   - Evolverの場合、パラメータの変遷をツリーに重ねて表示

4. **空間ビュー**:
   - 種族分布のヒートマップ
   - 資源分布の重ね合わせ（種族がどの資源域に集中しているか）

### MS-1, MS-2との関係

MS-1/MS-2の仕様変更がなくても着手可能だが、MS-1/MS-2が実現した後に観察すべき内容が大幅に増える（攻撃イベント、ニッチの空間分布等）。基盤部分は並行して構築可能。

## MS-A: プレイヤーインフラ（MS-1〜3と並行）

### 目標

プレイヤーが祖先種を設計・テスト・投入するサイクルを高速に回せる環境を整備する。

### 達成基準

- テンプレートから祖先種の設計を開始できる
- ローカル環境で祖先種の動作テストが可能
- コンパイルエラーや実行時の問題を迅速に特定できる

### 必要な実装

1. **テンプレート群**: 
   - 最小限の採取・複製テンプレート（200行程度）
   - 各戦略アーキタイプのテンプレート（MS-1/MS-2後に追加）
   - テンプレート内のパラメータにコメントで説明を付与

2. **ローカルテスト環境**:
   - CLIでの単一種テスト実行（既存のsimコマンド）
   - テスト結果の要約出力（寿命、複製数、死因）

3. **デバッグ支援**:
   - Mini-Cコンパイラのエラーメッセージ改善
   - VM実行のトレースモード（ステップ実行、ブレークポイント）

4. **ドキュメント**:
   - 戦略設計ガイド
   - Mini-C APIリファレンス（組み込み関数の一覧と使用例）
   - チュートリアル（「最初の祖先種を作る」）

## MS-4: マルチプレイヤー

### 目標

複数プレイヤーが同一フィールドに祖先種を投入し、競争・観察する基盤を構築する。

### 前提

MS-1（種間相互作用）、MS-2（ニッチ分化）、MS-3（観察体験）が一定水準で達成されていること。多様な戦略が共存できる環境と、それを観察する手段がなければ、マルチプレイヤーにしても面白くならない。

### 達成基準

- サーバーで常時稼働するシミュレーションが動作する
- プレイヤーがクライアントから祖先種を投入できる
- 他プレイヤーの種族との相対的な成績が確認できる
- プレイヤーは自分の種族の系統を追跡できる

### 必要なアーキテクチャ

1. **サーバーサイドシミュレーション**: ヘッドレスで動作するシミュレーションエンジン
2. **クライアント-サーバー通信**: 種族の投入、世界状態の配信（差分更新）
3. **プレイヤー認証と種族帰属**: 誰がどの種族を投入したかの管理
4. **ランキング/統計**: 種族の生存tick数、人口ピーク、子孫数などの集計

### リスク

- サーバーサイドのパフォーマンス（数万キャラクターのVM実行）
- チート対策（VM命令数制限は既にあるが、その他の不正の可能性）
- バランス崩壊時のリカバリ手段

---

## MS-5: スケーリング

### 目標

最終的なゲーム体験——数万キャラクターが巨大なフィールドで活動する世界——を実現する。

### 前提

MS-4（マルチプレイヤー）が動作していること。

### 達成基準

- フィールドサイズが現在の数十倍以上に拡張可能
- キャラクター数が数万規模でシミュレーションが安定動作
- 観察UIがスケールに対応（MS-3のヒートマップ等が必須）

### 技術課題

1. **空間分割と並列化**: フィールドを分割し、独立に更新可能な領域を並列処理
2. **VM実行の効率化**: INSTRUCTIONS_PER_TICKの最適化、JITコンパイルの検討
3. **ネットワーク帯域**: クライアントへの世界状態配信の効率化（視野ベースのフィルタリング）
4. **永続化**: 世界状態のスナップショットと復元

---

## マイルストーン間の依存関係（まとめ）

```
        MS-A（プレイヤーインフラ）
        │  並行して構築可能
        │
MS-1 → MS-2 → MS-3 → MS-4 → MS-5
 種間     ニッチ   観察    マルチ   スケール
 相互作用  分化     体験    プレイヤー
```

### 優先度の根拠

1. **MS-1が最優先**: 種間相互作用がなければ、生態系の複雑さに上限がある。ニッチ分化（MS-2）の一部は種間相互作用（捕食-被食）に依存する
2. **MS-2はMS-1の直後**: ニッチが1つのままマルチプレイヤーにしても、競争排除で数種に収束するだけ
3. **MS-3はMS-1/MS-2と並行着手可能**: データ収集基盤はシミュレーション仕様と独立。ただし表示内容はMS-1/MS-2の結果に依存
4. **MS-AはMS-1と並行**: テンプレート・ドキュメント・デバッグ環境は常に有用。MS-1/MS-2の仕様変更後に更新が必要
5. **MS-4/MS-5はシングルプレイヤーの体験が確立してから**: 多人数で遊んでも面白くないものは、スケールさせても面白くならない
