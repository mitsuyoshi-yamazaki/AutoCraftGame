# 3. 「多様な祖先種の獲得」に関する課題

プレイヤーが根本的に異なる戦略の祖先種を設計する動機と手段の両方が必要である。現状では、動機があっても手段（ゲーム仕様が支える戦略の幅）が不足しており、手段があっても動機（異なる戦略を試す理由）が不足している。

## 3-1. 生態的ニッチの単一性

### 問題

全種が同一の資源パイプラインに依存している:

```
Ore + Crystal → Metal + Circuit → 9種のComponent → Child
```

Scavengerのような「残骸を分解して資源を得る」戦略が存在するが、残骸自体が上記パイプラインの副産物であるため、独立したニッチとは言えない。

**競争排除則の帰結**:
- 同一ニッチの種は最終的に1種に収束する
- パラメータの微差（閾値の違い）で一時的に共存可能だが、本質的には同一戦略の変種
- 100種の祖先種を投入しても、生き残るのは3-5種

### 何が必要か

真のニッチ分化には、種ごとに**異なる資源を利用する**、または**異なる方法で同一資源を利用する**仕組みが必要。

**ニッチ分化の方向性**:

| 方向 | 具体例 | 効果 |
|------|--------|------|
| 資源の専門化 | Ore特化/Crystal特化の部品体系 | 同一資源を巡る競争が緩和 |
| 空間的棲み分け | 地形・環境バイオーム | 場所ごとに最適戦略が異なる |
| 時間的棲み分け | 環境の周期変動 | 時期ごとに最適戦略が異なる |
| 栄養段階の分化 | 捕食（ATTACK相当） | 草食/肉食の分化 |
| 共生・分業 | 資源授受 | 専門化した種同士の協力 |

### v4現状との関係

v4は資源の循環システム（GroundGrid → Node再生）を持ち、これは物質保存則に基づく良い基盤である。しかし、パイプラインが1本であるため、この循環が1種類の生活様式しか支えない。

## 3-2. 身体設計の自由度不足

### 問題

実質的に全種が同じ身体構成を持つ:

```
Frame×2, Actuator×1, Harvester×1, Charger×1, Assembler×1,
Processor×1, Sensor×1, MemoryCore×2
```

Harvesterを持たない種（Scavenger）やFrame×3の種（Replicator）が存在するが、Harvesterなしは著しく不利（一次生産にアクセスできない）であり、Frame数の違いは戦略的差異が小さい。

**根本原因**: 自己複製に必要な最小構成が決まっており、その最小構成がほぼ全てのComponentを含む:
- Actuator: 移動に必須（資源まで到達できない）
- Harvester: 一次資源獲得に必須
- Charger: エネルギー獲得に必須
- Assembler: 加工・組み立て・修理に必須
- Processor: WRITE/ACTIVATEに必須
- Sensor: 探索に必須
- MemoryCore: プログラム格納に必須
- Frame: 存在に必須

### 何が必要か

身体設計にトレードオフを生むには:
1. **Componentの特殊化**: 同一Componentの複数装備で性能が向上する（Sensor×2 → 探索範囲拡大、Actuator×2 → 推力倍増）
2. **Componentの代替**: ある機能を別の手段で実現可能にする（例: Harvesterなしでも、DISASSEMBLEで資源を得る戦略がより実用的になる）
3. **コストの差別化**: 重い身体は移動が遅い（既に実装済み）。さらに、代謝コストがComponentに依存する（既に実装済みだが差が小さい）

v4の代謝コスト体系（Component種別ごとに1-3/tick）は良い基盤だが、現在のパラメータでは身体構成の違いが戦略的差異を生むほどの影響力を持っていない。

## 3-3. 種間相互作用の不在がもたらす戦略空間の制約

### 問題

現在、キャラクター間の直接的相互作用はDISASSEMBLE（残骸に対してのみ）しかない。活性キャラクター同士は物理的衝突以外で干渉できない。

**これが戦略空間を制約する理由**:
- 「他種の存在」を考慮する必要がない → 単独最適解が全体最適解
- 「攻撃を避ける」「協力者を見つける」という行動が不要
- 結果として、プログラムの複雑さに上限がある

### 何が必要か

future_work_v1/03_character_interaction.md で分析された要素のうち、v4で特に重要なのは:

1. **ATTACK（キャラクターへのDISASSEMBLE）**: 捕食-被食関係の創発。ただし攻撃特化が支配戦略になるリスクへの対処が必要（攻撃の高コスト、防御手段の提供）
2. **SENSEによる他キャラクター情報の拡充**: 他キャラクターの強さ・状態を知る手段。攻撃/逃走の判断基盤

SIGNALやGIVEは、まず攻撃と防御の力学が成立した後に意味を持つ。

### v4現状との関係

v4はDISASSEMBLEを「残骸（Remains）」に対してのみ許可している。これをアクティブキャラクターに拡張すれば攻撃となるが、以下の設計判断が必要:
- 攻撃のコスト（エネルギー消費、耐久値消費）
- 防御手段（Frame数による耐久値、逃走速度）
- 「殺傷」と「略奪」の分離（相手を殺さなくてもComponentを奪えるか）

## 3-4. プログラミングの参入障壁

### 問題

種のデザインにはMini-Cでのプログラミングが必要であり、以下のハードルが存在する:

1. **言語仕様の理解**: 16bit整数演算、ポインタなし、配列なし
2. **I/Oアドレスとプロトコルの理解**: command-lastプロトコル、ローカルID管理
3. **ゲームメカニクスの理解**: 資源パイプライン、代謝モデル、エネルギー経済
4. **デバッグの困難**: VMレジスタとメモリのダンプからプログラムの状態を読む必要

### 何が必要か

想定するプレイヤー層が「プログラマー」であることを前提としても:

1. **テンプレートの提供**: 動作する最小限の祖先種プログラムをテンプレートとして提供し、パラメータ変更から始められるようにする
2. **ドキュメント**: 戦略設計ガイド（「どのパラメータがどの行動に影響するか」のマップ）
3. **デバッグ支援**: VM実行のステップ実行、ブレークポイント、変数ウォッチ
4. **コンパイル・テスト環境**: ローカルでの単体テスト実行環境

### 注意

参入障壁を下げすぎると、プレイヤーが表面的なパラメータ調整しかしなくなり、真に多様な戦略が生まれない。「プログラムを書く」こと自体がこのゲームのコアメカニクスであり、これを回避する手段（ビジュアルプログラミング等）は、少なくともコアプレイヤー向けには提供すべきでない。

## 3-5. 設計空間の認知

### 問題

仮にゲーム仕様が十分な戦略空間を提供していたとしても、プレイヤーがその空間の広さを認識できなければ、多様な祖先種は生まれない。

**現状の認知問題**:
- 既存種（Pioneer, Gatherer, Evolver, Explorer）が全て「Harvest型」であるため、「Harvestする以外の生き方」があることに気づきにくい
- 各種のプログラムが200-400行と長く、「何が本質的で何が定型文か」がわからない
- 成功例（長期生存する種）のプログラムは見えるが、「どこが成功の鍵か」がわからない

### 何が必要か

- **対照的な既存種の提供**: 明確に異なる生存戦略を持つ種族を3-4種提示し、戦略空間の幅を示す（例: 採取型、略奪型、共生型、遊牧型）
- **戦略の名前づけ**: 各戦略アーキタイプに名前をつけ、プレイヤーの思考の足場にする
- **失敗例と成功例の解説**: なぜ特定の設計が特定の環境で有利/不利なのかの分析

## 課題間の依存関係

```
3-1 ニッチの単一性
       ↓ (ニッチが1つしかないので)
3-2 身体設計が収束
       ↓ (身体が同じなので)
3-3 種間相互作用がなくても不都合がない
       ↓ (相互作用がないので)
   戦略が単一に収束
       ↓
3-5 設計空間が狭く見える
       ↓
   プレイヤーが多様な種を作らない
```

3-4（参入障壁）はこの依存チェーンとは独立した並行課題である。

**最も上流にある課題は3-1（ニッチの単一性）と3-3（種間相互作用の不在）**であり、これらを解決しない限り、下流の課題は構造的に解消されない。
