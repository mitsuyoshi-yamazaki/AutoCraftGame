# simulation-ui-kit 適用報告とフィードバック

## 0. 何に適用したか

人工生命シミュレータ v9 の観察用GUI（ブラウザ・Canvas 2D・100×100の世界）です。
画面に出る対象は次の4種類で、多いときに数百個が同時に見えます。

| 大分類 | 中身 | 個数の目安 |
|---|---|---|
| 個体 | 接続した部品の連結成分。**この系の主役** | 数個〜30 |
| 物質 | 資源ノードと地面の散布物。6カテゴリ・35品目 | 100〜800 |
| 単独部品 | グループに属さない部品。8種 | 数個〜50 |
| エネルギー | 湧出点（無限供給・毎tick流量制限）と散布エネルギー | 30〜60 |

規約は全面的に採用しました。導入前後で、描画コードへの生の色の直書きは
**70箇所から1箇所**（処方が指定する面の色）まで減りました。

以下、**1章が汎用規約への改善点・課題**、**2章が v9 固有の調整**です。

## 1. 汎用規約に対する改善点および課題

### 1.1 【提案】大きさの校正は、視覚言語ではなく系の側で行う

**これがいちばん大きな学びでした。**

規約 A-1 は「量は大きさ（面積比例）で表す」と定めますが、**量の絶対値をどう画面の大きさへ
写すか**は規約にもキットにも無く、実装が自分で決めることになります。ここで2回つまずきました。

1回目: 資源の量の基準を固定値（100）で書いたところ、v9 の資源ノードの初期量は
実験ごとに **400 / 4000 / 40000 と100倍違い**、基準として成立していませんでした。
結果、資源が個体の3.2倍の大きさで描かれました。

2回目: 散布エネルギーの基準を根拠なく 200 と置いたところ、実測の最大は 1227 で、
やはり個体より大きくなりました。

どちらも「視覚言語を決める時点では、系が実際に取る値の分布を知らない」ことが原因です。

**提案**: 視覚言語の側では**大きさの順序と比だけ**を決め（個体が最も大きい／エネルギーは
小さめ／資源は幅がある）、それを絶対値へ校正するのは系の側の仕事として分離する。
系の側は「資源量は100〜10000、最頻は1000」といった分布を知っているので、
そこから係数を決められます。

規約に条項を足すかは作成者の判断ですが、少なくとも INSTRUCTIONS.md に
**「量の基準は系のパラメータから引く。定数で書かない」**という注意があると、
同じ失敗を繰り返さずに済みます。キット側に `calibrate(samples, targetRatios)` のような
補助があってもよいかもしれません。

### 1.2 【提案】予約色という仕組み

「エネルギーは黄、廃棄物は灰」のように、**ある色をあるクラスの専用にしたい**要求が出ました。
これを「他で使ってはいけない」という禁止として検査で見つけるのではなく、
**導出したカテゴリ色から予約色の近傍を機械的に外して、そもそも選べなくする**ようにしたところ、
運用がとても楽になりました。

```
割り当て可能な色 = 導出したカテゴリ色のうち、予約色すべてから ΔE 15 以上離れているもの
```

汎用の仕組みとして価値があると思います。ただし**色の予算を強く圧迫します**（1.3参照）。

### 1.3 【課題】予約色を置くと色の予算がすぐ尽きる

v9 では黄1つと無彩色2段を予約しました。その結果:

- 資源6カテゴリのうち2つを無彩色へ逃がし、残り4つに色を割り当て
- 個体3種にも同じ4色から割り当て（形が文脈を与えるので使い回せる）
- **単独部品8種は4＋その他に畳まざるを得なかった**

全系列（Set1/Set2/Dark2/Paired/Accent）×彩度×色の部分集合を総当たりしたところ、
予約色3つを外して4色残るのは **Paired だけ**でした。

さらに、個体と資源を色で分けられるかを総当たりしたところ:

| 条件 | 個体色↔資源色の最小 ΔE |
|---|---|
| 現状（同じ系列・彩度だけ 0.95 と 0.75） | **2.7**（実質同じ色） |
| 資源の彩度を 0.60 へ | 6.1（ただし資源の色数が 4→2） |
| 系列を分ける（黄の色相を避けない） | 15.6（ただし黄と色相5°差の色を使うことになる） |
| 系列を分ける（黄の色相を25°以上避ける） | **5.4** |

つまり**予約色を置いた時点で、色による図と地の分離は諦めることになります**。
これはトレードオフとして規約に書いておく価値があると思います（「予約色は強力だが、
残る色の予算と、色による群の分離を同時には買えない」）。

### 1.4 【課題】処方の3項目では足りなかった

INSTRUCTIONS.md は「指定するのは3つだけです（面の色・原典の系列・彩度の寄せ方）」と
書いていますが、v9 では処方の外に**8つの調整項目**が必要になりました。

```js
environmentChroma: 0.75,                            // 環境用の彩度（個体と別の組を導出する）
energyHue: 95, energyChroma: 0.90, energyLightness: 0.86,  // 予約色の黄
energyBackdrop: 0.55,                               // 薄い下敷きの寄せ方
structureLightness: 0.55, wasteLightness: 0.40,     // 予約色の無彩色2段
cornerPx: 1.5,                                      // 角丸
```

このうち **`environmentChroma`** は「同じ面から彩度違いの2組を導出する」ためのもので、
汎用性があると思います（群を2層に分けたい系は多いはず）。処方が
`chromaScale` を配列で取れる、あるいは処方を2つ束ねる仕組みがあると素直です。

**`energyLightness`** は明度帯（`CATEGORICAL_BAND`）を外れる指定です。規約 B-2 は
「群の identity を明度に載せない」と言いますが、**1クラス専用の予約色なら明度を使っても
群が混ざらない**ので、この逸脱は安全だと判断しました。条項の但し書きにできるかもしれません。

### 1.5 【課題】「量を持たない対象」を A-1 が想定していない

v9 のエネルギー湧出点は**総量が無限**で、持っているのは「当tickの流出量の上限に対する
残り」だけです。「量は大きさで表す」を適用しようにも、載せる量がありません。

採った解は、**固定サイズの薄い同形を下敷きにして、その上に残流量ぶんの面積で本体色を
重ねる**（満量で下敷きが隠れて、ふつうの四角に見える）ものです。

これは `state-marks.js` の CHANNELS に無いチャネルなので v9 固有として足しましたが、
「割合を面積で表す」は `fill`（内側の塗りの高さ）の自然な兄弟であり、汎用の語彙に
入れる価値があると思います。**塗りの高さは形を選ばないが、面積で重ねるほうが
『満ちている／欠けている』を直感的に読める**という違いがあります。

### 1.6 【提案】角丸は「形」ではなく「仕上げ」である

菱形の角丸を、最初は半径に対する比で指定していました。すると**大きいマークほど角が丸くなり、
「辺は直線」という意図が消えます**。

角丸を**マークの大きさに依らず一定の px**（辺を食う長さで指定）に変えたところ、
半径 3〜60px の全域で食い込みが 1.50〜1.54px に揃い、意図どおりになりました。

一般化すると、**マークの装飾のうち「識別のための形」ではなく「描画の仕上げ」に属するものは、
データ量に連動させてはいけない**、ということだと思います。同じ話は縁の太さや点の大きさにも
当てはまるかもしれません（現在の実装は `mark.radius * 0.17` のように比で書かれています）。

**この原則は面積合わせにも及びます。** 角丸を固定 px にすると角丸の比が大きさで変わるので、
輪郭から面積を計算し直す `scaleOf()` では面積合わせが大きさで動きます（実測で最大 3.8%）。
**面積はシミュレーション上の量の表現であり、角丸は表現上の装飾**なので、面積合わせは
角を丸めない形の値で固定すべきです。v9 では `scaleOf()` が保存済みの `areaScale` を
使うように直して対応しました（1.10 の4点目）。

規約に条項を足すとすれば、**「量を運ぶ寸法の計算に、装飾を含めた輪郭を使わない」**
という形になると思います。

### 1.7 【課題】文字用の `ink` をマークに流用したくなる

無彩色のマークが必要になったとき、面のトークンに無彩色は `ink` / `inkDim` しかないので、
最初これをマークに使いました。**これは誤りでした**。文字色は面とのコントラストだけを
見て決まっており、**カテゴリ色との色差は誰も保証していません**。実測すると、
低彩度の資源色との ΔE が 9〜14（下限15）で、灰色の資源と色つきの資源が混ざりました。

明度だけを指定して無彩色を別に導出するようにして解決しました。
規約 B-6 は「文字に系列の色を使わない」と逆向きの注意をしていますが、
**「マークに文字の色を使わない」も要るのだと思います。**

### 1.8 【課題】検査が「使っていない色の対」まで数える

`checkCategoricalSeparation` はパレット全体を見るので、実際には使っていない色の対まで
警告に出ます。v9 では「同じ大分類の中で、実際に割り当てた色だけを照合する」検査を
自分で書き足しました。**この絵にとって意味のある問いはそちらでした**——
実際、この検査を入れた直後に本物の不具合が2件見つかりました（1.7の灰と、個体3色の衝突）。

キット側にも「使っている色の一覧を渡して検査する」入口があると良いと思います。

### 1.9 【課題】隙間の既定 2px はマークの小さい系には過大

規約 B-4 の既定は 2px ですが、v9 では資源のマークが 3〜6px なので、2px の隙間では
本体が目減りして形が読めません。**1px に下げました**（重なりが分かれば十分、という判断）。

既定値というより「マークの大きさに対する比で考える」ほうが移植しやすいかもしれません。

### 1.10 【課題】実装まわり（3点）

いずれも v9 側で手を入れました。差分は `v9/ui/simulation-ui-kit/` にあります。

| 箇所 | 内容 | 理由 |
|---|---|---|
| `lib/shapes.js` の `outline()` | `shape.points` があればそれを輪郭として返す（3行） | 「直線の辺＋角だけ丸い」は超楕円の式で書けない。点列を渡せれば `areaScale` も `path()` も既存のまま動く |
| `lib/recipes.js` の `derive()` | 第2引数に処方オブジェクトを直接渡せる（2行・後方互換） | 調整UIから処方を動かして即座に導出するため。無いと `RECIPES` を書き換えることになる |
| `package.json`（新規） | `{"type": "commonjs"}` | 取り込み先が `"type": "module"` だとキットの CommonJS スクリプトが `require is not defined` で落ちる |
| `lib/shapes.js` の `scaleOf()` | `shape.areaScale` が数値ならそれを使う（1行） | **`shapes.json` は導出時の `areaScale` を持っているのに、`scaleOf()` が毎回輪郭から計算し直していて、保存された値が使われていなかった。** 標準4形では差が 5e-7 未満なので実害は無いが、1.6 の用途では必要 |

最後の1点は、**ES module のプロジェクトへ入れると必ず踏みます**。
キットに最初から同梱しておくと親切だと思います。

### 1.11 【報告】色覚多様性を範囲外にしても、色の予算は増えなかった

v9 はプロトタイプなのでアクセシビリティを範囲外と決めました。そこで
「通常視の ΔE だけ見れば色数が増えるのでは」と期待して測りましたが、**増えませんでした**
（Paired で4色のまま）。束縛しているのは `MAX_CATEGORICAL` と `dropUndistinguishable`、
そして予約色であって、色覚の制約ではありませんでした。

規約は色覚多様性を前提にしていますが、**外しても得が無い**ことが分かったので、
その旨が書いてあれば無駄な検討をせずに済みます。

### 1.12 【報告】「機械が決められないもの」の実例

CONVENTION.md の末尾に「その絵が現象の意味を成しているかは人間が見るしかない」と
ありますが、まさにそのとおりの例に当たりました。

希少資源（初期量200）が全体表示で 1.4px の点に潰れ、**枯渇が淘汰圧の中心**である
この系で、いちばん見たいものが読めませんでした。検査は全項目 pass のままです。

対応として最小表示サイズを 2.6px（量696相当）へ上げましたが、**代償として、下限に
当たっている資源は残量が減っても大きさが変わりません**。「存在が見える」と
「枯渇が読める」は同時に買えず、前者を選んだ、という状態です。

規約 B-3 の但し書き（「小さすぎて見えない個体を実寸で描く意味はない」）が
この誇張を許容していますが、**誇張すると量が読めなくなるという代償**も
書き添えてよいかもしれません。

## 2. 本シミュレーション系に固有の調整点

以下は v9 の題材に固有の判断で、汎用規約へ持ち帰るものではありません。

### 2.1 形の割り当て

| 大分類 | 形 | 理由 |
|---|---|---|
| 個体 | 円 | 主役。外周の弧が使えるのが円だけなので、耐久を載せられる |
| 物質 | 菱形（辺は直線・角だけ丸い） | **資源は無機的なものなので辺を曲げない** |
| 単独部品 | 横長 | **加工された＝プリミティブな形状から離れた形**。遠景まで残る唯一の差でもある |
| エネルギー | 四角 | 残り |

### 2.2 主体を最も目立たせる

この系の主体は個体なので、3つの経路で他より目立たせています。

| 経路 | 個体 | 環境 |
|---|---|---|
| 面積係数 | 1.8 | 物質 0.7 / 単独部品 0.45 / エネルギー 0.2 |
| 彩度 | 0.95 | 0.75 |
| 描画順 | 最後（前景） | 先 |

「系の主役」という概念は多くのシミュレーションにあるので、汎用化の余地はありますが、
どのチャネルで目立たせるかは題材によるため、ここに置いています。

### 2.3 予約色の中身

| 予約色 | 持ち主 | 理由 |
|---|---|---|
| 黄（L 0.86） | エネルギー | **エネルギーは他の資源とは別格**であること、**黄は暗いと黄に見えない**こと、および Screeps の見た目を引き継いでいること |
| 無彩色・明（L 0.55） | 構造系の物質・その他の部品・残骸 | 世界を覆うほど豊富で、無彩色に落とすと色つきのものが希少資源か生物だけになる |
| 無彩色・暗（L 0.40） | 廃棄系の物質 | 最も豊富で最も情報量が少ない。意図的に後ろへ下げている |

黄の理由のうち前2つは汎用（1.4に書いたとおり）、3つ目は v9 固有です。

### 2.4 資源の状態と大きさの対応

v9 の資源が実際に持っている状態に素直に対応させています。**同じ量を2つのチャネルに
載せない**ことを原則にしました（当初は大きさと内側の塗りの両方に残量を載せていて、
重複でした）。

| オブジェクト | 持っている状態 | 描き方 |
|---|---|---|
| 資源ノード | 物質種 + 残量（減るだけ・再生せず・0で消滅） | 大きさ＝残量のみ |
| 地面の物体 | 物質種 + 個数 | 同じ形で大きさ＝個数 |
| エネルギー湧出点 | **量を持たない**。当tickの流出量のみ | 固定サイズ＋残流量ぶんの面積を重ねる |
| 散布エネルギー | 量 | 大きさ＝量 |

### 2.5 残骸は状態ではなく別のクラス

生存部品の無い個体も、耐久0の単独部品も、**種ではなく不活性な物質**なので、
予約色の無彩色で描いています。状態チャネル（弧・塗り）は空になるので、
同じ無彩色の「その他の部品」とは区別できます。

規約 A-6 は「状態のために色相を変えない」と言いますが、
**残骸は状態ではなく identity が変わったもの**、という解釈です。

### 2.6 採用しなかった案

資源が小さすぎる件に対し、**大きな資源ノードを近所の複数の塊へ分割する**案を実装して
測りましたが、採用しませんでした。

- 表示上は狙いどおり（最小の資源が 1.4px → 2.8px、大小比 4.5:1 → 2.2:1）
- しかし**実験の結論が2つ壊れました**。移動種が「局所枯渇から脱出して世界中へ拡散する」
  という実証が不成立に。近所に塊が散らばると、移動種が移動しなくなるためです
- 性能も、ノード数が 136→396 で該当テストが 5.1秒→18.0秒

**表示の都合で系の空間分布を変えると、系が示していた現象そのものが変わる**という、
分かりやすい失敗例でした。規約 A-1 の「量は大きさで表す」を守るために系をいじるのは
本末転倒だった、ということです。

## 3. まとめ

規約は有効でした。特に「値を手で選ばない」「identity と状態を別のチャネルへ」の2つは、
迷ったときに立ち返る足場として機能しました。検査を自分の題材向けに1つ足した直後に
本物の不具合が2件見つかったことも含め、**機械検査を持つ規約**という設計は正しいと思います。

汎用規約へ持ち帰る価値があると考えるのは、次の4点です。

1. **大きさの校正を系の側へ分離する**（1.1）——順序と比は視覚言語、絶対値は系
2. **予約色**という仕組みと、その代償の明文化（1.2・1.3）
3. **角丸は形ではなく仕上げ**——装飾をデータ量に連動させない（1.6）
4. **マークに文字の色を使わない**（1.7）

実装まわりの3点（1.10）は、取り込み先を選ばず踏む可能性が高いので、
キット側へ入れていただけると助かります。
