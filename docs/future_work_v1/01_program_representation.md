# 1. Program表現と変異メカニズム

## 現状の問題

現在のProgramはJSON形式のルールベース（`Rule[] = { condition, action }[]`）である。
この形式は人間が読み書きしやすいが、以下の理由で進化には不向きである。

- **ランダム変異に脆弱**: JSONの1バイトを変えると構文エラーになる。意味のある変異がほぼ起きない
- **自己書き換え手段がない**: キャラクターがランタイムでProgramを変更するActionが定義されていない
- **表現空間が離散的**: ルールの追加・削除・順序変更は大きなジャンプであり、漸進的な変化が困難

## 不足している仕様

1. **ランタイムでのProgram変異手段**: キャラクターが自身または子のProgramを変更する方法
2. **変異に耐える表現形式**: 小さな変更が壊滅的でなく、かつ意味のある行動変化を生む表現

## 提案

### 提案A: アセンブラ方式（Tierraモデル）

Programを固定長の数値命令列（オペコード + オペランド）として表現する。

```
例: [0x01, 0x03, 0x02, 0x00, 0x05, 0x01, ...]
      MOV   N     HARVEST       SENSE  ...
```

**利点**:
- 1ビット/1バイトの変異が意味のある変化を生みやすい
- 命令列の部分コピー・挿入・削除が自然に表現できる
- Tierraで実証済みの手法であり、開放的進化の実績がある
- AIコーディングエージェントに命令セットを与えれば、祖先種のプログラムを生成させることも、高等言語→アセンブラのコンパイラを作成させることもできる

**課題**:
- 命令セットの設計が進化の可能性を大きく左右する
- 無効な命令列の扱い（NOOPとして無視するか、ペナルティを与えるか）
- ジャンプ命令を入れるか（ループ・条件分岐の表現力 vs 無限ループのリスク）

**命令セット設計の方向性**:
- 現在のAction（MOVE, HARVEST, PROCESS, CRAFT, ASSEMBLE, WRITE, ACTIVATE, SENSE, REPAIR, NOOP）を基本オペコードとする
- Conditionをフラグレジスタ + 比較命令に変換する
- スタックマシンまたはレジスタマシンとして設計する

### 提案B: 構造化変異（現在のルールベースを拡張）

JSON形式を維持しつつ、構造を理解した変異操作を導入する。

```
変異操作の例:
- ルールの追加/削除/順序入れ替え
- Conditionの閾値変更（nearby radius: 3 → 4）
- Actionの対象変更（CRAFT(Frame) → CRAFT(Sensor)）
- Conditionの論理演算子変更（and → or）
```

**利点**:
- 現在の仕様からの変更が最小
- 変異が常に構文的に正しいProgramを生成する
- 人間にとって進化過程が読み取りやすい

**課題**:
- 変異操作自体がゲームシステムとして提供される「進化手法」にならないか？ → 最終目標に反する可能性
- 表現空間が制限されており、本当に開放的な進化が起きるか疑問
- 変異操作をキャラクターがどう実行するかの設計が必要

### 提案C: ハイブリッド方式

内部表現はアセンブラ（数値列）、WRITEでコピーされるのもこの数値列。
ただし、人間が祖先種を設計する際には高等言語（現在のJSON形式に近いもの）で記述し、コンパイラで数値列に変換する。

```
人間/AI → 高等言語Program → コンパイラ → 数値命令列 → MemoryCore
                                                    ↓
                                              変異（数値レベル）
                                                    ↓
                                              子のMemoryCore
```

**利点**:
- 祖先種の設計容易性と進化の自由度を両立
- コンパイラ自体もAIに生成させられる
- 数値列の変異が意味のある行動変化を生む可能性が高い

**課題**:
- 仮想マシンの仕様策定が必要（スタック/レジスタ、命令幅、メモリモデル）

## 変異の発生タイミング

変異がどう起こるかも仕様に不足している。選択肢:

1. **WRITEコピー時のエラー**: コピーに確率的なビットフリップが入る（生物のDNA複製エラーに相当）
   → ただしこれはゲームシステムが変異を提供することになり、最終目標に反する可能性がある
2. **キャラクター自身による書き換え**: 新しいAction（例: `MODIFY_MEMORY`）で自分のMemoryCoreを操作する
   → キャラクターが自律的に変異を起こすため、最終目標に合致する
3. **環境要因**: 特定条件（放射線ノードなど）でMemoryCoreが損傷する
   → ゲームシステムの一部だが、変異の「手法」というより「自然現象」として解釈可能

**推奨**: 主として手段2を採用し、補助的に手段1（低確率のコピーエラー）を組み合わせる。
手段2により「進化を自律的に行う」という目標を達成しつつ、手段1により最低限の多様性維持を保証する。
