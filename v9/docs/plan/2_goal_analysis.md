# 目的・要件の分析

## プロジェクトの目的

「クラフトゲームの世界観に人工生命の要素をどれだけ入れられるかを検証する」

自動で進行するクラフトゲーム自体は要素技術が揃っており検証不要。
人工生命の要素をどこまで組み込めるかが本質的な検証対象である。

## 要件一覧

### 人工生命の要素

| # | 要件 |
|---|------|
| R1 | 自己複製が可能 |
| R2 | 複製時に変異を入れることができる |
| R3 | 淘汰圧: 資源の有限性 |
| R4 | 淘汰圧: 再生産コスト < 修理コスト |
| R5 | 淘汰圧: 捕食性個体の存在 |
| R6 | 進化や変異の手法を直接提供しない |
| R7 | "個体"の境界をシステム的に定義しない |
| R9 | 他個体との相互作用: "物理的"な相互作用と、情報的な相互作用（遺伝子の水平伝播や有性生殖を可能とするための情報の公開/読み取りの仕組み） |

### 好みとして入れたい要素

| # | 要件 |

## 内部整合性の検証

### 問題1: R2 と R6 の緊張関係 → 解決済み

R2は「変異を入れることができる」、R6は「変異の手法を直接提供しない」。

個体のプログラム自身が自己改変によって変異を実装できることは原理的に分かっている（自己書き換えコード、コピー時の意図的改変など）。システムが変異メカニズムを提供しなくても、プログラムレベルで変異を実現可能であるため、R2 と R6 は両立する。

**結論**: 達成可能。プログラムが自身の複製時に変異を実装する方式で解決。

### 問題2: R7 と自己複製の定義

R7は「個体の境界をシステム的に定義しない」。v8の GroupObject は接続されたコンポーネント群をシステムが明示的にまとめている。

GroupObject はあくまで接続という物理状態の帰結であり、「どこまでが自分か」をシステムが決めているわけではない（プログラムが何をコピーするかで「個体」の実質が決まる）。

**結論**: 実用上は矛盾しない。

### 問題3: R4 は v9 の変更範囲外

v9の要件文書(0_requirement.md)で R4（再生産コスト < 修理コスト）が「変更範囲外」と明記されている。人工生命の要件としては必要だが、v9 で対処しないという方針は、v9 の目標を限定する意味では問題ない。最終的にはどこかのバージョンで検証が必要。

**結論**: 矛盾ではなくスコープの問題。

### 問題4: R8 と v7/v8 の非決定論

v7/v8 では `Math.random()` を使ったランダム移動により決定論が放棄された。R8 を満たすには、v2/v3 のようにシード付きPRNG に戻す必要がある。技術的には可能。

**結論**: 矛盾なし。実装選択の問題。

### 問題5: R9（他個体との相互作用）の実現可能性

R9は物理的・情報的な相互作用の両方を求める。

- **物理的相互作用**: 衝突（v3-v5で実現済み）、捕食（v2で部分検証）、接続（v8で実現済み）。基盤は揃っている
- **情報的相互作用**: 遺伝子の水平伝播や有性生殖には、他個体のプログラムを読み取る手段が必要。v8のPMEM外部アクセス（0x2000系）は同グループまたは近接コンポーネントのメモリを読み書きできるため、基盤は存在する。ただし「非接続の他個体」への情報公開/読み取りは現状のアクセス可能性ルール（近接 OR 同グループ）の範囲内に限られる

**結論**: 矛盾なし。既存の I/O 機構（PMEM, OPMEM）の延長で実現可能。情報の「公開」をどう設計するか（能動的な書き込み vs 受動的な読み取り許可）は設計選択の問題。

### 総合判断

致命的な矛盾はない。全要件は原理的に達成可能。

### 未検証の核心課題

1. **多コンポーネント構成での自己複製** — v7/v8は Assembler+Processor の2種のみ。7種で複製手順が成立するかは未検証
2. **捕食行動の自然発生** (R5) — 事前定義でなく、プログラムの変異から捕食戦略が出現するかは未検証（R2に依存）
3. **耐久度・修理・再生産コストの導入** (R4) — コンポーネントの劣化と修理のメカニズム自体が未設計
4. **情報的相互作用** (R9) — 遺伝子水平伝播や有性生殖を可能にする情報公開/読み取りの仕組みの設計と検証
