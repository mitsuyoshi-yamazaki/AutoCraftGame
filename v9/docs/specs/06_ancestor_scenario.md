# 祖先種の自己複製シナリオ（机上検証）

本書はv9仕様のゲート検証である: **本仕様の下で、人間（またはAI）が書ける規模のプログラムで
自己複製する祖先種が成立するか**を、実装前に机上で確認する。
数値は `npm run craft:report` の生産計画とパラメータ暫定値（[05_parameters.md](05_parameters.md)）による。

## 最小祖先の構成

```
Processor ─ Assembler ─ Storage ─ Harvester   （4コンポーネント、1グループ）
```

- MemoryCore・Actuator・Sensor・Disassemblerを持たない**定住型**
- 前提: クレードル配置（射程3.0内に6種のMatterNodeとEnergyNodeがあること）を
  初期状態configで保証する（[00_world_objects.md](00_world_objects.md)）。
  この前提は移動能力の獲得（Actuator）で不要になる＝進化の初期勾配として意図的に残す

## 複製1サイクルの工程と収支

生産計画（正準経路・貪欲展開）: エネルギー705 / クラフト18回 / レシピ15種類 /
材料 BindingShard×12, InfoSeed×5, BaseSolid×5, VolatileCore×2, CatalystGrain×1, SignalFluid×1（計26個）。

### 工程

| # | フェーズ | 内容 | 見積り |
|---|---------|------|--------|
| A | 回収 | HARVEST×26（物質）＋HARVEST×約70（エネルギー、下記収支分） | 約100アクション。クラフトと並行実行可能 |
| B | クラフト | SET_RECIPE×15（75 tick, 450E）＋CRAFT×14（基本8×5 + 中間6×10 = 100 tick） | 直列で約175 tick |
| C | 子の組立 | ASSEMBLE×4（RC8 Storage→自由設置, RC7/RC3/RC1を子Storageへ連鎖接続, 各30 tick） | 120 tick。子は最初から親と別グループ（接続先を子側に指定するため）。近接I/Oで到達可能 |
| D | プログラム複写 | 親が自pmem(1024語)をLWで読み、0x2003（外部pmem AUTO）で子Processorへ書く | 約5命令/語 × 1024語 ≈ 5,120命令 = 1 tick以内 |
| E | 分与と起動 | TRANSFER×2（エネルギー500・予備材料を子Storageへ）→ 子run_flagに1を書く | 数tick |

### エネルギー収支（1サイクル、暫定値）

| 項目 | 量 |
|------|-----|
| レシピ実行 | 705 |
| SET_RECIPE×15 | 450 |
| Processor実行（約800 tick × 1） | 約800 |
| HARVEST/TRANSFERアクション | 約200 |
| 子への分与 | 500 |
| **合計** | **約2,650** |

- EnergyNode流量100/tick・HARVEST回収40/回に対し約70回の回収 → エネルギーは律速でない
- サイクル時間 ≈ max(クラフト系列 約300 tick, 回収 約100アクション) ＋ 組立120 ＋ 複写・起動
  ≈ **約500〜800 tick**

### 寿命との比較（複製が死より速いか）

- Processorの摩耗: 経年1/10tick ＋ 実行中1/10tick = 0.2/tick → 寿命約5,000 tick（無修理）
- 1サイクル約800 tickなら、**1個体が生涯に約5〜6回複製できる** → 人口は指数増殖可能 ✓

## プログラム規模の見積り

v8の実測（レプリケータ184語・ハイジャッカー97語、いずれも手書きアセンブリ）を基準に:

| 部位 | 見積り（語） |
|------|:---:|
| クラフト手順テーブル（18工程×2語） | 40 |
| クラフト実行ループ（SET_RECIPE→wait→CRAFT→wait） | 60 |
| 回収制御（在庫照会・HARVESTトリガ） | 40 |
| 子の組立系列（ASSEMBLE×4、last_product_idの引回し） | 80 |
| pmem複写ループ | 40 |
| 分与・起動 | 30 |
| 状態機械・雑用 | 80 |
| **合計** | **約370** |

- pmem 1024語に対し**約2.7倍の余裕**。祖先種にMemoryCoreは不要（設計どおり）
- **意図的変異**（本プロジェクトの核心実験）: 複写ループに「PRNG（プログラム内実装）で選んだ
  アドレスの語を子にのみ改変して書く」を加えると +30〜60語。**十分に収まる** ✓

## ゲート判定

| 基準 | 判定 | 根拠 |
|------|:---:|------|
| プログラムがpmem 1024語に収まる | **PASS** | 見積り約370語（v8実測比の外挿） |
| サイクル時間が実験可能な規模 | **PASS** | 約500〜800 tick。10世代でも1万tick以内（v2以降の実験規模と同等） |
| 複製速度 > 劣化速度 | **PASS** | 生涯5〜6回の複製が可能 |
| エネルギー収支が成立 | **PASS** | ノード流量に対し十分小さい |
| 変異をプログラムで実装可能 | **PASS** | 自pmem読取＋外部pmem書込＋算術命令で任意の複写時改変が可能（R2/R6両立） |
| 定住型の資源到達性 | **条件付きPASS** | クレードル配置が前提。移動種はこの制約から解放される（意図された進化勾配） |

## 認識しているリスク（実装後に実測・調整）

1. **SET_RECIPEコストの比重**（450E ≈ レシピ実行energy の64%）: 高すぎれば分業（複数Assembler）や
   バッチ生産が唯一解になりすぎる。RECONFIG_ENERGY/TICKSは主要な調整レバー
2. **待機中のProcessorコスト**（約800E/サイクル）: 「生きているだけでかかるコスト」として意図的だが、
   総収支の3割を占める。PROC_TICK_COSTは慎重に調整する
3. **InfoSeed枯渇**: クレードルの希少ノード（40個）は約8サイクルで枯渇 → 定住型は8世代前後で
   拡散か再利用（分解・捕食）を強制される。**これは意図された淘汰圧である**（05_parameters 参考欄）
4. 貪欲展開は最適でない: 実プログラムは副産物再利用・×2バッチでコストを下げられる（上界としての見積り）
