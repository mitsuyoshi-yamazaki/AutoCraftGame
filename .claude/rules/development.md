# 開発ルール（共通）

## コーディングスタイル

- オブジェクトをmutateしない。常にspread/destructuringで新しいオブジェクトを生成する
- 関数は50行未満、ネストは4レベル未満
- console.logをコミットしない（cli.tsの出力を除く）
- ハードコードした値を使わない（定数として定義する）

## 実装の進め方

1. 仕様ファイル（各バージョンの `docs/specs/`）を読み込み、実装対象を把握する
2. 型定義（`types.ts`）から着手する — 全モジュールの共通基盤
3. 依存関係の少ないモジュールから順に実装する
4. 各モジュール実装後、対応するテストを作成して通過を確認する

## テスト方針

- 各モジュールに対応するテストファイルを作成する
- プロトタイプのためエッジケースのテストは不要。正常系のみ

## バージョニング

- v3以降、実装変更時は各バージョンの `src/version.ts` に記載されたルールに従いバージョンを更新する

## コミット

**コミットは ClaudeCode が行う。** 人手でのコミットを待たない。
ひとまとまりの作業（機能追加・修正・仕様更新など）が完了したら、指示がなくても自分でコミットする。

手順:

1. `git status` / `git diff` で、**自分が変更していないものが混ざっていないか**確認する。
   混ざっていたら、その変更の意図を確認してから含めるか決める
2. 検証を通す — 該当バージョンの `npm test`、UIを触ったなら `npm run verify:ui`、
   型が動いたなら型検査。**落ちたままコミットしない**
3. `src/version.ts` と `package.json` のバージョンを更新する（上記バージョニング規約）
4. 関係する `docs/specs/` を実装に合わせて更新し、同じコミットに含める
5. `git add <path>` で明示的に staging し、`git commit` する

書式・粒度:

- `<type>: <description>`（type は feat / fix / refactor / docs / test / chore / perf / ci）
- 本文には**何をしたか**だけでなく**なぜそうしたか**を書く。
  規約や仕様に照らした判断、破棄した案、意図的に残した逸脱を残す
- 関心事が違うものは分けてコミットする（実装とリポジトリ規約の変更を混ぜない等）
- 署名・Co-Authored-By 等の attribution 行は付けない

やらないこと:

- **push は勝手に行わない。** 明示的に指示されたときだけ
- 破壊的な操作（`git reset --hard`、`git rebase`、既存コミットの改変、
  追跡済みファイルの削除）は、指示なしに行わない
- 未追跡ファイルのうち、自分が作っていないものを勝手に追加しない

## 仕様との関係

- 実装は各バージョンの `docs/specs/` の仕様に従う
- 仕様に記載のない挙動は最もシンプルな解釈を採用する
- 仕様と実装に矛盾がある場合は仕様を正とする
- 仕様の不備を見つけた場合は修正せず、コメントで記録して実装を続行する
