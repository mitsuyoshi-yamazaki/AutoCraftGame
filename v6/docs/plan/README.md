## 実装順序の推奨

```
[M1 完了]
   ↓
M2 (反射) ← 最優先。低コスト・低リスク・効果が直接的に観測可能
   ↓
M3 (アポトーシス) ← M2 と独立、M2 の効果検証中に並行可能
   ↓
M5 (有性生殖) ← 新ゲームメカニクス。集団動態の変化を観測
   ↓
[M4 再評価] ← M2/M3/M5 の知見を基に符号化冗長化の必要性を判断
   ↓
[M6 検討] ← マルチスレッドが必要かどうかを判断
```

### 順序の根拠

1. **M2 が最優先**: 実装コスト最小（既存システムへの追加のみ）、効果が個体生存に直接現れる。M1 の効果と直交（M1=PC回復、M2=条件反射）。
2. **M3 を次に**: M2 で延命される個体が増えるため、機能不全個体の除去機構が必要になる。M3 は M2 と独立しており、並行実装可能。
3. **M5 を次に**: 集団遺伝学的な動態を導入する。M2/M3 の効果が出てから導入することで、効果の重ね合わせが観測可能。
4. **M4 は保留**: 中立変異の意義は理論的には大きいが、実装コストと効果のトレードオフが現状不明。M2/M3/M5 後に「進化が起きていないなら追加検討」とする。

## 共通する設計方針（M1 で確立した原則）

[CLAUDE.md](../../../CLAUDE.md) および M1 の議論から確立した方針:

- **VM がプログラムに強い構造的制約を課さない**: M1 の方式A 採用時、ユーザは「大きな処理が記述できなくなる」ことを懸念したため、最終的には方式A + プログラム書き換え（pioneer.c に `checkpoint()` 1 行）で済むよう設計した。同様の原則を M2 以降でも維持する
- **追加的変更を優先**: 既存システムへの破壊的変更ではなく、追加で済むものを優先
- **決定論性**: 全ての処理は決定論的であること
- **primitive 重視**: 法則 (game_spec) と初期状態 (initial_state) を分離。M2-M5 はゲームの法則に該当する
- **コード破壊は許容**: メモリ破損は進化の材料・淘汰圧として機能させる。書き込み保護等は導入しない
