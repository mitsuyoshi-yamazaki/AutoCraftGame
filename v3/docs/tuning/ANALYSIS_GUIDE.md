# チューニング分析ガイド

本ドキュメントは、シミュレーションの実行・分析・記録を行う際の手順と観点をまとめたものである。分析を行ったことのない開発者やコーディングエージェントを対象とする。

## 分析の全体像

チューニング分析とは、「現在のパラメータと初期条件でシミュレーションを実行し、何が起きているかを定量的に把握し、改善の手がかりを得る」作業である。

作業の流れ:

1. **条件の確認** — 現在のパラメータ・プログラム・初期状態を把握する
2. **シミュレーション実行** — 複数のseedで実行し、再現性のあるデータを得る
3. **定量的な記録** — スナップショットから数値データを表にまとめる
4. **分析** — データからパターンや因果関係を読み取る
5. **記録の作成** — 結果と分析を `docs/tuning/` に記録する

## 1. 条件の確認

### 何を確認するか

シミュレーションの結果を左右する3種類のパラメータを把握する。

**ワールド設定（`src/world.ts` の `DEFAULT_WORLD_CONFIG`）:**
- マップサイズ（width × height）
- 各ノードの数（oreNodeCount, crystalNodeCount, energyNodeCount）
- ノードの初期残量（nodeRemaining）
- エネルギー生産レート（energyProductionRate）
- エネルギー最大蓄積量（energyMaxStored）

**ゲーム法則（`src/constants.ts`）:**
- 基礎代謝（METABOLISM）
- アクションコスト
- 物理パラメータ（MOVE_FORCE, FRICTION_COEFFICIENT 等）
- SENSE_RANGE（情報取得範囲）

**プログラムと初期条件（`programs/` + `ui/main.ts` or `scripts/tuning-run.ts`）:**
- 投入する種族（プログラムファイル一覧）
- 各種族の初期個体数
- 初期エネルギー

### 前回との差分を明確にする

「何が変わったか」を把握することが分析の出発点である。直近のチューニング記録（`docs/tuning/` の最新ファイル）を読み、現在の条件との差分を確認する。差分がなければ「同一条件の再確認」であり、差分があればその影響を中心に分析する。

## 2. シミュレーションの実行

### 基本コマンド

```bash
cd v3
npx tsx scripts/tuning-run.ts --ticks 5000 --seed 42 --snapshot-interval 500
```

### 複数seedの実行

**再現性の確認のために必ず複数seedで実行する。** 1つのseedの結果だけでは、初期配置の偶然に起因する結果なのか、パラメータの構造的な帰結なのか区別できない。

最低3seed、理想的には5seedを推奨する。定番のseedは `42, 123, 999` で、追加する場合は `7, 2024` など。

```bash
for seed in 42 123 999; do
  npx tsx scripts/tuning-run.ts --ticks 5000 --seed $seed --snapshot-interval 500
done
```

各seedの実行は独立しているため、並列に実行してよい。

### snapshotの粒度

- `--snapshot-interval 500` が標準。5000tickで10+1ポイントのデータが得られる
- 細かい動態を追いたい場合は `100` にする（データ量は多くなるが記録への転記は主要ポイントのみで十分）

### 実行結果の読み方

スクリプトは以下の3つのブロックを出力する:

1. **条件サマリ** — seed、tick数、ワールド設定、投入種族
2. **Species Lifespan** — 各種族の生存期間（first seen tick - last seen tick）
3. **Snapshots** — TSV形式の時系列データ（tick、人口、種族別個体数、資源ノード数、エネルギー、残骸数、誕生/死亡数）

## 3. 記録に書く内容

ファイルは `docs/tuning/` に連番で作成する（例: `006_large_world_variant_competition.md`）。

### ドキュメントの構造

```
# NNN: タイトル（何を確認するための実行か）

日付: YYYY-MM-DD

## 目的
  なぜこの実行を行うのか。何を確認・検証したいのか。

## 条件
  ワールド設定、種族構成、実行条件（tick数、seed）を表形式で。
  前回からの変更点があれば明記する。

## 結果
  サマリ表（各seedの最終人口、生存バリアント、総誕生/死亡）
  バリアント別生存tick表
  各seedのスナップショット表

## 分析
  データから読み取れるパターンと、その構造的な理由の考察。
  番号付きで、1項目1観点で記述する。

## 所見
  分析結果のまとめ。改善の方向性があれば挙げる。
```

### サマリ表

全seedの結果を横断的に比較できる表を最初に置く。一覧することで全体像が掴める。

```
| seed | 最終人口 | 生存バリアント | 総誕生 | 総死亡 |
|------|---------|-------------|--------|--------|
| 42   | 10      | Sca-Avoid(9), Sca-Wand(1) | 479 | 505 |
```

### バリアント別生存tick表

「どのバリアントがどのseedで何tickまで生存したか」を一覧にする。5000tick生存を太字で強調する。この表から「配置に依存しない安定した強さ」と「配置に依存する不安定な強さ」を区別できる。

### スナップショット表

スクリプトの出力をそのまま転記するのではなく、**そのseedで注目すべきバリアントを選んで列を絞る**。全12バリアントを並べると読めないため、最終生存種と初期の主要勢力に限定し、残りは「他合計」列にまとめる。

## 4. 分析の観点

データを眺めて「何が起きたか」を記述するだけでは分析にならない。**「なぜそうなるか」の構造的な理由**まで踏み込むことが重要である。

### 基本の分析観点

#### (a) 人口動態のフェーズ

時系列データを見て、人口がどのようなフェーズを経るかを特定する。典型的なパターン:

- **増殖期** — 資源が豊富な序盤に人口が急増する
- **淘汰期** — 資源消費に伴い弱い種族が脱落する
- **安定期** — 生存種が資源とバランスし人口が安定する
- **静的平衡** — 繁殖も死亡もなくなり完全に変化が停止する

フェーズの切り替わりtickと、各フェーズでの誕生/死亡の比率を確認する。

#### (b) 種族間の優劣とその理由

「どの種族が勝ったか」だけでなく、**なぜ勝てたか/負けたか**を資源・代謝・行動戦略の観点から説明する:

- **代謝コスト**: コンポーネント数が多い種族は基礎代謝が高く、同じエネルギーでの活動時間が短い
- **資源の空間分布との相性**: 静的資源（ノード）にはノード探索型が有利、動的資源（残骸）にはノード付近の待機型が有利
- **行動戦略**: 探索型/定住型/回避型の違いが、資源アクセス効率にどう影響するか
- **正のフィードバック**: 例えば「死亡が増える→残骸が増える→Scavengerが有利→他種族が減る→さらに残骸が増える」のような自己強化ループ

#### (c) seed間の再現性

「全seedで同じ結果か、seedによって結果が異なるか」を確認する:

- 全seedで同じ → パラメータの構造的な帰結（確信度が高い）
- seedによって異なる → 初期配置の偶然に左右される（確信度が低い、「ドリフト」の影響）

再現性が低い場合、seed数を増やすか、結果の分散を明記する。

#### (d) 資源経済の持続性

資源が枯渇するか、持続するかを確認する:

- **資源ノード残存数の推移**: 消費ペースは一定か、加速/減速しているか
- **エネルギー蓄積量の推移**: 人口に対してエネルギーが余っているか不足しているか
- **残骸の蓄積**: 残骸が増え続けているか（Scavengerの食糧供給指標）

資源が枯渇するなら「いつ枯渇するか」、持続するなら「何がボトルネックになっているか」を特定する。

#### (e) 前回との比較

前回の記録と条件が異なる場合、**変更した部分が結果にどう影響したか**を比較する。変更していない部分が同じ傾向を示すことも確認する（回帰テスト的な意味）。

### 高度な分析観点

以下は常に必要ではないが、データに特徴的なパターンが見られた場合に有用:

- **静的平衡の検出**: 「誕生0・死亡0」が続くtick区間はあるか。それは一時的か恒久的か
- **人口振動**: 人口が増減を繰り返す場合、その周期と振幅。資源の再生サイクルとの関連
- **絶滅カスケード**: 1種族の絶滅が他種族に波及するか（例: Replicatorの絶滅→残骸減少→Scavengerへの影響）
- **人口の上限/下限**: 人口のピーク値と底値。資源容量（carrying capacity）の推定

## 5. よくある落とし穴

### 「何が起きたか」の記述で終わる

スナップショットの数値を言い換えただけの分析は価値が低い。「tick 2000でOpportunistが絶滅した」ではなく、「Opportunistの代謝コスト18/tickは資源枯渇期にScavenger（15/tick）より3/tick多くエネルギーを消費するため、同じ充電機会では先に飢餓死する」のように、構造的理由まで踏み込む。

### 1つのseedの結果を一般化する

seed 42で「Scavenger最強」であっても、seed 123では「Replicator最強」かもしれない。必ず複数seedの結果を横断的に確認し、再現性のある傾向と、配置依存の偶然を区別する。

### スナップショット表に全列を載せる

12バリアントの列を全て並べると表が読めなくなる。そのseedで注目すべき3-5バリアントを選び、残りは「他合計」にまとめる。選出基準は「最終生存種」「一時的に最大勢力だった種」「特異な動態を見せた種」。

### 改善案を具体化しすぎる

「所見」セクションで改善案を挙げる場合、パラメータの具体的な値まで提案する必要はない。方向性（「残骸の消失メカニズムの導入」等）にとどめ、具体的なパラメータは次の実験で探索する。

## 6. 記録のファイル命名と管理

- ファイル名: `NNN_概要.md`（例: `006_large_world_variant_competition.md`）
- 連番は `docs/tuning/` 内の既存ファイルの最大番号 + 1
- README.md の調整記録テーブルにも追記する
- 分析の目的が異なれば別ファイルにする（同じ実行条件でも「種族間比較」と「資源持続性」で観点が異なれば分けてよい）
