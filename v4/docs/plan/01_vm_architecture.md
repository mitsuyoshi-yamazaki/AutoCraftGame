# v4 計画: VMアーキテクチャ

## メモリモデル

### ノイマン型統一アドレス空間

プログラム（命令列）とデータが同一アドレス空間に存在する。

- メモリとして読み書きしていた領域にプログラムカウンタを移動させれば、その内容がプログラムとして解釈・実行される
- 自己プログラム読み取りは通常のメモリ読み出し命令で実現できる（専用命令不要）
- 自己書き換えプログラムが原理的に可能

### メモリサイズ

- コンポーネント依存とする（例: MemoryCore 1個 = Nワード）
- 巨大なメモリ使用を可能にしつつ、コンポーネントコスト（基礎代謝等）でバランスを取る
- 具体的なサイズとコンポーネントの関係は未決定

## ワードサイズと値の型

- **符号なし整数**
- ワードサイズは要件を実現できる最小のものとする（具体値は未決定）
- 符号付き整数が必要な場合は高級言語/コンパイラ側で対応する
- **浮動小数点は不要** — ゲームシステム上の浮動小数値（角度、座標等）はVM I/Oにおいて整数に丸める

### 浮動小数→整数丸めについて

- エネルギー: v3実装でもすべて整数演算。問題なし
- 角度: atan2の結果を整数度(0-359)に丸める場合、最大0.5度の誤差。近距離では無視可能、遠距離でも実用上問題なし
- 座標: 整数丸めの方針は未決定（ワールドサイズに対する精度の検討が必要）

## 実行モデル

### tick あたりの実行

- 1tickあたりのプログラム実行量（命令数）は未決定
- アクションは1tickあたり複数実行可能（互いに干渉しないもの同士）
- v3の「1tick = 1アクション」制限は要件上の制約ではなかった

### プログラムカウンタの持続

未決定。選択肢:
- **(a) 保持**: 前tickの続きから実行。複数tickにまたがる処理が書ける
- **(b) 毎tickリセット**: tick開始時にPCを先頭に戻す。レジスタ/メモリのみ保持

### NOOP

不要。プログラムがアクションを実行しなければNOOP相当となる。

## 命令セット

未決定。最小VMに必要な命令カテゴリ:
- 算術演算（加減乗除、剰余等）
- 論理演算（AND, OR, NOT, シフト等）
- メモリ操作（load, store）
- 制御フロー（条件分岐、ジャンプ）
- ゲームI/O（アクション発行、環境情報取得 → [02_game_interface.md](02_game_interface.md) 参照）

## 初期プログラムの供給

- 「人間が記述できること」は必須要件
- 高級言語 → コンパイラ → 命令列のツールチェインにより達成可能
- アセンブリ直書きも可能であるべき
