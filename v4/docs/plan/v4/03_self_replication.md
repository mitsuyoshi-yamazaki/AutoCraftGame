# v4 計画: 自己複製の実現方法

## 自己複製のフロー

```
1. 資源収集: HARVEST, RECHARGE で資源・エネルギーを蓄積
2. 加工・製作: PROCESS, CRAFT でコンポーネントを製作
3. 身体生成: ASSEMBLE（ランタイムにコンポーネント構成を指定）→ 子（inactive）が生成される
   → 返り値として子のローカルIDを取得
4. プログラム複製: ローカルIDを指定してWRITE（ソースアドレス、書き込み先アドレス、長さ）でブロック書き込み
5. 起動: ローカルIDを指定してACTIVATE → 子が起動
```

### v3との違い

| | v3 | v4 |
|--|----|----|
| ASSEMBLE | components引数はプログラム中に固定 | ランタイムにメモリの値から決定 |
| WRITE | プログラム全体を一括ディープコピー | ブロック書き込み（ソースアドレス、書き込み先、長さ指定。コスト=長さ比例） |
| 自己読み取り | 不要（WRITEが暗黙にコピー） | 必要（通常のメモリ読み出しで実現） |
| 対象指定 | `nearest_inactive` 等の抽象指定 | ローカルIDによる一意指定 |
| 変異の可能性 | なし（完全コピーのみ） | あり（コピー時に意図的/偶発的な変更が可能） |

## 変異（mutation）の発生源

### (a) 意図的変異: プログラムによる不完全コピー

親プログラムが子のメモリに書き込む際、完全に同一のコピーを行わないことで変異が発生する。

実現手段（いずれもプログラム自身のロジックとして記述）:
- **(a)** 自身のメモリを書き換えてからWRITE → 自身も変異。WRITE後に復元が必要
- **(b)** バッファ領域にコピー→改変→WRITE → メモリ消費が増えるが自身は変異しない
- **(c)** バッチWRITEで大部分をコピーし、変異箇所だけlength=1のWRITEで上書き

どの手法を採用するかは種族のプログラム次第。

### (b) 偶発的変異: 複製時の不具合

プログラムの仕様に依存するため、現時点では具体的な形式は未定。

可能性として:
- メモリ容量の制約によるプログラムの切り詰め
- WRITEの精度やコスト制約による不完全コピー
- VM実行ステップ数の制限によるコピーループの途中終了

## 子のメモリへのアクセス

WRITEアクションがローカルIDで対象を指定し、対象のメモリの特定アドレスに1ワード書き込む。
詳細は [02_game_interface.md](02_game_interface.md) を参照。

## 必要な機能のまとめ

自己複製を実現するためにVMが最低限備えるべき機能:

1. **メモリ読み出し**: 自身のプログラム領域を読み取る（通常のload命令）
2. **外部メモリ書き込み**: ローカルIDを指定してWRITEアクションで子のメモリにブロック書き込み
4. **ランタイム引数**: ASSEMBLEのcomponentsをメモリの値からI/O経由で指定する手段
5. **条件分岐**: 状態に応じた行動選択（資源収集 vs 複製 vs 回避等）
6. **I/O操作**: IN/OUT命令でコンポーネントI/O空間にアクセス
