# プログラム破損ロバスト性: 改善案の検討

Issue [005](../issues/005_program_robustness.md) で提示された「プログラムが少しでも壊れると全体が機能を失う」課題に対し、以下2つの改善案を検討する。

両提案は、Issue 005で不採用となった「tick開始時のリセット」のようにVMがプログラムに強い構造的制約を課す方式とは異なる方向性を持つ。

- **改善案a**: メモリ値→命令の解釈方式を変更し、メモリ変化に対する命令の変化を緩やかにする
- **改善案b**: プログラム単位の責務を縮小し、1プログラムの破損が全体に与える影響を限定する

## 改善案a: 命令エンコーディングの冗長化（コドン的マッピング）

### 現状

現在のVMでは、メモリ1ワード（16bit）が以下のように1命令にマッピングされる:
- 上位6bit (15:10) = opcode (64通り、有効31通り)
- 残り10bitに rd, rs1, rs2, imm4 などの操作対象が密に詰め込まれる

**問題**: 1ワードのうち1bitが反転しただけで、命令種別、レジスタ、即値のいずれかが必ず変化する。中立的（neutral）な変異が存在しない。生物のDNAでは、第3塩基の変化の多くがアミノ酸を変えない（同義置換）が、現VMには対応する仕組みがない。

### アイデアの方向性

メモリ値→命令の写像を多対一にすることで、メモリの一部の変化が命令の変化を引き起こさない領域を作る。具体的な実現方式は複数考えられる:

#### 方式1: opcodeフィールドのHamming距離グルーピング

64通りの6bit opcodeを、たとえば16の「等価類」に分割する。各等価類に属する複数のbitパターンが同じ命令にデコードされる。等価類同士のHamming距離を最大化するように設計すれば、1bitの反転は同じ等価類内で吸収される確率が高くなる。

```
例:
opcode raw値 000000, 000011, 001100, 001111 → 命令ADD
opcode raw値 010101, 010110, 011001, 011010 → 命令SUB
...
```

実装はraw値からデコード後の命令への64要素のlookup tableで足りる。

**効果**:
- opcodeフィールドにおける単bit反転の~50%以上を中立化できる
- 命令種別の変化頻度が下がる

**限界**:
- レジスタフィールド（rd, rs1, rs2）と即値フィールドの脆弱性は解決しない
- 1ワードの中で命令種別だけが冗長化されても、operandは変わってしまう

#### 方式2: 反復符号化（多ワード命令）

各命令をN回繰り返して格納し、デコード時に多数決を取る。

```
例: ADD r1, r2, r3 を3ワードに格納
  word[0] = encode(ADD r1, r2, r3)
  word[1] = encode(ADD r1, r2, r3)
  word[2] = encode(ADD r1, r2, r3)
  → デコード時、各bit位置で多数決
```

**効果**:
- 任意の1bit/1ワード単位の破損を訂正できる
- 命令の全要素（opcode, register, immediate）に対して耐性を持つ

**限界**:
- メモリコストN倍（プログラムサイズが3倍以上に膨らむ）
- 既存のメモリサイズ（MemoryCore × N = N×1024ワード）では大規模プログラムが入らなくなる
- VMのフェッチ処理が複雑化（PCの進み方が変わる）

#### 方式3: 誤り訂正符号（Hamming符号など）

1命令を複数ワードに分割し、データビットとパリティビットを組み合わせて格納する。Hamming(7,4)であれば4bitのデータを7bitに符号化し、1bitエラーを訂正できる。

**効果**:
- 反復符号より効率的に1bitエラーを訂正できる
- 命令全体に対して保護が及ぶ

**限界**:
- メモリコスト約2倍（16bitデータ→約26bit以上の符号化、2ワード必要）
- エンコード/デコードのロジックが複雑
- VMの実装コストが大きい

#### 方式4: 命令長の縮小（情報密度の低下）

現在の16bitを「実質8bit命令 + 8bit冗長」と再解釈する。8bit部分のみで命令を定義し、残り8bitは無視するか、誤り検出/訂正に使う。

**効果**:
- 単純な実装（マスクするだけで済む実装が可能）
- 命令の意味を変えずに、無視bitに任意の値を格納できる

**限界**:
- 情報密度が半減し、プログラムサイズが2倍程度に増える
- 「無視bit」を進化的に活用する仕組みがないと、単に空間を浪費するだけ
- アドレス即値（16bit）など、フル幅を必要とする場面と整合しない

### 改善案aが解決すること

| 解決される課題 | 程度 |
|---|---|
| 単bit反転による命令種別の変化 | 高（特に方式2,3） |
| 単ワード破損による命令種別の変化 | 高（方式2,3） |
| メモリ変化に対する命令変化の確率 | 中〜高 |
| 中立的変異（同義置換）の存在 | ◎（DNAコドンと同等の性質を獲得） |

### 改善案aが解決しないこと

| 解決されない課題 | 理由 |
|---|---|
| **PCの迷走と回復不能（Issue 005の核心）** | デコード結果が正常な命令でも、PCが正常な実行パスに戻る保証はない。`JMP不正アドレス` がデコードされた瞬間、PCは迷走する |
| 制御フローの脆弱性 | JALR/JMPの即値フィールドに対する保護は方式2,3でしか達成できず、コストが高い |
| 多bit/多ワード破損 | スタックオーバーフローによる連続書き込みなどには無力 |
| 意味的な誤り | 命令としては有効でも、プログラムロジックとして不正な命令（例: 別phaseに飛ぶJMP）には無力 |

### 実現可能性

| 方式 | 実装コスト | メモリコスト | 効果範囲 |
|------|----------|------------|---------|
| 1. opcodeグルーピング | **低**（lookup table 1個） | 0（既存サイズで動く） | opcodeフィールドのみ |
| 2. 反復符号化 | 中（フェッチ・PC更新の変更） | 3倍以上 | 全フィールド |
| 3. Hamming符号 | 高（エンコード/デコード実装） | 約2倍 | 全フィールド |
| 4. 命令長縮小 | 低 | 2倍 | 効果は限定的 |

**現実的な選択肢**: 方式1は実装コストが極めて低く、効果も部分的だが意味がある。方式2,3はメモリコストが高く、現在のMemoryCoreベースのメモリ管理と相性が悪い（既存プログラムが収まらなくなる）ため、メモリサイズの見直しと併せて検討する必要がある。

### 改善案aの本質的な評価

**この案の真の価値**: 進化的に意味のある「中立的変異」を可能にする点にある。

現在のVMでは「ほぼすべての変異が即座に挙動を変える」状態であり、これは進化アルゴリズムの観点から見て**変異がほぼ常に観測可能**であることを意味する。一方、生物のゲノムでは多くの変異が中立的（表現型を変えない）であり、ゲノム配列の自由な探索が可能になっている。中立的変異の存在は、進化が「安全に変異を蓄積し、後で意味を獲得する」プロセスを可能にする。

つまり改善案aは、**Issue 005の症状（破損による即死）を直接緩和する**よりも、**進化の設計空間そのものを生物学的なものに近づける**変更である。

ただし、PC迷走問題（Issue 005の核心）に対しては部分的にしか効果がない。

## 改善案b: コンポーネント間相互作用による分散制御

### 現状

現在のv4では:
- 1キャラクター = 1つのProcessor + 複数のコンポーネント
- 1つのProcessorが実行するプログラム1本がキャラクター全体の挙動を決定する
- このプログラムが破損すると、キャラクター全体が機能停止する

### アイデアの方向性

「キャラクター」というシステム上の区分を将来的に廃止し、コンポーネント同士の相互作用によって挙動を生成する設計に移行する。これにより:

- **小器官（organelle）の構成**: 少数のコンポーネント + それを制御する局所Processor を1単位とする小器官を作る
  - 例: 「収穫小器官」= Harvester + Sensor + 専用Processor
  - 例: 「移動小器官」= Actuator + Sensor + 専用Processor
- **階層的制御**: 全体を制御するProcessorは小器官に対して高レベルな指示（「収穫を行え」など）を送り、低レベルな制御（どう動くか、どう収穫するか）は小器官内部のProcessorが担う
- **冗長化**: 同種の小器官を複数配置することで、1つが機能停止しても他が代替する

### 改善案bが解決すること

| 解決される課題 | 程度 |
|---|---|
| 1プログラム破損による全体停止 | **高**（破損は局所化される） |
| プログラムサイズの増大とそれに伴う脆弱性 | 高（各Processorのプログラムが小さくなる） |
| 進化的探索の困難さ | 高（小さな機能単位ごとに進化できる） |
| 冗長性による生存性向上 | 高（同種小器官の複数配置） |

### 改善案bが解決しないこと

| 解決されない課題 | 理由 |
|---|---|
| 個々のProcessorのPC迷走 | 各小器官内部では依然として同じVM仕様 |
| 「全体制御Processor」が破損した場合の影響 | 階層構造の頂点が壊れると全体が機能不全になる可能性 |
| 小器官間の協調の脆弱性 | 通信・連携プロトコルが破損した場合の挙動 |

### 実現可能性

#### 必要な変更

1. **コンポーネント間通信の仕組み**: 現在のProcessorは自身のキャラクターのI/Oスペースしかアクセスできない。複数Processor間で情報をやり取りする仕組み（共有I/O、メッセージパッシングなど）が必要
2. **「キャラクター」抽象の解体**: 現在の `Character` 型はコンポーネント集合を1つの実体として扱う。これを「ゆるく結合したコンポーネント群」へ変更する必要がある
3. **空間配置と接続性**: どのコンポーネントがどのProcessorと連携するかの定義方法。物理的接続（v3で検討した結合）か、ID指定か、近接性か
4. **エネルギー・物質の共有**: 小器官をまたいだリソース移動の仕組み
5. **複製・継承の再設計**: write_memoryは現在「子キャラクター」を対象にする。小器官単位の複製、または小器官構成の継承方法

#### 実装規模

これは**v4の根幹部分の再設計**にあたり、Issue 005の解決策というよりも次バージョン（v5？）の設計方針そのものに近い。具体的には:

- 型システム（types.ts）の大幅な変更
- I/Oハンドラ（io.ts）の再設計
- アクション処理（actions.ts）の再設計
- 既存プログラムは全廃棄して書き直し
- 複製・進化メカニズムも再設計

### 副次的な効果

改善案bは、ロバスト性以外にも以下の効果を持つ:

- **進化の単位が小さくなる**: 各小器官は独立に変異・選択を受けられる。組み合わせ最適化の探索空間が縮小する
- **モジュール性の獲得**: 「共通の小器官 + 特殊な小器官」という構成が自然に表現できる
- **生物学的なリアリズム**: 細胞内小器官や多細胞生物の組織分化に近い構造になる

### 改善案bの本質的な評価

**この案の真の価値**: 「キャラクター」という人為的な抽象を取り払い、より低レベルな相互作用から組織化された挙動を生成する、本プロジェクトの最終目標に直接対応している。

ロバスト性の改善は副次的な恩恵であり、主目的は「自律的な活動の結果として進化が創発するシミュレータの実現」（CLAUDE.mdより）に向けた根本的なアーキテクチャ変更である。

## 2案の比較と関係

| 観点 | 案a (エンコーディング冗長化) | 案b (分散制御) |
|------|--------------------------|--------------|
| 解決対象 | 個々の命令の脆弱性 | プログラム単位の影響範囲 |
| 階層 | VM仕様レベル | システムアーキテクチャレベル |
| 実装規模 | 小〜中 | 極大（システム再設計） |
| 既存資産への影響 | プログラム再アセンブル | プログラム全廃棄 |
| Issue 005の核心（PC迷走）を直接解決するか | 部分的 | 部分的（影響を局所化） |
| 進化への貢献 | 中立的変異の獲得 | 進化単位の縮小 |
| プロジェクト目標との整合 | 補助的 | **直接的** |

**両者の関係**: 排他的ではなく、補完的である。

- 案bが実現すれば、各小器官のProcessorプログラムは小さくなる。小さなプログラムでは、1ワード破損あたりの影響が大きくなる傾向があり、案aによる中立的変異の確保が一層重要になる
- 案aが実現すれば、プログラムの「進化しやすさ」が向上する。小器官構成（案b）下では、小器官ごとに独立した進化が走るため、案aの効果が局所的に積み上がる

## Issue 005の核心問題との関係

両改善案とも、Issue 005の本質的な問題である**「PC迷走からの回復手段がない」**を直接解決するものではない。

- 案aは「迷走の発生確率」を下げ、「破損が中立的に終わる確率」を上げるが、迷走したPCを正常な実行パスに戻す手段は提供しない
- 案bは「迷走したProcessorの影響範囲」を1つの小器官に限定するが、その小器官内部では依然として同じ問題が残る

**結論**: 両案ともロバスト性の改善には寄与するが、PC迷走問題の根本解決には別途の対策が必要。Issue 005で検討したような「迷走時の復帰メカニズム」（リセット案、PC追跡など）と組み合わせて初めて、ロバスト性が総合的に確保される。

## 推奨される検討順序

短期的に着手可能で、効果が見込める順:

1. **案a-方式1（opcodeグルーピング）**: 実装コストが極めて低く、既存プログラムへの影響もアセンブラ再生成のみ。中立的変異の存在を実証できる。次のステップに進む前の試験的導入として有効
2. **案a-方式2 or 3 の検討**: メモリサイズ見直しと併せて、より強力な冗長化を実現する。実装前に「現在のプログラムサイズ × 冗長化倍率」がメモリに収まるか試算が必要
3. **案bの設計検討**: v5以降の根本設計として、コンポーネント間通信プロトコルから仕様を起こす。Issue 005とは独立した、より大きな設計変更として扱う

ただし、これらはいずれもPC迷走問題（Issue 005）の単独解決にはならないため、並行してIssue 005の独自対策（命令セット再設計、回復メカニズムなど）も検討する必要がある。
