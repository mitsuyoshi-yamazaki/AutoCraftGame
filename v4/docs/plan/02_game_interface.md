# v4 計画: ゲーム世界とのインターフェース

## アクション一覧（v4最小スコープ）

v3の全アクションを含む（NOOPを除く）:

| アクション | 概要 | v3での必要コンポーネント |
|-----------|------|------------------------|
| MOVE | 移動（方向指定） | Actuator |
| HARVEST | 資源採取 | Harvester |
| RECHARGE | エネルギー補給 | Charger |
| PROCESS | 素材加工 | Assembler |
| CRAFT | コンポーネント製作 | Assembler |
| ASSEMBLE | 子の身体生成 | Assembler |
| WRITE | 対象メモリへの書き込み（新仕様） | Processor |
| ACTIVATE | 子の起動 | Processor |
| SENSE | 周囲の探知 | Sensor |
| REPAIR | 自身の修理 | Assembler |
| DISASSEMBLE | 残骸の分解 | Disassembler |

### ASSEMBLEの変更

- v3: `components`引数はプログラム中にハードコード
- v4: `components`引数をランタイムに決定する（メモリ/レジスタの値から構築）

### WRITEの変更

- v3: 自身のプログラム全体を対象にディープコピー
- v4: 対象キャラクターのメモリの特定アドレスに1ワード書き込むプリミティブ
- プログラム全体のコピーはプログラム側がループで実現する

### 複数アクション実行

- 1tickあたり複数のアクションを実行可能
- 互いに干渉しないアクション同士が対象
- 干渉の定義・実行順序の仕様は未決定

## コンポーネントの個別制御

### 要件

将来的に同種コンポーネントの複数搭載を可能にし、個別に異なるアクションを行わせる。

### 検討された方式

#### 方式1: メモリマップドI/O（推奨案）

コンポーネントごとにメモリ上のアドレス範囲を割り当てる:
```
アドレス 0xF000-0xF00F: Actuator[0]
アドレス 0xF010-0xF01F: Actuator[1]
...
```

- 長所: 特殊命令不要。ノイマン型と高い親和性。コンポーネント増加に自然にスケール
- 短所: アドレス割り当てルールの設計が必要

#### 方式2: SYSCALL + コンポーネントインデックス

レジスタにアクション種別・コンポーネントインデックス・パラメータを設定し、SYSCALL命令を実行。

- 長所: 実装がシンプル
- 短所: 専用命令が必要。ノイマン型の統一性を崩す

#### 方式3: コマンドキュー

メモリ上の特定領域にコマンド列を書き込み、tick末尾でまとめて実行。

- 長所: 複数アクションの同時発行が自然
- 短所: コマンドフォーマットの解析が必要

### 決定

未決定。方式1（メモリマップドI/O）がノイマン型メモリモデルとの一貫性が高い。

## 環境情報の取得

未決定。メモリマップドI/Oを採用する場合、特定アドレスの読み出しで環境情報を取得する方式が自然:

```
アドレス 0xE000: 自身のエネルギー（読み取り専用）
アドレス 0xE001: 自身の耐久値（読み取り専用）
アドレス 0xE002: 自身のX座標（整数丸め、読み取り専用）
...
```

SENSE結果も同様にメモリマップされたアドレスに格納される想定。
