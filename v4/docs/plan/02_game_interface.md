# v4 計画: ゲーム世界とのインターフェース

## I/O空間

プログラム/データ空間とは**分離された独立空間**。コンポーネントの増減がプログラム空間を圧迫しない。

```
┌─────────────────────┐
│  プログラム/データ    │  ノイマン型統一空間（MemoryCore依存サイズ）
│  メモリ空間          │  通常のload/storeでアクセス
└─────────────────────┘

┌─────────────────────┐
│  コンポーネントI/O    │  分離空間（コンポーネント数に応じて自動拡張）
│  空間                │  IN/OUT命令でアクセス
└─────────────────────┘
```

- I/O空間のワードサイズはプログラム空間と同一
- nullは導入しない。不在スロットのINは0を返す。不在スロットへのOUTは無視

### アクセス命令

```
IN  dest, io_addr    ; I/O空間の io_addr から読み、dest に格納
OUT io_addr, src     ; src の値を I/O空間の io_addr に書き込む
```

## コンポーネントI/O空間のレイアウト

### 方式: 固定アドレス＋動的マウント（案D）

コンポーネント種別×インデックスで固定アドレスを決定。アドレスは不変。

```
アドレス計算: base(type) + index * SLOT_SIZE(type)
```

- インデックスは生成時に種別内で連番割り当て（単調増加、欠番を埋めない）
- コンポーネントが破壊されると欠番になる（既存コンポーネントのアドレスは変わらない）
- SLOT_SIZEは種別ごとに異なる

### 種別ごとのベースアドレス

具体的なアドレス値は未決定。構造例:
```
グローバル:    0x0000
Actuator:      0x1000
Harvester:     0x2000
Charger:       0x3000
Assembler:     0x4000
Processor:     0x5000
Sensor:        0x6000
Disassembler:  0x7000
Frame:         0x8000
MemoryCore:    0x9000
```

### グローバル領域

```
0x0000: 自身のエネルギー（読み取り専用）
0x0001: 自身の耐久値（読み取り専用）
0x0002: 自身のX座標（整数丸め、読み取り専用）
0x0003: 自身のY座標（整数丸め、読み取り専用）
0x0004: 自身のVX（整数丸め、読み取り専用）
0x0005: 自身のVY（整数丸め、読み取り専用）
0x0006: 現在のtick（読み取り専用）
...
```

### スロット共通ヘッダ

```
+0x00  status: 1=存在, 0=不在（読み取り専用）
+0x01  command: アクションコマンド書き込み先
+0x02~ 種別固有のパラメータ/結果領域
```

### ディスカバリ（自己構成の認識）

以下の組み合わせで存在確認を行う:
- 種別ごとの存在コンポーネント数（実在数）
- 種別ごとの接続総数（欠番を含むインデックス上限）
- 各スロットのstatusフィールド

## アクション一覧（v4最小スコープ）

v3の全アクションを含む（NOOPを除く）:

| アクション | 概要 | v3での必要コンポーネント |
|-----------|------|------------------------|
| MOVE | 移動（方向指定） | Actuator |
| HARVEST | 資源採取 | Harvester |
| RECHARGE | エネルギー補給 | Charger |
| PROCESS | 素材加工 | Assembler |
| CRAFT | コンポーネント製作 | Assembler |
| ASSEMBLE | 子の身体生成 | Assembler |
| WRITE | 対象メモリへの1ワード書き込み | Processor |
| ACTIVATE | 子の起動 | Processor |
| SENSE | 周囲の探知 | Sensor |
| REPAIR | 自身の修理 | Assembler |
| DISASSEMBLE | 残骸の分解 | Disassembler |

NOOPは不要（プログラムがアクションを発行しなければNOOP相当）。

### ASSEMBLEの変更

- v3: `components`引数はプログラム中にハードコード
- v4: `components`引数をランタイムに決定する（メモリの値からI/Oスロット経由で指定）
- ASSEMBLEは返り値として子のローカルIDを返す

### WRITEの変更

- v3: 自身のプログラム全体を対象にディープコピー
- v4: 対象キャラクターのメモリの特定アドレスに1ワード書き込むプリミティブ
- 対象はローカルIDで指定する
- プログラム全体のコピーはプログラム側がループで実現する

## アクション実行タイミング

アクションはプログラム実行時には**予約**状態。実際の実行は世界全体の更新時に行われる。

```
1tick の流れ:
  1. 各キャラクターのプログラムが実行され、アクションが予約される
  2. 世界全体が更新される。予約されたアクションが実行される
     - 予約時には存在しなかった問題により失敗することがある
       - 他アクション実施によるエネルギー不足
       - 他キャラクターとの競合
       - 対象の消滅・移動
       等
```

## 対象指定: ローカルID方式

### 概要

キャラクターごとにローカルIDテーブルを持ち、システムIDとの相互変換を行う。

- プログラムはシステムIDに直接アクセスしない
- ローカルIDはキャラクターごとに独立（同じオブジェクトでもキャラクターごとに異なるローカルID）

### ローカルIDテーブル

```
キャラクターA のテーブル:
  local_id=0 → system_id="c42"
  local_id=1 → system_id="r17"
  local_id=2 → system_id="c99"
```

- テーブルはゲームシステム側が管理。キャラクター側のコスト（メモリ、基礎代謝等）にならない
- テーブル容量に上限はない
- テーブルはキャラクター死亡時に解放される

### ID登録の流れ

```
1. SENSE実行 → 結果バッファに (type, angle, distance, properties...) が並ぶ
   （この時点ではIDなし）
2. プログラムが「バッファのN番目のエントリを登録する」操作を実行
   → ゲームシステムがローカルIDを割り当て、テーブルに追加
   → ローカルIDがプログラムに返る
3. プログラムがそのローカルIDを使ってアクションを発行
```

- 同じシステムIDを再度登録した場合 → 既存のローカルIDを返す（重複なし）
- ASSEMBLEは例外的に、子のローカルIDを返り値として返す（SENSE不要で取得可能）

### ローカルIDの割り当てと解放

- 割り当て: 登録のたびにカウンタをインクリメント（単調増加）
- 解放命令をプログラム側に提供する
- 解放されたIDは次の登録で再割り当て可能
- プログラムメモリ空間の外にあるため、自己複製（メモリコピー）の影響を受けない

### アクション実行時のID解決

```
1. ローカルID → テーブル参照 → システムID
2. システムIDでオブジェクトを解決
3. 存在しない → 失敗
4. 射程外 → 失敗
5. アクション固有の前提条件チェック
6. 実行
```

## SENSE結果形式

### バッファ構造

上限N件、距離順ソート。1エントリあたり:

```
+0x00  type           ; オブジェクト種別
+0x01  angle          ; 自分からの角度（整数度）
+0x02  distance       ; 自分からの距離（整数丸め）
+0x03~ property...    ; 種別依存の属性
```

- 結果件数はSensorスロットのresult_countフィールドで取得
- Nの決定方法（固定 / Sensor性能依存 等）は未決定

### 種別依存の属性

- **Character**: energy, durability, コンポーネント数, species等
- **InactiveCharacter**: コンポーネント数
- **ResourceNode**: 種別(Ore/Crystal/Energy), 残量
- **Remains**: コンポーネント数

### ID登録操作

Sensorスロットの登録用フィールド:
```
+0xNN  register_index   ; 登録したいバッファエントリ番号（書き込み）
+0xNN  register_cmd     ; 1を書き込む → 登録実行
+0xNN  registered_id    ; 登録結果のローカルID（読み取り専用）
```

## コンポーネントの個別制御（将来対応）

### 要件

- 同種コンポーネントの複数搭載を可能にし、個別に異なるアクションを行わせる
- コンポーネントは動的に増減する（破壊/パージ、成長）
- 破壊されたコンポーネントの機能は失われる

### 対応方針

案D（固定アドレス＋動的マウント）により構造的に対応済み:
- 種別×インデックスで固定アドレスなので、同種複数搭載は自然に表現できる
- 各スロットに独立したcommandフィールドがあるため、個別アクション発行が可能
- コンポーネント消滅時はstatusが0になり、書き込みは無視される（安全な失敗）
- アドレスは不変なので、他のコンポーネントの増減に影響されない
