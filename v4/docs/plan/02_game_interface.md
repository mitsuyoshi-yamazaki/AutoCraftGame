# v4 計画: ゲーム世界とのインターフェース

## I/O空間

プログラム/データ空間とは**分離された独立空間**。コンポーネントの増減がプログラム空間を圧迫しない。

```
┌─────────────────────┐
│  プログラム/データ    │  ノイマン型統一空間（MemoryCore依存サイズ）
│  メモリ空間          │  通常のload/storeでアクセス
└─────────────────────┘

┌─────────────────────┐
│  コンポーネントI/O    │  分離空間（コンポーネント数に応じて自動拡張）
│  空間                │  IN/OUT命令でアクセス
└─────────────────────┘
```

- I/O空間のワードサイズはプログラム空間と同一（16bit）
- nullは導入しない。不在スロットのINは0を返す。不在スロットへのOUTは無視

### アクセス命令

```
IN  dest, io_addr    ; I/O空間の io_addr から読み、dest に格納
OUT io_addr, src     ; src の値を I/O空間の io_addr に書き込む
```

## コンポーネントI/O空間のレイアウト

### 方式: 固定アドレス＋動的マウント（案D）

コンポーネント種別×インデックスで固定アドレスを決定。アドレスは不変。

```
アドレス計算: base(type) + index * SLOT_SIZE(type)
```

- インデックスは生成時に種別内で連番割り当て（単調増加、欠番を埋めない）
- コンポーネントが破壊されると欠番になる（既存コンポーネントのアドレスは変わらない）
- SLOT_SIZEは種別ごとに異なる

### 種別ごとのベースアドレス

具体的なアドレス値は未決定。構造例:
```
グローバル:    0x0000
Actuator:      0x1000
Harvester:     0x2000
Charger:       0x3000
Assembler:     0x4000
Processor:     0x5000
Sensor:        0x6000
Disassembler:  0x7000
Frame:         0x8000
MemoryCore:    0x9000
```

### グローバル領域

```
0x0000: 自身のエネルギー（読み取り専用）
0x0001: 自身の耐久値（読み取り専用）
0x0002: 自身のX座標（整数丸め、読み取り専用）
0x0003: 自身のY座標（整数丸め、読み取り専用）
0x0004: 自身のVX（整数丸め、読み取り専用）
0x0005: 自身のVY（整数丸め、読み取り専用）
0x0006: 現在のtick（読み取り専用）
...
```

### ディスカバリ（自己構成の認識）

以下の組み合わせで存在確認を行う:
- 種別ごとの存在コンポーネント数（実在数）
- 種別ごとの接続総数（欠番を含むインデックス上限）
- 各スロットのstatusフィールド

## アクション予約: コマンドラスト方式

### 全アクション共通の規約

1. 引数をI/Oスロットに書き込む
2. 最後にcommandフィールドに値を書き込む → **アクション予約が確定**
3. command書き込みにより引数領域がクリアされ、結果領域に切り替わる

この方式により:
- 引数の書き込み途中でアクションが受理されることがない
- 引数と結果が同じ領域を共有し、I/Oスロットを効率的に使う
- 結果（返り値）はcommand書き込み直後に読み出し可能

### スロット共通ヘッダ

```
+0x00  status    ; 1=存在, 0=不在（読み取り専用）
+0x01  command   ; 書き込み → 予約確定。引数領域をクリアし結果を格納
+0x02~ 引数/結果 共用領域（種別ごとに異なるレイアウト）
```

## アクション一覧と各スロットレイアウト

### Actuator — MOVE

```
+0x00  status
+0x01  command        ; 1=MOVE
--- 引数 ---
+0x02  direction      ; 移動方向（角度、0-359）
--- 結果（command後）---
+0x02  (クリア: 0)
```

### Harvester — HARVEST

```
+0x00  status
+0x01  command        ; 1=HARVEST
--- 引数/結果 ---
（なし）
```

### Charger — RECHARGE

```
+0x00  status
+0x01  command        ; 1=RECHARGE
--- 引数/結果 ---
（なし）
```

### Assembler — PROCESS / CRAFT / ASSEMBLE / REPAIR

```
+0x00  status
+0x01  command        ; 1=PROCESS, 2=CRAFT, 3=ASSEMBLE, 4=REPAIR
--- 引数（command=3: ASSEMBLE）---
+0x02  frame_count
+0x03  actuator_count
+0x04  harvester_count
+0x05  charger_count
+0x06  assembler_count
+0x07  processor_count
+0x08  sensor_count
+0x09  disassembler_count
+0x0A  memorycore_count
--- 結果（command=3: ASSEMBLE 後）---
+0x02  child_local_id   ; 子のローカルID（即時読み出し可能）
+0x03~ (クリア: 0)

--- 引数（command=1: PROCESS）---
+0x02  recipe           ; 加工レシピ
--- 結果 ---
+0x02  (クリア: 0)

--- 引数（command=2: CRAFT）---
+0x02  component_type   ; 製作するコンポーネント種別
--- 結果 ---
+0x02  (クリア: 0)

--- 引数（command=4: REPAIR）---
（なし）
--- 結果 ---
（なし）
```

### Processor — WRITE / ACTIVATE

```
+0x00  status
+0x01  command         ; 1=WRITE, 2=ACTIVATE
--- 引数（command=1: WRITE）---
+0x02  target_id       ; 対象のローカルID
+0x03  src_addr        ; 自身のメモリ上のソースアドレス
+0x04  dst_addr        ; 対象のメモリ上の書き込み先アドレス
+0x05  length          ; 書き込みワード数
--- 結果（command=1: WRITE 後）---
+0x02~ (クリア: 0)

--- 引数（command=2: ACTIVATE）---
+0x02  target_id       ; 対象のローカルID
--- 結果 ---
+0x02  (クリア: 0)
```

WRITEのエネルギーコストはlengthに比例する。

### Sensor — SENSE

```
+0x00  status
+0x01  command          ; 1=SENSE
--- 引数 ---
（フィルタ等、未決定）
--- 結果（SENSE実行後）---
+0x02  result_count     ; 検出件数
+0x03  entry_index      ; 現在選択中のエントリ番号（書き込みで選択切替）
+0x04  entry_type       ; 選択エントリの種別（読み取り専用）
+0x05  entry_angle      ; 選択エントリの角度（読み取り専用）
+0x06  entry_distance   ; 選択エントリの距離（読み取り専用）
+0x07  register_cmd     ; 1を書き込む → 選択中のエントリを登録
+0x08  registered_id    ; 登録結果のローカルID（読み取り専用）
```

### Disassembler — DISASSEMBLE

```
+0x00  status
+0x01  command        ; 1=DISASSEMBLE
--- 引数 ---
+0x02  target_id      ; 対象のローカルID
--- 結果 ---
+0x02  (クリア: 0)
```

## アクション実行タイミングと複数アクション

アクションはプログラム実行時には**予約**状態。実際の実行は世界全体の更新時に行われる。

```
1tick の流れ:
  1. 各キャラクターのプログラムが実行され、アクションが予約される
  2. 世界全体が更新される。予約されたアクションが実行される
     - 予約時には存在しなかった問題により失敗することがある
       - 他アクション実施によるエネルギー不足
       - 他キャラクターとの競合
       - 対象の消滅・移動
       等
```

### 複数アクションの同時予約

1tickに複数のアクションを予約可能。ただし:
- **異なる種別のアクション**: 同時実行可能（例: MOVE + HARVEST）
- **同一種別の競合するアクション**: 最後の予約のみが実行される（例: 上方向MOVE + 右方向MOVE → 右方向MOVEのみ）
- **同一コンポーネントスロットへの複数command**: 最後のcommand書き込みが有効

### 複数WRITEの競合

同一対象の同一アドレスへの複数WRITEが予約された場合（自キャラクター内の複数Processorから、または他キャラクターから）:
- アクション実行順に従い順番に書き込む
- 先のWRITEの内容は後のWRITEで上書きされうる

## 対象指定: ローカルID方式

### 概要

キャラクターごとにローカルIDテーブルを持ち、システムIDとの相互変換を行う。

- プログラムはシステムIDに直接アクセスしない
- ローカルIDはキャラクターごとに独立（同じオブジェクトでもキャラクターごとに異なるローカルID）

### ローカルIDテーブル

```
キャラクターA のテーブル:
  local_id=0 → system_id="c42"
  local_id=1 → system_id="r17"
  local_id=2 → system_id="c99"
```

- テーブルはゲームシステム側が管理。キャラクター側のコスト（メモリ、基礎代謝等）にならない
- テーブル容量に上限はない
- テーブルはキャラクター死亡時に解放される

### ID取得方法

**SENSE経由（一般的な対象）:**
```
1. SENSE実行 → 概要バッファに結果格納
2. バッファ内のエントリを選択し、登録コマンドを実行
   → ゲームシステムがローカルIDを割り当て、テーブルに追加
   → ローカルIDが即座に読み出し可能
```

- 同じシステムIDを再度登録した場合 → 既存のローカルIDを返す（重複なし）

**ASSEMBLE経由（子の取得）:**
```
1. ASSEMBLEのcommandを書き込む
2. 引数領域がクリアされ、child_local_id が結果領域に格納される
3. 即座にchild_local_idを読み出し、同一tick内でWRITE/ACTIVATEに使用可能
```

ASSEMBLEが世界更新時に失敗した場合、child_local_idは存在しないオブジェクトを指す。そのIDを使う後続アクションは「対象不在→失敗」で安全に処理される。

### ローカルIDの割り当てと解放

- 割り当て: 登録のたびにカウンタをインクリメント（単調増加）
- 解放命令をプログラム側に提供する
- 解放されたIDは次の登録で再割り当て可能
- プログラムメモリ空間の外にあるため、自己複製（メモリコピー）の影響を受けない

### アクション実行時のID解決

```
1. ローカルID → テーブル参照 → システムID
2. システムIDでオブジェクトを解決
3. 存在しない → 失敗
4. 射程外 → 失敗
5. アクション固有の前提条件チェック
6. 実行
```

## SENSE: 概要＋個別クエリ方式

検討された他の案は [drafts/sense_alternatives.md](drafts/sense_alternatives.md) を参照。

### 設計方針

SENSEは「何がいるか」の概要だけ返す。詳細プロパティは対象を登録した後に個別クエリで取得する。

- 概要エントリが軽量（3ワード/件）なため、多くの対象を検知できる
- 不要な情報を読まなくて済む（必要な対象だけ詳細取得）
- 「何がいるか」→「それは何か」という段階的な認知プロセスに近い

### SENSEの概要バッファ

上限N件、距離順ソート。1エントリあたり3ワード:

```
+0x00  type           ; オブジェクト種別
+0x01  angle          ; 自分からの角度（整数度、0-359）
+0x02  distance       ; 自分からの距離（整数丸め）
```

- Nの決定方法（固定 / Sensor性能依存 等）は未決定（Q15）
- 結果件数はSensorスロットのresult_countフィールドで取得

### 個別クエリ

登録済みのローカルIDを使って、対象の詳細プロパティを取得する。
クエリはアクション予約ではなく、tick内で即時応答する（I/O読み取り）。

```
クエリ用I/O領域:
  query_target_id    ; クエリ対象のローカルID（書き込み）
  query_cmd          ; 1を書き込む → クエリ実行
  query_valid        ; 1=成功, 0=失敗（対象不在/射程外）（読み取り専用）
  query_type         ; 対象の種別（読み取り専用）
  query_angle        ; 現在の角度（読み取り専用）
  query_distance     ; 現在の距離（読み取り専用）
  query_prop0        ; 種別依存の属性（読み取り専用）
  query_prop1        ; 種別依存の属性（読み取り専用）
  ...
```

種別依存の属性:
- **Character**: energy, durability, コンポーネント数, species
- **InactiveCharacter**: コンポーネント数
- **ResourceNode**: 種別(Ore/Crystal/Energy), 残量
- **Remains**: コンポーネント数

### 自己複製の利用フロー

```
tick N:
  1. ASSEMBLE予約 → child_local_id を即時取得
  2. child_local_id を使って WRITE 予約（自身のメモリ → 子のメモリ）
  3. child_local_id を使って ACTIVATE 予約
  4. HALT

tick N → N+1 の世界更新:
  5. ASSEMBLE 実行 → 子が生成される（失敗する可能性あり）
  6. WRITE 実行 → 子のメモリにプログラムをコピー（ASSEMBLE失敗なら不発）
  7. ACTIVATE 実行 → 子が起動（ASSEMBLE失敗なら不発）
```

### C言語での表現

```c
// ASSEMBLE → WRITE → ACTIVATE を直線的に記述
int child = assemble(1,1,1,0,1,1,0,0,1);  // Frame,Actuator,Harvester,...
write_memory(child, 0, 0, PROGRAM_SIZE);    // 自身のメモリを子にコピー
activate(child);
```

コンパイラが各関数呼び出しを「引数OUT → command OUT → 結果IN」のシーケンスに展開する。

## コンポーネントの個別制御（将来対応）

### 要件

- 同種コンポーネントの複数搭載を可能にし、個別に異なるアクションを行わせる
- コンポーネントは動的に増減する（破壊/パージ、成長）
- 破壊されたコンポーネントの機能は失われる

### 対応方針

案D（固定アドレス＋動的マウント）により構造的に対応済み:
- 種別×インデックスで固定アドレスなので、同種複数搭載は自然に表現できる
- 各スロットに独立したcommandフィールドがあるため、個別アクション発行が可能
- コンポーネント消滅時はstatusが0になり、書き込みは無視される（安全な失敗）
- アドレスは不変なので、他のコンポーネントの増減に影響されない
