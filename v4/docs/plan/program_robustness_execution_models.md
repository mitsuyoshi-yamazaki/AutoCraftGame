# プログラム破損ロバスト性: 処理系・実行モデルからの検討

Issue [005](../issues/005_program_robustness.md) で課題となった「PCの迷走によるトラップ」「無限ループからの回復不能」に対し、実行モデル自体を変更するアプローチを検討する。

[改善案c (イベント駆動)](program_robustness_bio_inspired.md#改善案c-イベント駆動型プログラミングモデル生物の遺伝子発現に対応) はPCを廃止する強力な解決策だが、複雑な手続的処理（順序、ループ、条件分岐の入れ子）の表現力に課題があった。本文書では、**手続的表現力を保ったままPCトラップ問題を回避する**実行モデルを探る。

## 評価基準

各案を以下の観点で評価する:

| 観点 | 説明 |
|------|------|
| **PCトラップ耐性** | 制御が異常な状態にトラップされても、何らかの動作を続けられるか |
| **手続的表現力** | 「Aを行い、次にBを行い、結果に応じてC or D」のような順序処理を素直に書けるか |
| **変異耐性** | プログラム表現の一部が変化しても、残りが動作を続けるか |
| **実装コスト** | 既存のVMから移行するコスト |
| **既存資産への影響** | 既存のMini-Cプログラムを廃棄する必要があるか |

## 改善案i: マルチスレッド + ウォッチドッグ

### アイデア

VMを単一PC実行から複数の独立したスレッド（実行コンテキスト）に変更する。各スレッドは独自のPC、レジスタ、スタックを持ち、メモリは共有する。各tickで全スレッドを順に実行するが、**1スレッドあたりの命令数に上限**を設け、上限到達時は強制的に次のスレッドに切り替える。

```
Tick開始
  Thread 0: PC0から実行 → 上限到達 or HALT
  Thread 1: PC1から実行 → 上限到達 or HALT
  Thread 2: PC2から実行 → 上限到達 or HALT
  ...
Tick終了 (各スレッドのPC, レジスタは保持)
```

### 生物学的対応

- **複数の神経経路**: 1つの経路が損傷しても他の経路が機能する
- **複数の臓器**: 各臓器が独立して動作

### PCトラップ耐性

1スレッドが破損して無限ループに陥っても、他のスレッドは独立して動作する。スレッド0が収穫担当、スレッド1が充電担当、スレッド2が複製担当のように分けると、1スレッドの破損は対応する機能のみの喪失で済む。

### 手続的表現力

各スレッド内では従来のPC方式で手続的処理を記述できる。表現力は現状と同等。

### 変異耐性

スレッド単位の機能分割により、破損が局所化される。スレッドが多いほど耐性は高まるが、並列度に対するリソース制約とのトレードオフ。

### 解決すること

- **1スレッドの無限ループが他スレッドを止めない**: PCトラップ問題が「機能の一部」に限定される
- **手続的表現力の維持**: 既存のMini-Cプログラムをほぼそのまま流用可能
- **明示的な機能分割**: 進化が「スレッド単位」で進められる

### 解決しないこと

- **全スレッドが同じプログラムを共有する場合の連鎖破壊**: メモリ共有のため、ある領域の破損が複数スレッドに影響する可能性
- **スレッド初期化の脆弱性**: スレッド開始PCがどこから来るか（ハードコーディング、最初のJMPテーブル等）の設計次第で脆弱性が残る

### 実装コスト

中。VMの実行コンテキストを単数→複数に変更し、tick内のスケジューリングロジックを追加。Mini-Cコンパイラに `spawn_thread(addr)` のような組み込み関数を追加する必要がある。

### 既存資産への影響

小〜中。既存プログラムは「メインスレッドのみ動作」として動かせる。徐々にスレッド分割していくことができる。

## 改善案j: データフロー実行

### アイデア

プログラムをPCで進行する命令列ではなく、**入力が揃った命令から実行されるグラフ**として表現する。各命令ノードは入力ポートと出力ポートを持ち、入力ポートに値が揃った瞬間に実行され、出力ポートに結果を流す。

```
[my_energy] ──┐
              ├──> [LT 300] ──> [if true: recharge]
[const 300] ──┘
```

### 生物学的対応

- **酵素反応**: 基質が揃った時点で反応が起きる
- **遺伝子発現の調節ネットワーク**: 因子の濃度で反応速度が決まる
- **代謝経路**: 化学物質の流れで動作する

### PCトラップ耐性

**PCそのものが存在しない**。実行は「入力が揃ったか」のみで決まり、グラフのどこか1箇所が壊れても他のノードは独立して動作を続ける。ただし、グラフが「壊れたノードに依存するサブグラフ」を持つ場合、その下流は止まる。

### 手続的表現力

順序処理は「前のノードの出力を次のノードの入力とする」依存関係で表現する。条件分岐は「条件ノードがtrue/falseに応じて異なる出力ポートに流す」で表現する。ループは「自己フィードバックエッジ」で表現する。

ただし、複雑な手続き的フロー（多段の条件分岐、深いネスト）はグラフが見にくくなる。手続き型言語のような直線的な記述には不向き。

### 変異耐性

各ノードが独立しているため、ノード単位の破損は局所化される。エッジ（接続）の破損は下流に影響するが、孤立したサブグラフは影響を受けない。

### 解決すること

- **PCトラップが原理的に存在しない**: 「次に実行する命令」という概念がないため、トラップしようがない
- **並列性が自然に表現される**: 独立したサブグラフは同時に動作する
- **進化的探索の単位が明確**: ノード追加・削除・接続変更が独立した変異単位

### 解決しないこと

- **複雑な手続的処理の記述コスト**: 直線的な処理を書くにもグラフ構造が必要
- **グラフ実行エンジンの複雑性**: VMの実装コストが大きい
- **既存資産の完全廃棄**: Mini-Cからの移行は不可能、専用言語が必要

### 実装コスト

大。実行モデルを根本から変更するため、VM、コンパイラ、プログラム表現の全てを再設計する必要がある。

### 既存資産への影響

大。既存プログラムは全て廃棄、新しいモデルで書き直し。

## 改善案k: アクターモデル（独立メモリ・メッセージ通信）

### アイデア

[改善案b (分散制御)](program_robustness_proposals.md#改善案b-コンポーネント間相互作用による分散制御) と類似だが、より明示的にアクターモデルを採用する。各「アクター」は:

- 独立したメモリ空間（共有しない）
- 独自のPC、レジスタ、スタック
- メッセージキューを持つ
- メッセージ受信時に対応するハンドラを実行する

アクター間の通信はメッセージのみ。メモリは共有しない。

```
Actor "harvester" → メッセージ "found_ore at (5,3)" → Actor "main"
Actor "main" → メッセージ "go harvest" → Actor "actuator"
```

### 生物学的対応

- **細胞間のホルモン通信**: 細胞は独立しているが、ホルモンで協調する
- **多細胞生物の組織**: 各細胞は独立した遺伝子発現、化学物質で連携

### PCトラップ耐性

1アクターのPCがトラップされても、他のアクターは独立したメモリ空間を持つため影響を受けない。トラップしたアクターはメッセージ処理が止まるだけで、メッセージ送信元の別アクターは別の経路を試せる。

メモリが共有されないため、**1アクターのスタックオーバーフローが他アクターを破壊することはない**。これが改善案iとの大きな違い。

### 手続的表現力

各アクター内ではPC方式で手続的処理を書ける。複雑な処理はメッセージのやり取りで分散的に実装する。

### 変異耐性

アクター単位の独立性が高いため、変異の影響が局所化される。1アクターが破損しても、他のアクターは健全に動作を続ける。

### 解決すること

- **メモリ分離による物理的隔離**: 1アクターの破損が他に波及しない
- **PCトラップの局所化**: トラップしたアクターを他のアクターが補完可能
- **冗長化が自然**: 同種アクターを複数生成して冗長化できる
- **進化単位の明確化**: アクター単位での進化が可能

### 解決しないこと

- **個別アクター内のPCトラップ**: 各アクター内では依然として同じ問題
- **アクター間プロトコルの脆弱性**: メッセージフォーマットの破損
- **オーバーヘッド**: メモリ分離とメッセージパッシングのコスト

### 実装コスト

中〜大。複数VM実行コンテキスト + メッセージキュー機構が必要。

### 既存資産への影響

中。既存プログラムは1アクター内で動かせるが、メッセージ通信を活用するには再設計が必要。

## 改善案l: プロダクションシステム（ルール+作業記憶）

### アイデア

[改善案c (イベント駆動)](program_robustness_bio_inspired.md#改善案c-イベント駆動型プログラミングモデル生物の遺伝子発現に対応) を強化し、**作業記憶 (working memory)** を追加することで手続的表現力を持たせる。

- メモリ上にルール集合と作業記憶領域がある
- 各tickで全ルールを評価し、条件を満たすルールが「発火」して作業記憶を更新する
- 作業記憶の状態に応じて次のtickで別のルールが発火する
- ルールの連鎖により手続的シーケンスを表現できる

```
RULE 1: WHEN energy < 300         DO  set_state(recharging)
RULE 2: WHEN state == recharging  DO  recharge_action; if (energy > 800) clear_state
RULE 3: WHEN phase == 0           DO  set_substate(seek_ore)
RULE 4: WHEN substate == seek_ore AND nearby_ore  DO harvest; increment count
RULE 5: WHEN count >= 24          DO  set_phase(1); reset_count
```

作業記憶の変数（state, substate, count, phase など）を介して、ルール間に「順序」が生まれる。手続き型プログラムの状態遷移を、ルールの連鎖として表現できる。

### 生物学的対応

- **CLIPS / OPS5 / RETE アルゴリズム**: 古典的なAIプロダクションシステム
- **遺伝子発現カスケード**: 1つの遺伝子発現が次の遺伝子の発現条件を作る
- **ホルモン制御による状態遷移**: ホルモン濃度の変化が次の段階を引き起こす

### PCトラップ耐性

PCそのものが存在しない。各tickで「全ルールを評価する」ループだけがVM内部にあり、これはVMが管理するため破損しない。**ルールの一部が破損しても、他のルールは独立して評価される**。

### 手続的表現力

作業記憶を介した状態遷移により、手続き型言語と同等の表現力を持つ（チューリング完全）。ただし、記述スタイルは大きく異なる。「次の処理」を作業記憶の更新として表現する必要がある。

### 変異耐性

ルール単位の独立性が高い。1ルールの破損は1機能の喪失のみで、他のルールは動作を続ける。新しいルールの追加・削除も独立した変異として扱える。

### 解決すること

- **PCトラップが原理的に存在しない**: VMの内部ループが管理するため、ユーザープログラム側で制御できない
- **手続き的順序処理が表現可能**: 作業記憶を介したルール連鎖
- **進化単位の明確化**: ルール単位の追加・削除・変異
- **既存のロジックをルール群に変換可能**: Mini-Cプログラムから機械的に変換できる可能性

### 解決しないこと

- **作業記憶の破損**: 作業記憶の変数が壊れると状態遷移が乱れる（ただし1ルールの誤発火に留まる）
- **ルール評価のコスト**: 全ルールを毎tick評価するのは命令数を消費する。ルール数N * 命令数Mが命令上限を超える可能性
- **複雑な計算の表現**: 数値計算が多い処理はルール集合で書きにくい

### 実装コスト

中。ルールエンジンと作業記憶のフォーマットを設計し、VMにルール評価ループを実装する。コンパイラはMini-Cからルール集合への変換を行う。

### 既存資産への影響

中〜大。既存プログラムは全面書き直し、または機械変換ツールを作成する。

## 改善案m: 継続ベース実行（チェックポイント方式）

### アイデア

PCを保持するが、プログラム中に**明示的なチェックポイント命令**を配置し、PCがチェックポイントから外れた場合は最も近い（または最後に通過した）チェックポイントに復帰する。

```
CHECKPOINT 0:    // 安全な復帰点
  ... 通常処理 ...
CHECKPOINT 1:    // 別の安全な復帰点
  ... 別の処理 ...
CHECKPOINT 2:
  ...
```

VMは「最後に通過したチェックポイントのアドレス」を別のレジスタ（または特殊メモリ）に記録する。HALT時、PCをそのアドレスに上書きする（または、次tick開始時にチェックする）。

PCが不正な位置に飛んだ場合、いずれHALTかinstructionsPerTick上限に達するが、その時点でPCがチェックポイントレジスタの値に強制復帰する。

### 生物学的対応

- **タンパク質のドメイン構造**: 機能単位ごとに区切られ、1ドメインが壊れても他は機能する
- **遺伝子のエクソン構造**: 機能単位ごとに分かれた配列
- **記憶の固定（メモリ統合）**: 短期記憶から長期記憶への変換時に「セーブポイント」を作る

### PCトラップ耐性

PCがどこに迷走しても、tick終了時には必ずチェックポイントに戻る。**毎tick確実に既知の安全な位置から再開できる**。これは [Issue 005の不採用案 (毎tickリセット)](../issues/005_program_robustness.md#検討した提案) と類似だが、リセット先が固定アドレス0ではなく、**プログラムが最後に明示的に到達したチェックポイント**である点が異なる。

これにより、長い処理の途中でtickを跨いでも、続きから再開できる。

### 手続的表現力

通常のPC方式と同じ。プログラム作者は「ここまで来たら安全」というポイントにCHECKPOINT命令を置くだけで済む。命令の追加コストはチェックポイント間の通常処理に対して無視できる。

### 変異耐性

CHECKPOINT命令自体が破損しても、それは「チェックポイントが減る」だけで動作には影響しない。次のチェックポイントが残っていれば、復帰先がそこになるだけ。

### 解決すること

- **PCの迷走が必ず1tick以内に収束する**: 次tickでチェックポイントから再開
- **手続的処理の自由度を維持**: tick跨ぎの長い処理も書ける
- **プログラム作者が制御できる**: どこを「安全な点」とするかを設計時に決められる
- **進化に対しても有効**: 進化したプログラムでも、CHECKPOINT命令が残っていればそこから動作する

### 解決しないこと

- **チェックポイントレジスタ自体の破損**: VMがどう保護するか別途設計が必要（特殊レジスタとしてr0同様に書き込み制限する等）
- **チェックポイント間で全機能が破壊された場合**: チェックポイント間に有効なI/Oがなければ、その期間は無駄になる
- **最初のtick**: 初回はチェックポイントレジスタが未初期化（アドレス0で初期化する）

### 実装コスト

**低〜中**。VMに新しい命令 `CHECKPOINT` を追加（1ワード命令、特殊レジスタを更新）。tick開始時にPCをチェックポイントレジスタの値で上書きする処理を追加。Mini-Cコンパイラに `checkpoint()` 組み込み関数を追加。

### 既存資産への影響

**小**。既存プログラムは動作を変えずにそのまま使える（チェックポイントなしで動く）。徐々にCHECKPOINT命令を追加していくことで段階的に強化できる。

### この案の本質

**Issue 005の不採用案を拡張し、プログラム側に「リセット先」の制御権を渡したもの**。VMによる強制的なリセットではなく、プログラム自身が「ここなら安全に再開できる」という点を宣言する。

これにより:
- VMがプログラムに強い構造的制約を課さない
- 大きな処理（tick跨ぎ）が依然として記述可能
- 進化しやすい（チェックポイント命令の追加・削除・移動が変異の単位として有効）

## 改善案n: 多重ループ・サンドボックス実行

### アイデア

PCトラップを「無限ループに入った状態」と捉え、**実行を時間的に区切って複数の独立した「実行スロット」に割り当てる**。各スロットは別々のエントリポイントから始まり、独立した命令上限を持つ。

```
Tick開始
  Slot 0: addr 0 から実行 (上限N命令)
  Slot 1: addr K から実行 (上限N命令)
  Slot 2: addr 2K から実行 (上限N命令)
  ...
Tick終了
```

スロット間は一切共有しない（PCもレジスタも独立）。1スロットで実行されたコードがスタックを破壊しても、次のスロットには影響しない。エントリポイント（addr 0, K, 2K...）は固定なので、PC迷走しても次tickでは固定位置から再開する。

### 改善案iとの違い

改善案iは「永続的な複数スレッド」（前のtickの続きから実行）。改善案nは「毎tick固定エントリポイントから実行する複数の独立スロット」（永続性なし、PC・レジスタは毎tickリセット）。

改善案nは [Issue 005の不採用案 (毎tickリセット)](../issues/005_program_robustness.md#検討した提案) のマルチエントリ版と言える。

### PCトラップ耐性

各スロットは毎tick固定アドレスから始まるため、迷走しても次tickでリセットされる。さらに、複数スロットに分かれているため、1スロットが命令上限まで迷走しても、別のスロットは独立して動作する。

### 手続的表現力

各スロット内では通常のPC方式で記述できる。ただし、スロット間で状態を引き継ぐにはグローバル変数を使う必要がある（PC・レジスタはリセットされる）。tick跨ぎの長い処理は書きにくい。

### 解決すること

- **PCトラップが1tick・1スロットに限定される**
- **複数の独立した機能を並列実行できる**
- **エントリポイントが固定なので、進化しても入口は安定**

### 解決しないこと

- **tick跨ぎの長い処理**: 不可能（リセットされる）
- **スロット数の固定性**: いくつのスロットを持つかをVMが決めるか、プログラムが決めるか

### 実装コスト

中。VMの実行ループを「スロットごとに繰り返す」構造に変更。

| **n. マルチエントリ** | 高（局所化+リセット） | 中（tick跨ぎ不可） | 中 | 中 | 中 |

## 推奨

### 最も実装コストが低く効果が高い: 改善案m (チェックポイント)

- VMへの追加が1命令 + 1レジスタ + tick開始時の1行
- 既存プログラムを変更せずに動作する（チェックポイントなしの場合は現状と同じ）
- プログラムに `checkpoint()` を散りばめるだけで、PCトラップから1tick以内に必ず回復する
- 進化に対しても、チェックポイントが残っていれば部分的に動作を続ける

**Issue 005の核心問題（PC迷走）に対する直接的な解決策**として、最も現実的。プログラムに対する制約も最小限。

### 最も柔軟で生物学的な方向: 改善案k (アクターモデル)

- メモリ分離による物理的隔離が、改善案iの「メモリ共有による連鎖破壊」問題を解決する
- 進化的にも「アクター単位での選択」が可能
- 改善案b (分散制御) との統合的な発展形として位置づけられる

長期的には、本プロジェクトの最終目標（コンポーネント相互作用による創発）に直接対応する。

### 最もラディカルな選択: 改善案l (プロダクションシステム)

- PCを廃止しつつも、作業記憶により手続的処理を表現できる
- 改善案c (純粋イベント駆動) の表現力不足を解消する
- 進化単位がルールという明確な形を持つ

ゲームシステムを根本から変更する覚悟が必要だが、進化シミュレーションとしては最も適合する可能性。

## 推奨される検討順序

1. **改善案m (チェックポイント) の試験導入**: 実装コストが極めて低く、効果が大きい。短期的に着手可能。**Issue 005の直接的な解決として最有力**
2. **改善案i (マルチスレッド) の試験**: チェックポイント方式と組み合わせて、機能ごとのスレッド分離を試す
3. **改善案k (アクターモデル) の長期検討**: 改善案b (分散制御) と統合してv5の根本設計とする
4. **改善案l (プロダクションシステム) のプロトタイプ**: 別ブランチで実験的に実装し、表現力と効果を評価

## Issue 005の核心問題への対応

PCトラップ問題に対する各案の対応:

| 案 | 対応方法 |
|----|--------|
| i. マルチスレッド | 局所化（1スレッド内に閉じ込める） |
| j. データフロー | **原理的消滅**（PC廃止） |
| k. アクターモデル | 局所化（1アクター内に閉じ込める） |
| l. プロダクションシステム | **原理的消滅**（PC廃止） |
| m. チェックポイント | **明示復帰**（プログラム指定の安全点） |
| n. マルチエントリ | 局所化+毎tick強制復帰 |

**改善案mは「PCを廃止せず、しかしトラップから必ず回復する」**という、最も保守的かつ実用的な解決策である。Issue 005で挙げた「VMがプログラムに強い制約を課す」問題も、`checkpoint()` をオプショナルにすることで回避できる。
