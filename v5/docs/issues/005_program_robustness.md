# プログラム破損に対するロバスト性の分析

## 背景

現在のv4アーキテクチャでは、`write_memory`によるプログラムコピー時の誤り、スタックオーバーフロー、将来的な変異メカニズムなどにより、キャラクターのメモリ内容が変化する可能性がある。

進化の観点では、プログラムの内容が変化すること自体は望ましい。問題は、**現在の仕様・プログラム構造では、わずかな破損でも全機能が失われる**ことにある。多くの変異が即座に致死的であれば、進化的探索空間が極めて狭くなり、有意な進化が起きにくい。

生物学における「変異ロバスト性」（mutational robustness）に相当する性質を確保することが目標である。すなわち、**プログラムが多少変化しても、何らかの動作（移動、充電、収穫など）を続けられる**ようにする。

## 前提: コード領域の破壊は保護しない

スタックオーバーフローやSWの誤りによるコード領域の書き込みは、VM仕様として禁止しない。理由:
- キャラクターが変異を自ら生み出す手段として利用しうる
- コード破壊を防ぐ「安全なプログラム」を進化させる淘汰圧として機能する
- 進化の材料として積極的に許容すべき

## 現状分析: なぜ破損が致命的か

### 1. PCの迷走と回復不能（核心的問題）

**問題**: 制御フローが破損してPCが不正な位置に到達した場合、**正常な実行パスに復帰する仕組みが一切ない**。

PCが不正な位置に飛ぶと:
1. その位置のメモリ内容を命令として解釈・実行する
2. PC が +1 または +2 進む
3. 次のメモリ内容も命令として実行する
4. HALTに出会えばtickは終了するが、**次tickはHALTの次のアドレスから再開する** — つまり依然として不正な位置にいる
5. いつかPCがメモリ末尾を超えてアドレス0にラップすると、`JMP _main` を実行してmainに飛ぶ。ただし**レジスタ状態（特にr7スタックポインタ）は破損したまま**なので、mainの実行も正常には進まない

**要点**: HALTはtickを区切るだけであり、PCの位置もレジスタ状態も修復しない。HALTの有無は「迷走中のCPU時間消費量」に影響するだけで、回復には寄与しない。

### 2. 制御フロー（関数呼び出し）の脆弱性

**問題**: 関数呼び出しは `LI r5, <address>; JALR r6, r5` の2命令、復帰は `POP r6; JALR r0, r6` の2命令で構成される。これらのいずれかが壊れると、制御フローが完全に崩壊する。

**連鎖的崩壊のメカニズム**:
1. 呼び出し先アドレス（LIの即値）が破損 → 無関係なメモリ位置にジャンプ → PC迷走開始
2. JALR命令が壊れる → 戻りアドレスが保存されない、または不正なアドレスにジャンプ
3. POP r6が壊れる → 不正なリターンアドレスで復帰 → さらに不正な位置に着地
4. いずれも**PCの迷走**に帰着し、上記1.の回復不能問題に至る

**呼び出し深度**: 現在のプログラムでは最大5段の呼び出しチェーンが存在する（main → do_replicate → mutate → clamp → next_rng）。各段にPUSH r6/POP r6があり、どの段で壊れても全体が崩壊する。

### 3. 2ワード命令のアラインメント崩壊

**問題**: LI、JMP、BEQL/BNEL/BLTL/BGELは2ワード命令であり、第2ワードが即値（アドレスまたは定数）である。

**第1ワードのopcodeが壊れて1ワード命令に化けた場合、第2ワード（即値）が独立した命令として実行される**。これによりPCのアラインメントが1ワードずれ、以降のすべての2ワード命令のデコードが狂う。即値を命令として実行することでレジスタ値が予測不能に変化し、PCの迷走を引き起こす。

**規模**: Pioneerプログラムの全1624ワード中、2ワード命令のペアは約400組（800ワード）を占める。プログラムの約49%が2ワード命令の一部であり、アラインメント崩壊の影響を受けやすい。

### 4. グローバル変数（状態機械）の脆弱性

**問題**: プログラムはグローバル変数 `phase`（0-6）を中心とした状態機械で動作する。`phase`の値が不正な値に壊れると:
- 全ての `if (phase == N)` チェックをすり抜ける
- 最終的にwhile(1)の末尾のHALTに到達する（これ自体は安全側）
- しかし、**一切の有用な動作を行わないまま**HALTする
- そして次tickでも同じ状態が繰り返される — phaseは壊れたまま

`phase`が有効な値（0-6）のうち別の値に壊れた場合は、工程を飛ばしたり、材料なしにcraftを試みたりする。直接的に致命的ではないが、正しい動作はできない。

### 5. スタックポインタの破壊力

**問題**: スタックポインタr7には境界チェックがない。スタックはメモリ末尾から下方に成長し、プログラム領域と衝突する可能性がある。Issue 004で実際に発生した。

**破壊のパターン**: スタックがプログラム領域に侵入すると、PUSH命令が命令列を上書きする。これは**メモリ内容自体を変更する**ため、HALTやJMPが破壊され、永続的にプログラムが機能不全に陥る。

さらに悪いのは、r7自体が破損した場合（メモリ上書きやレジスタ破損による）、PUSHが**予測不能な位置**に書き込みを行い、プログラムの別の部分を破壊する。

### 6. tick間の状態持ち越し

**問題**: VMはtick間でPC、レジスタ（r0-r7）、メモリの全状態を保持する。破損した状態は永続的に引き継がれ、自然に回復することがない。

生物のタンパク質が常にターンオーバーする（古い分子が分解され新しい分子で置き換わる）のと対照的に、VMには「リフレッシュ」の仕組みがない。一度壊れたレジスタやPC位置は、明示的に正しい値で上書きされない限り、壊れたままである。

## 課題の本質

上記の個別問題を貫く本質的な課題:

### A. PCの復帰手段がない

破損の多くは最終的に「PCが不正な位置にいる」状態に帰着する。しかし、**PCを既知の正常な位置に戻す仕組みがVM仕様にもプログラム構造にも存在しない**。HALTはtickを区切るだけで、PCを移動させない（+1するのみ）。

### B. 制御フローの脆弱性

関数呼び出し（JALR）は、呼び出し先アドレスと戻りアドレスの両方が正確である必要がある。2ワード命令の即値が1ビット変わるだけで全く異なるアドレスにジャンプする。**制御フローの「正常に動作する領域」が極めて狭い**。

### C. 破損状態の永続性

tick間で全状態が保持されるため、1回の破損が永続的に影響する。レジスタ、PC、メモリのいずれも自然には正しい値に戻らない。

## 検討した提案

### 提案X: tick開始時のPC・レジスタリセット（不採用）

**変更内容**: 各tickの実行開始時に、PCを固定アドレス（アドレス0）にリセットし、r7（スタックポインタ）をメモリ末尾にリセットする。r1-r6もリセットする。メモリはリセットしない。

**効果**:
- **PCの迷走が1tickに限定される**: どんなに制御フローが壊れても、次tickでは必ずアドレス0から開始する
- **スタック破壊が1tickに限定される**: 毎tickクリーンなスタックで開始
- **レジスタ破損が1tickに限定される**: 破損したr6によるリターンアドレス汚染が次tickに持ち越されない
- 課題A, Cを根本的に解決する
- コード領域が壊れていても、壊れていない分岐パスに入れば正常動作する → 部分的な機能喪失が可能になる
- r7リセットにより、破損したr7が毎tick新たなコード破壊を連鎖的に引き起こすことを防止

**不採用理由**:
- **大きな処理が実現しにくくなる**: 1 tickを超えてPC位置を維持する処理（例: 長いループ）ができなくなる。プログラムは毎tick「グローバル変数を見て即座に判断・行動する」構造に制限される
- **システムがキャラクタープログラムに対して強い制約を入れることになる**: tick間でPCやレジスタを保持する自由はプログラムの設計空間の一部であり、VM仕様で一律にリセットすることはこの自由を奪う。進化によって「tick間の状態保持を活用する」プログラムが生まれる可能性を排除してしまう

**プログラム構造への影響** (参考):
```c
// 現在: while(1) { ... halt(); continue; } — PCは各halt()の位置を記憶
// リセット方式: main()が毎tick呼ばれる「tickハンドラ」
void main(void) {
    int energy = my_energy();
    if (recharging) {
        if (energy > EXIT_THRESHOLD) { recharging = 0; }
        else { do_recharge(); return; }
    }
    if (phase == 0) {
        if (count >= ORE_NEEDED) { phase = 1; count = 0; return; }
        do_harvest(FILTER_ORE); return;
    }
    // ...
}
```

**記録理由**: 課題A, Cに対して最も直接的な解決策であり、効果は高い。プログラムの自由度とのトレードオフが合わなかったが、将来的に制約が許容される文脈では有効な選択肢。

## 未解決: 採用可能な対策

上記の提案Xが不採用となったため、課題A（PCの復帰手段がない）に対する有効な対策は未決定。以下の方向性が考えられるが、いずれも詳細な検討が必要:

- **プログラム側での対策**: プログラム構造自体をロバストにする（関数呼び出しの排除、冗長なJMP 0の埋め込みなど）。VMへの制約なしに、プログラムの「進化しやすさ」を改善する
- **VM仕様の部分的変更**: PC・レジスタの完全リセットではなく、より限定的な仕様変更で回復可能性を与える（例: 未使用opcodeの動作変更、割り込み的な仕組みなど）
- **命令セットの根本的再設計**: 2ワード命令の排除、固定長命令への移行など、アラインメント崩壊を構造的に防ぐ設計
