# M4: 符号化冗長化 (Encoding Redundancy) — 保留分析

## 状態

**保留**。M2/M3/M5 の実装と評価が完了するまで着手しない。

## 保留の理由

[ロードマップ M4](../../../v4/docs/plan/program_robustness_roadmap.md#マイルストーン4-中立変異の獲得-案a-符号化冗長化) は「中立変異の獲得」を目的として、命令エンコーディングを冗長化する案である。検討の結果、以下の理由で他のマイルストーンより優先度を下げた:

1. **効果が間接的**: 中立変異の存在は進化の長期的な土壌だが、短期的に観測可能な現象を生まない。M2/M3/M5 が観察可能な変化を生むのと対照的。
2. **実装コストが大きい**: 既存のすべてのプログラムを再アセンブルする必要がある (アセンブラ・コンパイラ・既存バイナリ全て)。
3. **設計の自由度が高すぎる**: 4 つの実装方式 (opcode グルーピング、反復符号化、Hamming符号、命令長縮小) があり、どれが適切かは M2/M3/M5 の経験に依存する。
4. **CHECKPOINT のマジックパターンで部分的に達成済み**: M1 で導入した CHECKPOINT のマジックパターン (`0x36A5`) は「特定の命令を破損から守る」という意味で、ある種の冗長化と言える。

## 着手の前提条件

以下が満たされた段階で M4 の本格設計に進む:

1. M2 (反射) と M3 (アポトーシス) が稼働し、破損注入下での集団動態が観察可能になっている
2. M5 (有性生殖) が稼働し、多様性維持機構が動いている
3. これらの上で「進化が起きていない」または「変異が常に致死的」という観察結果が得られている
4. 中立変異の不在が進化停滞のボトルネックであると判定された

## 着手時に決定すべき事項

M4 着手時に以下を決定する必要がある:

### 1. エンコーディング方式の選択

| 方式 | 実装コスト | メモリコスト | 効果範囲 | 評価が必要な点 |
|------|----------|------------|---------|-------------|
| 1. opcode グルーピング | 低 | 0 | opcode フィールドのみ | グルーピングの設計 (どの bit パターンを同義とするか) |
| 2. 反復符号化 | 中 | 3倍 | 全フィールド | プログラムサイズ増大が許容できるか |
| 3. Hamming 符号 | 高 | ~2倍 | 全フィールド | デコード時オーバーヘッドが問題ないか |
| 4. 命令長縮小 (8bit命令) | 低 | 2倍 | 部分 | 16bit即値との整合 |

### 2. 既存プログラムの扱い

- すべて再アセンブルする (CI/CD的)
- 旧エンコーディングと新エンコーディングを併存させる (移行期間)
- 新規プログラムから順次移行

### 3. メモリサイズの拡張

冗長化によりプログラムサイズが膨らむため、MemoryCore あたりの word 数 (現状 1024) を増やす必要があるか検討する。

### 4. アセンブラ/コンパイラの変更範囲

- アセンブラの命令テーブルに複数のbitパターンを許容するか
- コンパイラが意図的に冗長化を活用するか (e.g., 重要な命令を反復配置)

## M4 設計時の参考情報

### 現状の opcode 使用状況

| opcode 範囲 | 使用 | 空き |
|----------|------|------|
| 0-12 | ADD, SUB, MUL, DIV, MOD, AND, OR, XOR, SHL, SHR, IN, OUT, JALR | - |
| 13 | CHECKPOINT (M1) | - |
| 14-15 | 未使用 | 2 |
| 16-20 | ADDI, LW, SW, PUSH, POP | - |
| 21-23 | 未使用 | 3 |
| 24-27 | BEQ, BNE, BLT, BGE | - |
| 28-31 | 未使用 | 4 |
| 32-37 | LI, JMP, BEQL, BNEL, BLTL, BGEL | - |
| 38-62 | 未使用 | 25 |
| 63 | HALT | - |

未使用 opcode が 34 個ある。方式1 (opcode グルーピング) では、これらを既存命令の同義パターンとして再割り当てできる。

### 中立変異の必要性に関する直感

現状: 1bit 反転で命令種別が変わる確率は約 50% (有効 opcode 32/64)。
- ADD (opcode 0=000000) の bit を 1 つ反転 → 別の有効 opcode になる確率 ~50%
- 残り ~50% は無効 opcode (= NOP) となり、意味的には「何もしない」変異

つまり、現状でも opcode 1bit 反転の半分は事実上中立 (NOP)。残り半分が「別の命令になる」変異で、これが致死率の主因。

これを「同じ命令の別 bitパターン」に置き換えることで、より多くの bit 反転が真の中立変異 (元と同じ命令) になる。

### 予想される効果

opcode グルーピング (方式1) を実装した場合:
- 1bit 反転の中立率: ~50% → ~80% (推定)
- 致死変異率: 大幅に低下

ただし、これは opcode フィールドのみの話。レジスタフィールド (3bit × 3) や即値フィールド (4bit/16bit) は依然として脆弱。

### 全フィールド保護のコスト

完全な中立変異 (どのフィールドも 1bit 反転で意味が変わらない) を達成するには、Hamming符号や反復符号化が必要。これらはメモリ 2-3 倍を消費するため、現状の MemoryCore サイズでは大規模プログラムが入らなくなる。

## 評価指標 (M2/M3/M5 完了後の判定)

M4 の必要性は以下で判定する:

1. **M2/M3/M5 完了後、進化が起きているか?**
   - 種内多様性の経時変化を測定
   - 有性生殖下で新しい振る舞いが生まれているか

2. **進化のボトルネックは何か?**
   - 致死変異率が高すぎる → M4 が有効
   - 致死変異率は許容範囲だが多様性が生まれない → M4 ではなく別の問題
   - 既に進化が起きている → M4 は不要

3. **計算コストの余裕**
   - 命令数の増加が許容できるか
   - メモリサイズ拡張が現実的か

## 当面の方針

M4 は「将来の選択肢」として保留する。M2/M3/M5 を実装し、運用してから再評価する。

[v4 ロードマップ](../../../v4/docs/plan/program_robustness_roadmap.md) では M4 → M5 の順だったが、v5 では実装容易性を優先して **M2 → M3 → M5 → (再評価) → M4** の順序に変更する。
