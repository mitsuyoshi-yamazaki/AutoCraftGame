# v5 開発プロセス

v5 (auto-craft-game v5) のバージョン作成から実装完了までに行った/行う作業を記録する。各作業について、ユーザの意思決定が必要なパートと Claude が自律的に進められるパートを明示する。

## 凡例

| 記号 | 意味 |
|------|------|
| 👤 | **ユーザ意思決定**: ユーザの判断・指示・承認が必要 |
| 🤖 | **Claude 自律実行**: Claude が情報収集・実装・検証を進めて報告 |
| 🤝 | **協働**: Claude が提案し、ユーザが選択・修正する |

## v5 の経緯（要約）

v5 は v4 の延長として、「キャラクタープログラムのロバスト性向上」を目的として作成されたバージョン。v4 でユーザが「プログラムが少しでも壊れると全体が機能を失う」課題を提起し、Claude が解決策を提案・分析した結果として v5 が立ち上がった。

## 作業フェーズ一覧

### Phase 0: バージョン作成のきっかけ

#### 0-1. 課題の発見と問題提起
**👤 ユーザ意思決定**

ユーザが v4 の運用を通じて「プログラムが少しでも壊れると全体が機能を失う」「進化シミュレータとして致命的な欠陥になりうる」と判断し、Claude に分析を依頼。

> 課題提起の例: 「現在のVMでは、書き込みミスやスタックオーバーフローでメモリの内容が破損することがありうる。しかし、現在の仕様・キャラクタープログラムでは、プログラムが少しでも壊れると全体が機能を失ってしまう」

この**問題発見そのものがユーザの貢献**。Claude は症状を診断はできても、それがゲームシステムとしての欠陥であるという判断はユーザにしかできない。

#### 0-2. 課題の分析と複数案の提示
**🤖 Claude 自律実行 (報告ベース)**

Claude が以下を自律的に実施:
- 既存 VM の脆弱性分析（PC 迷走、制御フロー、スタック等の整理）
- v4 の `docs/issues/005_program_robustness.md` への問題記録
- 複数アプローチの提案 (`v4/docs/plan/program_robustness_*.md`):
  - 改善案 a, b: 符号化冗長化、分散制御
  - 改善案 c-h: 生物学的着想 (イベント駆動、反射、有性生殖等)
  - 改善案 i-n: 実行モデル（マルチスレッド、データフロー、チェックポイント等）

#### 0-3. 案の絞り込みと方針決定
**👤 ユーザ意思決定 (重要)**

各提案について、ユーザが以下を判断:
- 「VM がプログラムに強い構造的制約を課すべきでない」(M1 議論で確立)
- 「コード破壊は進化の材料として許容する」(書き込み保護を不採用)
- 「個体ロバスト性ではなく集団・種ロバスト性を目指す」(生物学的視点)

これらの方針決定により、採用候補が「追加的な改善 (m, d, f, a, e, i)」に絞られた。**この絞り込みはユーザの価値観・ゲームデザイン哲学に基づくため、Claude が代替できない**。

#### 0-4. ロードマップ策定
**🤖 Claude 提案 → 👤 ユーザ承認**

Claude が `v4/docs/plan/program_robustness_roadmap.md` を作成し、6 マイルストーン (M1-M6) と推奨実装順序を提案。ユーザが「ではそのマイルストーンで実装に着手せよ」と承認。

#### 0-5. v5 ディレクトリの用意
**👤 ユーザが実施**

ユーザが手動で v4 → v5 のディレクトリコピーを実施。Claude には「v5 ディレクトリを作成したのでそちらを変更せよ」と通達。

理由: バージョン管理は人間の責任範囲。Claude が勝手にディレクトリを増やすと混乱する。

### Phase 1: M1 (CHECKPOINT) 実装

#### 1-1. 設計の詳細決定
**🤝 協働**

Claude が設計上の質問をリストアップ (Q1〜Q9) し、ユーザが回答:
- PC リセット方式 (方式A: 毎tick開始時 vs 方式B: 命令上限到達時のみ)
- レジスタリセットの有無
- 既存プログラム改修範囲
- 検証手段 (CLI/GUI 両方)
- 成功基準 (最低限「破損が即座に複製停止に繋がらない」)
- バージョン番号 (5.0.0)
- UI 表示の詳細

ユーザが当初 方式B を選択 → Claude が方式 B の限界を指摘 → ユーザが方式 A に変更。**この往復に意味がある**。Claude が一方的に判断すべきではない。

#### 1-2. 仕様書更新
**🤖 Claude 自律実行**

`v5/docs/specs/vm/vm_spec.md`, `c_compiler_spec.md`, `ui_spec/*.md` を更新:
- CHECKPOINT 命令の定義
- cp / cpSet レジスタ
- tick 開始時のPCリセット動作
- UI の CheckpointHit 表示と CorruptButton

#### 1-3. 実装
**🤖 Claude 自律実行**

VM・アセンブラ・コンパイラ・プログラム・CLI・GUI・テストの実装。

途中、ユーザの方針 (「コード破壊は許容」) を踏まえた設計変更:
- マジックパターン `0x36A5` の導入 (偶発的な CHECKPOINT トリガー対策)

#### 1-4. 検証とチューニング
**🤖 Claude 自律実行**

破損注入テストを多数実施し、`v5/docs/tuning/checkpoint_M1.md` に記録:
- 1〜3 word 破損では完全な生命周期維持
- 5+ word 破損でも個体は約 200 tick 生存
- 周期的破損下でも種は繁殖継続

ユーザの最低基準を達成。

### Phase 2: M2 以降のマイルストーン実装計画

#### 2-1. 「次に何をするか」の方向性確認
**👤 ユーザ意思決定**

ユーザが「実装計画を立てよ」と指示。Claude は実装に着手する前にまず計画文書を作成する。

#### 2-2. 実装計画の作成
**🤖 Claude 自律実行**

以下を作成:
- `v5/docs/plan/README.md`: マイルストーン全体のインデックスと実装順序
- `v5/docs/plan/M2_reflexes.md`: 反射機構の詳細計画
- `v5/docs/plan/M3_apoptosis.md`: アポトーシス機構の詳細計画
- `v5/docs/plan/M5_sexual_reproduction.md`: 有性生殖の詳細計画
- `v5/docs/plan/M4_encoding_redundancy.md`: 符号化冗長化の保留分析
- `v5/docs/plan/development_process.md`: 本文書

各計画には「決定事項」と「未決事項」を明記。**未決事項があればユーザに確認するが、現状は全て決定済み**。

#### 2-3. 実装計画への承認
**👤 ユーザ意思決定**

ユーザが計画を確認し、必要なら修正指示。問題なければ「着手せよ」と承認。

### Phase 3: M2-M5 の実装 (順次)

各マイルストーンについて以下を繰り返す:

#### 3-1. 仕様書の更新
**🤖 Claude 自律実行**

実装計画を元に、対象の仕様書を先行して更新する:
- M2: `game_spec.md` に反射セクションを追加
- M3: `game_spec.md` にアポトーシスセクションを追加
- M5: `vm_spec.md`, `c_compiler_spec.md`, `game_spec.md` に CROSS_WRITE を追加

仕様 → 実装 の順序を守る (CLAUDE.md の方針)。

#### 3-2. 実装
**🤖 Claude 自律実行**

実装計画の「実装ステップ」順に進める。途中で計画の不備に気付いた場合は計画文書を更新してから続行。

#### 3-3. 動作検証と分析
**🤖 Claude 自律実行**

各マイルストーン完了時、または Claude が必要と判断したタイミングで:
- 全テスト実行
- 破損注入や統合シナリオの実行
- パラメータチューニング
- 結果を `v5/docs/tuning/<milestone>.md` に記録

#### 3-4. 完了報告と次マイルストーンへの移行
**🤝 協働**

Claude が「M2 完了。次は M3 に進む」と報告。ユーザが方針変更を指示しなければそのまま続行。

### Phase 4: M2-M5 完了後の再評価

#### 4-1. 進化観察結果のレビュー
**🤝 協働**

M2-M5 が完成した時点で、長時間シミュレーションを実行し:
- 進化が起きているか
- 多様性が維持されているか
- 致死変異率がボトルネックか

を観察。Claude が結果を整理して報告し、ユーザが解釈する。

#### 4-2. M4 の必要性判定
**👤 ユーザ意思決定**

観察結果を元に、ユーザが「M4 (符号化冗長化) を実装するか」「別の方向に進むか」「v5 を完了として v6 に進むか」を決定。

## ユーザ決定が必要なポイントの一覧

| フェーズ | 決定事項 | なぜ Claude では決められないか |
|--------|---------|---------------------------|
| 0-1 | 何が「課題」か | プロジェクトの価値観・最終目標との照合が必要 |
| 0-3 | 提案案の中から何を採用するか | デザイン哲学 (制約 vs 自由度、個体 vs 集団等) の判断 |
| 0-5 | バージョン番号の繰り上げ | リリース管理の責任は人間 |
| 1-1 | M1 設計詳細 (方式A/B等) | トレードオフの選択。Claude は両論を提示できるが選択はユーザ |
| 2-1 | 「次に何をするか」の指示 | 実装順序や優先度はプロジェクトオーナーの判断 |
| 2-3 | 実装計画への承認 | 計画の妥当性を評価する責任 |
| 3-4 | 計画変更の指示 | 進捗を見ての方針修正 |
| 4-2 | M4 の必要性判定 | 観察結果の解釈、次バージョンへの移行判断 |

| 1-3, 3-2 | 実装 | ✓ |
| 1-4, 3-3 | 検証・チューニング・記録 | ✓ |
| 2-2 | 実装計画文書作成 | ✓ |

Claude が自律実行する範囲は、**技術的な実装と分析に限定**される。設計判断や優先度判断はユーザに委ねる。

## 決定論性の確保について

Claude の自律実行範囲では、以下を必ず守る:

1. **仕様書を先に更新**: 実装と仕様の不一致を避ける
2. **テストファースト**: 不可能な場合もあるが、可能な限りテストを書いてから実装
3. **既存テストの非破壊**: 全テスト通過を確認してから次のステップへ
4. **小さな変更の積み重ね**: 一度に大規模変更を入れない
5. **CLAUDE.md と development.md のルール遵守**

これらを守ることで、ユーザは「Claude の自律実行を信頼して詳細を見ない」という選択ができる。
