# チューニング分析ガイド

本ドキュメントは、シミュレーションの実行・分析・記録を行う際の手順と観点をまとめたものである。分析を行ったことのない開発者やコーディングエージェントを対象とする。

## 分析の全体像

チューニング分析とは、「現在のパラメータと初期条件でシミュレーションを実行し、何が起きているかを定量的に把握し、改善の手がかりを得る」作業である。

作業の流れ:

1. **条件の確認** — 現在のパラメータ・プログラム・初期状態を把握する
2. **シミュレーション実行** — 複数のseedで実行し、再現性のあるデータを得る
3. **定量的な記録** — スナップショットから数値データを表にまとめる
4. **分析** — データからパターンや因果関係を読み取る
5. **記録の作成** — 結果と分析を `docs/tuning/` に記録する

## 1. 条件の確認

### 何を確認するか

シミュレーションの結果を左右する要素を把握する。

**ワールド設定（tuning-run.ts のオプション）:**
- マップサイズ（`--map-size`、デフォルト60）
- 各ノードの数（`--ore-nodes`, `--crystal-nodes`, `--energy-nodes`）
- ノードの初期残量（`--node-remaining`）

**ゲーム法則（`src/constants.ts`）:**
- 基礎代謝（コンポーネント別の代謝コスト）
- アクションコスト（MOVE, HARVEST, SENSE, PROCESS, CRAFT, ASSEMBLE）
- 物理パラメータ（MOVE_FORCE, FRICTION_COEFFICIENT 等）
- SENSE_RANGE（情報取得範囲）

**チューニング可能パラメータ（`--param key=value` で上書き）:**
- `inventoryMetabolismPerItem` — インベントリ内アイテム1個あたりの追加代謝
- `rechargeAmount` — 充電1回あたりのエネルギー回復量
- `frameDurability` — Frameコンポーネントの耐久値
- `assembleEnergyTransfer` — ASSEMBLE時に子に移転するエネルギー量

**プログラム:**
- v4ではキャラクターのプログラムはMini-Cで記述し、コンパイラ→アセンブラを通してバイナリとしてメモリに格納される
- 16ビットVMが毎tick命令を実行し、I/Oポートへの読み書きでアクションを発行する
- プログラムの効率（資源管理、充電タイミング等）がシミュレーション結果に大きく影響する

### 前回との差分を明確にする

「何が変わったか」を把握することが分析の出発点である。直近のチューニング記録（`docs/tuning/` の最新ファイル）を読み、現在の条件との差分を確認する。差分がなければ「同一条件の再確認」であり、差分があればその影響を中心に分析する。

## 2. シミュレーションの実行

### 基本コマンド

```bash
cd v4
npx tsx scripts/tuning-run.ts --ticks 5000 --seed 42 --snapshot-interval 500
```

### パラメータの上書き

`--param key=value` でデフォルトパラメータを上書きできる:

```bash
npx tsx scripts/tuning-run.ts --ticks 5000 --seed 42 --snapshot-interval 500 \
  --param inventoryMetabolismPerItem=0 \
  --param rechargeAmount=1000 \
  --param frameDurability=5000
```

### ワールド設定の変更

```bash
npx tsx scripts/tuning-run.ts --ticks 5000 --seed 42 --snapshot-interval 500 \
  --map-size 80 --ore-nodes 80 --crystal-nodes 80 --energy-nodes 60 --node-remaining 300
```

### 複数seedの実行

**再現性の確認のために必ず複数seedで実行する。** 1つのseedの結果だけでは、初期配置の偶然に起因する結果なのか、パラメータの構造的な帰結なのか区別できない。

最低3seed、理想的には5seedを推奨する。定番のseedは `42, 123, 999` で、追加する場合は `7, 2024` など。

```bash
for seed in 42 123 999; do
  npx tsx scripts/tuning-run.ts --ticks 5000 --seed $seed --snapshot-interval 500 \
    --param inventoryMetabolismPerItem=0
done
```

`--count N` オプションで同一条件を複数seed連続実行することもできる:

```bash
npx tsx scripts/tuning-run.ts --ticks 5000 --seed 42 --snapshot-interval 500 --count 3
```

### snapshotの粒度

- `--snapshot-interval 500` が標準。5000tickで10+1ポイントのデータが得られる
- 細かい動態を追いたい場合は `100` にする（データ量は多くなるが記録への転記は主要ポイントのみで十分）

### 実行結果の読み方

スクリプトは以下のブロックを出力する:

1. **条件サマリ** — seed、tick数、ワールド設定、パラメータ上書き
2. **Snapshots** — TSV形式の時系列データ（tick、人口、資源ノード数、エネルギー、誕生/死亡数）
3. **Action Stats** — アクション種別ごとの実行回数と成功/失敗率

v4ではv3と異なり種族は現在1種（Replicator）のみであるため、種族別の列はない。代わりにアクションの成功/失敗率がプログラムの動作確認に重要な指標となる。

## 3. 記録に書く内容

ファイルは `docs/tuning/` に連番で作成する（例: `001_baseline_self_replication.md`）。

### ドキュメントの構造

```
# NNN: タイトル（何を確認するための実行か）

日付: YYYY-MM-DD

## 目的
  なぜこの実行を行うのか。何を確認・検証したいのか。

## 発見されたバグ
  チューニング中に発見・修正したバグがあれば記録する。（任意セクション）

## プログラム改善
  プログラムの変更履歴があれば記録する。（任意セクション）

## キャラクター仕様
  コンポーネント構成、プログラムサイズ、基礎代謝。

## パラメータ探索
  変更パラメータと不変パラメータを表形式で。
  変更の理由を明記する。

## 結果
  サマリ表（各seedの最終人口、ピーク人口、総誕生/死亡）
  各seedのスナップショット表

## 分析
  データから読み取れるパターンと、その構造的な理由の考察。
  番号付きで、1項目1観点で記述する。

## 所見
  達成事項、課題、改善方向をまとめる。
```

### サマリ表

全seedの結果を横断的に比較できる表を最初に置く。一覧することで全体像が掴める。

```
| seed | 最終人口 | ピーク人口 | 総誕生 | 総死亡 |
|------|---------|----------|--------|--------|
| 42   | 8       | 98       | 95     | 90     |
```

### スナップショット表

スクリプトの出力から主要なtickポイントを選んで転記する。全ポイントを載せる必要はなく、フェーズの変わり目や注目すべき変化が見えるポイントを選ぶ。

## 4. 分析の観点

データを眺めて「何が起きたか」を記述するだけでは分析にならない。**「なぜそうなるか」の構造的な理由**まで踏み込むことが重要である。

### 基本の分析観点

#### (a) 人口動態のフェーズ

時系列データを見て、人口がどのようなフェーズを経るかを特定する。v4での典型的なパターン:

- **増殖期** — 資源が豊富な序盤に人口が急増する
- **飽和期** — 資源ノード枯渇に伴い増殖が停止する
- **老化期** — 初期世代のFrame耐久値が尽きて順次死亡する
- **再生期** — 死亡後のノード再生により新世代が複製可能になる（理想的にはここで持続可能なサイクルが生まれる）

フェーズの切り替わりtickと、各フェーズでの誕生/死亡の比率を確認する。

#### (b) アクション成功率の分析

v4ではI/Oポート経由のアクション発行が正しく動作しているかが重要な確認事項となる:

- **HARVEST成功率**: 資源ノード上にいるときのみ成功する。低い場合はSENSEやMOVEのロジックに問題がある
- **PROCESS/CRAFT成功率**: レシピIDや材料の不足が原因で失敗する。コンパイラ定数との整合性を確認する
- **ASSEMBLE成功率**: 全コンポーネントが揃っているか、エネルギーが足りているかで決まる

#### (c) seed間の再現性

「全seedで同じ結果か、seedによって結果が異なるか」を確認する:

- 全seedで同じ → パラメータの構造的な帰結（確信度が高い）
- seedによって異なる → 初期配置の偶然に左右される（確信度が低い）

#### (d) 資源経済の持続性

資源が枯渇するか、持続するかを確認する:

- **資源ノード残存数の推移**: 消費ペースは一定か、加速/減速しているか
- **エネルギー蓄積量の推移**: 人口に対してエネルギーが余っているか不足しているか
- **代謝とエネルギー収支**: 基礎代謝 × 人口 と充電能力のバランス

#### (e) プログラムの効率

v4ではプログラムのロジックがシミュレーション結果に直結する:

- **インベントリ管理**: 大量のアイテムを長時間保持するとインベントリ代謝が増大する
- **充電戦略**: エネルギー残量に応じた充電タイミングの最適化
- **収穫と加工のインターリーブ**: 収穫→即加工でインベントリサイズを抑える戦略

## 5. よくある落とし穴

### 「何が起きたか」の記述で終わる

スナップショットの数値を言い換えただけの分析は価値が低い。「tick 2000で人口が78に達した」ではなく、「基礎代謝19/tickに対し充電1000/回で約52tick分のバッファがあり、収穫→加工→組立の1サイクル（~500tick）を賄えるため安定的に増殖する」のように、構造的理由まで踏み込む。

### 1つのseedの結果を一般化する

seed 42で「ピーク98」であっても、seed 123では「ピーク76」かもしれない。必ず複数seedの結果を横断的に確認し、再現性のある傾向と配置依存の偶然を区別する。

### VMやコンパイラのバグを見逃す

v4ではプログラムがMini-C→コンパイラ→アセンブラ→16ビットVMという多段パイプラインを通るため、各段階でのバグがシミュレーション結果に影響する。アクション成功率が異常に低い場合は、パラメータの問題ではなくVMやコンパイラのバグを疑う。

### 改善案を具体化しすぎる

「所見」セクションで改善案を挙げる場合、パラメータの具体的な値まで提案する必要はない。方向性にとどめ、具体的なパラメータは次の実験で探索する。

## 6. 記録のファイル命名と管理

- ファイル名: `NNN_概要.md`（例: `001_baseline_self_replication.md`）
- 連番は `docs/tuning/` 内の既存ファイルの最大番号 + 1
- README.md の調整記録テーブルにも追記する
- 分析の目的が異なれば別ファイルにする（同じ実行条件でも観点が異なれば分けてよい）
