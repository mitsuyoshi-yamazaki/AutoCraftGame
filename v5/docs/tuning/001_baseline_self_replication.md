# 001: ベースライン自己複製の達成

日付: 2026-04-06

## 目的

v4 VMアーキテクチャで初の自己複製を達成するパラメータ組み合わせを探索する。

## 発見されたバグ

1. **RECIPE/CRAFT IDの不一致** (actions.ts): コンパイラ定数(0-based)とアクション実行側(1-based)のずれ。全PROCESS/CRAFTが無条件失敗していた。
2. **スタックリーク** (コンパイラ/VM): `halt(); continue;` パターンでローカル変数のスタック領域が解放されず、長時間実行でメモリ破壊。グローバル変数のみ使用で回避。
3. **WRITE/ACTIVATE予約の上書き**: 同一tick内でProcessor:0スロットのWRITEがACTIVATEに上書きされる。別tickに分離して解決。

## プログラム改善

- v1 (初期): harvest_count>20 で複製試行 → 資源不足 (52回必要)
- v2: 正しい資源計算、SENSE毎tick
- v3: ヒステリシス充電 (200-600)
- v4: WRITE/ACTIVATE分離
- v5: 全変数グローバル化 (スタックリーク修正)
- v6 (最終): 安定動作確認

## キャラクター仕様

Components: Frame×3, Actuator, Harvester, Charger, Assembler, Processor, Sensor, MemoryCore×2 (11 components)
プログラムサイズ: 1144 words (MemoryCore×2 = 2048 words memory)

## 分析

1. **増殖フェーズ (tick 0-3000)**: 指数関数的増殖。3→33→78→93。初期個体が~500tickで複製し、子も同様に複製。
2. **飽和フェーズ (tick 3000-7000)**: 人口安定。資源ノード枯渇(100→69)が増殖を制限。誕生0、死亡0。
3. **老化フェーズ (tick 7000-10000)**: 初期世代の寿命(frameDurability×3=15000 ticks at normal decay)に達し始め、順次死亡。資源ノードが再生(69→161)。
4. **再現性**: 全seedで同じパターン(増殖→飽和→老化)。ピーク人口は69-98と幅があるのは初期配置による。
5. **資源制約**: ピーク人口は資源ノード数(ore:50+crystal:50)に制約される。各キャラクターが56回の収穫を必要とし、ノードあたり225回→約4キャラクター分。
6. **持続性**: tick 10000時点で少数生存(3-8)。2世代目以降の複製が限定的。老化した初期世代の死後、ノード再生により新世代が複製可能になる兆候あり(resNodes増加)。

## 所見

### 達成事項

- v4 VMアーキテクチャでの自己複製を初めて達成
- Mini-Cプログラムが正しくコンパイル→アセンブル→実行→複製サイクルを完了
- 複数世代の増殖を確認（seed 42で95誕生）

### 課題

- **2世代目以降の複製が不安定**: 資源枯渇により停滞。飽和後の新規複製がゼロに近い。
- **inventoryMetabolismPerItem=0 は非現実的**: 物質保存則の観点からインベントリ代謝が0であるべきではない。インベントリ代謝を維持しつつ複製を可能にするには、プログラムの資源管理を改善する必要がある（収穫と加工のインターリーブ等）。
- **frameDurability=5000 は大幅な増加**: デフォルトの16.7倍。より合理的な値での動作を目指すべき。

### 改善方向

- プログラムで収穫と加工をインターリーブし、インベントリサイズを小さく保つ
- 複数の充電・収穫サイクルを効率的に組み合わせる
- 資源再生メカニズムの活用（残骸の分解等）

## 仕様変更の提案

以下はゲーム仕様を変更せずに今回の探索で見つけた課題と、それを解決しうる仕様変更の提案である。

### 1. インベントリ読み取りI/Oの追加

**課題**: プログラムが自身のインベントリを読み取れないため、PROCESS/CRAFTの成否を事前に判定できない。資源収集量をハードコードする必要があり、型の不一致（Ore収穫のつもりがCrystalだった）に対応できない。

**提案**: インベントリ読み取り用のI/Oアドレス（例: `IN r1, INVENTORY_ORE` → Ore所持数を返す）を追加する。これによりプログラムが動的に資源管理できるようになり、inventoryMetabolismPerItem > 0 でも収穫と加工のインターリーブが可能になる。

### 2. HARVEST対象の指定

**課題**: `harvest()` は最も近い資源ノード（種類不問）を採取する。Ore狙いでCrystalNodeの隣にいると意図しない資源を取得する。

**提案**: HARVESTコマンドに対象ノード種別フィルタを追加する（例: `HARVEST_ORE`, `HARVEST_CRYSTAL`）。あるいはSENSEで取得したlocal IDを指定して特定ノードから採取する方式。

### 3. コンパイラのスタック管理改善

**課題**: `halt(); continue;` パターンでローカル変数のスタック領域がリークする。これはコンパイラのバグであり仕様変更ではないが、ユーザープログラムの記述性に大きく影響する。

**提案**: codegen.tsの`continue`文処理で、現在のスコープのローカル変数分のスタック巻き戻しを生成する。

### 4. 同一コンポーネント複数アクションの許可

**課題**: WRITE（Processor:0）とACTIVATE（Processor:0）が同一tickで衝突する。プログラムは2tickに分けて対処するが、非直感的。

**提案**: 同一コンポーネントスロットで1tick内に複数の異なるコマンドを発行可能にする（キューイング方式）。あるいはACTIVATEを別コンポーネント（Assembler等）に移動する。
