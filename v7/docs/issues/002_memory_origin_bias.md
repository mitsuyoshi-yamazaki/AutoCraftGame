# 002: メモリアドレスの原点バイアス

## 問題

Processor のプログラムメモリは 1024 ワードの循環空間であり、仕様上どのアドレスにも「原点」としての特権はない。しかし現在の実装では、アドレス 0 が事実上の原点として固定されている。

### 原点バイアスの発生箇所

1. **プログラム配置**: `createProcessor` がプログラムをアドレス 0 から書き込む
2. **コピー開始**: レプリケータプログラムが `PMEM_ADDR = 0` を明示的に設定し、アドレス 0 から順にコピーする
3. **PC 初期値**: 新規 Processor の PC が 0 に設定される

### 変異への影響

コピーがドリフトアウト（近接範囲外への移動）で中断された場合、欠損するのは常にアドレスの「末尾」側である。プログラムがアドレス 0 から配置されているため:

- 先頭側（プログラム本体）は常にコピーされる
- 末尾側（ゼロ埋め領域）が欠損する
- 結果として変異は無害な「末尾ゼロ埋め」にとどまる

プログラムの中央部が欠損するようなドリフトアウトや、異なるプログラムの断片が混在するキメラ型変異は、この構造では原理的に発生しにくい。

## 分析

### なぜアドレス 0 が特権化されているか

根本原因は**ロング分岐命令（BEQL, BNEL, BLTL, BGEL）と JMP が絶対アドレスを使用する**ことにある。

| 命令種 | アドレス指定 | 備考 |
|--------|------------|------|
| BEQ, BNE, BLT, BGE | PC 相対オフセット（4bit 符号付き） | 位置独立だが範囲 -8〜+7 |
| BEQL, BNEL, BLTL, BGEL | **絶対アドレス**（16bit） | 位置依存 |
| JMP | **絶対アドレス**（16bit） | 位置依存 |
| JALR | レジスタ間接 | 値次第 |

現在のレプリケータプログラム（120 ワード）は分岐距離がショート分岐の範囲（±7）を超えるため、全てロング分岐（絶対アドレス）を使用している。このため、プログラムはアドレス 0 に配置されることを前提としており、別のアドレスに配置すると分岐先が不正になり動作しない。

### コピー開始アドレスを変えるだけでは不十分

仮にコピーの開始アドレスをオフセット X にしても:
- ソースの `memory[X], memory[X+1], ...` が正しくコピーされる（LW は循環アドレス対応）
- ターゲットの `memory[X], memory[X+1], ...` に書き込まれる（PMEM_ADDR も循環）
- **プログラム内の絶対分岐アドレスはそのまま** → 分岐先は正しい

つまり、循環コピーならプログラムの配置アドレス自体は変わらないため、コピー開始オフセットを変えることはプログラムの正当性に影響しない。ドリフトアウトの切断点だけが変わる。

## 解決の方向性

### 方式 A: コピー開始オフセットの変動（プログラム側変更のみ）

プログラムが `PMEM_ADDR = 0` ではなく、自然に変動する値をオフセットとして使う。

```
現在:  PMEM_ADDR = 0,        ソース読み出し = LW r1, [0 + i]
変更:  PMEM_ADDR = offset,   ソース読み出し = LW r1, [offset + i]
```

オフセット候補:
- **tick 値** (`IN 0x0002`): tick ごとに +1 される自然なカウンタ
- **前回コピーの終了地点**: I/O レジスタ永続化により PMEM_ADDR は保持されるため、明示リセットしなければ前回の続きから始まる
- **自身の PC 値**: 実行タイミングにより自然にばらつく

長所:
- システム変更不要。VM もコピー機構もそのまま
- ソースとターゲットが同一オフセットから循環コピーすれば、プログラムの絶対アドレスはそのまま保たれる
- ドリフトアウトの切断点がプログラム中央部に来る可能性が生まれる

短所:
- プログラム側の複雑化（オフセット計算の命令追加）
- プログラムがこの機構を「自覚的に」実装する必要がある

### 方式 B: ロング分岐を PC 相対化（VM 変更）

BEQL, BNEL, BLTL, BGEL の第 2 ワードを「絶対アドレス」から「PC 相対オフセット」に変更する。

```
現在:  BEQL rs1, rs2, [absolute_target]   → pc = target
変更:  BEQL rs1, rs2, [relative_offset]   → pc = pc + offset
```

長所:
- プログラムが位置独立（Position Independent Code）になる
- アドレス 0 の特権性が完全に消滅
- コピー先の配置アドレスを自由に変えられる（方式 D と組み合わせ可能）

短所:
- VM 仕様の変更が必要
- 既存の全プログラム（手動アセンブル含む）の分岐アドレスを相対に書き換える必要がある
- JMP 命令も相対化するか、廃止するか検討が必要

### 方式 C: プログラム配置アドレスの分散（方式 B が前提）

方式 B で位置独立コードが実現した上で:
- Processor 間コピー時、ターゲットへの書き込み開始アドレスをコピー元の PC 等から決定
- 新規 Processor の PC 初期値を配置アドレスに合わせる

長所:
- 各 Processor のプログラムが異なるアドレスに配置され、メモリ空間に「原点」がなくなる
- ドリフトアウトの切断点が完全に一様分布する

短所:
- 方式 B の実装が前提
- PC 初期値の設定に追加の仕組みが必要

### 方式 D: コピー対象領域の制限廃止

copySize を廃止し、常に 1024 ワード全体をコピーする。

長所:
- 「プログラム末尾」という概念がなくなる
- ドリフトアウトはプログラム内の任意の位置を切断する

短所:
- コピーに要する命令数が増加（1024 × 4 = 4096 命令）
- 低 instructionsPerTick 環境ではコピー完了に多数の tick を要する
- 方式 A と組み合わせなければ、切断点はやはりプログラム末尾に偏る

## 推奨

**短期: 方式 A**（プログラム側変更のみ）で効果を検証する。システム変更なしで実装可能であり、ドリフトアウトの切断点を分散させる効果が確認できる。

**長期: 方式 B**（ロング分岐の相対化）を検討する。位置独立コードは変異の多様化だけでなく、プログラムの断片化・再結合による進化的探索の可能性を開く。ただし VM 仕様の変更を伴うため、v7 の範囲で行うか次バージョンに持ち越すかは別途判断が必要。

## ステータス
