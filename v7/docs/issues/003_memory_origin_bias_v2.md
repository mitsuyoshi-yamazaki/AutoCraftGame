# 003: メモリアドレスの原点バイアス（改訂版）

[002](002_memory_origin_bias.md) の改訂版。ロング分岐の PC 相対化（方式 B）と LABEL/JMPL/LWL/SWL 命令（ラベル機構）の追加により状況が変わったため、現時点での原点バイアスを再整理する。

## 問題の定義

Processor のプログラムメモリ（1024 ワード）は仕様上循環しており、どのアドレスにも原点としての特権はない。しかし実装・仕様の複数箇所でアドレス 0 が「始点」として扱われており、以下のような現象の根本原因となっている:

- ドリフトアウトによる変異が「プログラム末尾のゼロ埋め」にしか現れない
- プログラムの配置アドレスが常に 0 であり、位置独立性の恩恵を受けていない
- 複製された Processor は全て同一の配置になり、メモリ空間の使い方が均質化する

## 既に対応済みの事項

### 方式 B: ロング分岐・ジャンプの PC 相対化

[002](002_memory_origin_bias.md) で対応:

- `BEQL, BNEL, BLTL, BGEL` の第 2 ワードを絶対アドレスから **PC 相対の符号付き 16bit オフセット**に変更
- `JMP` も同様に PC 相対化
- 短分岐 `BEQ, BNE, BLT, BGE` はもともと PC 相対

これにより、「分岐命令の中のアドレス」に関する原点バイアスは解消された。プログラム本体は理論上どのアドレスに配置しても動作する。

### ラベル機構: LABEL / JMPL / LWL / SWL

複数地点から同一地点への合流（関数呼び出し・ループ continue 等）を PC 相対だけで表現するのは難しいため追加:

- `LABEL imm10`: メモリ内目印（実行時 NOP）
- `JMPL imm10`: 同 ID の LABEL を検索し、その次のワードへジャンプ
- `LWL rd, rs, imm10`: `mem[label_addr + 1 + rs]` を rd にロード
- `SWL rs_val, rs_idx, imm10`: `mem[label_addr + 1 + rs_idx] = rs_val`

識別性は**内容**（メモリに書かれた値のパターン）に基づくため、プログラムのどの位置にあっても探索できる。

## 現時点で残っている原点バイアス

以下のコード調査の結果、アドレス 0 または絶対アドレスに依存している箇所が **6 系統** 残っている。

### 1. Processor の初期 PC

**場所**:
- [processor.ts:50](../src/processor.ts#L50): `createProcessor` が `pc: 0` で生成
- [assembler.ts:338](../src/assembler.ts#L338): `createEmptyProcessor`（Assembler がレシピ 4 で生成する空の Processor）が `pc: 0`

**問題**: 起動された新規 Processor は必ずアドレス 0 から実行を開始する。コピーされたプログラムがアドレス 0 に配置されている前提。

### 2. Processor へのプログラムロードがアドレス 0 から始まる

**場所**:
- [processor.ts:34-37](../src/processor.ts#L34-L37): `createProcessor` が `memory[i] = program[i]` でアドレス 0 から書き込み
- [vm.ts:150-159](../src/vm/vm.ts#L150-L159): `loadProgram` ヘルパーが同様にアドレス 0 から書き込み

**問題**: 初期状態でワールドに投入される Processor は全てアドレス 0 にプログラムを持つ。

### 3. レプリケータプログラムが `PMEM_ADDR = 0` を明示設定

**場所**:
- [programs.ts:134](../src/programs.ts#L134): `li(1, 0); li(2, PMEM_ADDR); out(1);` — コピー先 Processor の書き込み開始位置を 0 に設定
- [programs.ts:136](../src/programs.ts#L136): `li(6, 0);` — ソース読み出しカウンタも 0 から開始

**問題**: レプリケータが対象 Processor に書き込む際、常に**対象側のアドレス 0 から**プログラムをコピーする。ソースアドレスも 0 から。結果として、複製世代を経てもプログラムの配置は全て「アドレス 0 基点」に固定される。この 2 行がある限り、位置独立コードの恩恵を受けられない。

### 4. JALR がレジスタ値を絶対 PC として扱う

**場所**:
- [vm.ts:432-440](../src/vm/vm.ts#L432-L440): `case Opcode.JALR` — `target = readReg(registers, rs)` を直接 PC に代入
- 戻りアドレスは `(pc + 1) & WORD_MASK`（絶対 PC）

**使用状況**:
- v7 のレプリケータプログラム（`programs.ts`）は JALR を使っていない
- レガシーの Mini-C コンパイラ（`vm/compiler/codegen.ts`）が関数呼び出しで JALR を使う — v7 では未使用のパスだが、コード自体は残っている

**問題**: 位置独立ではない。呼び出し規約の再設計（例: レジスタ値を PC 相対オフセットとして扱う）が必要だが、既存の Mini-C 依存との整合性を取るため別課題扱いとする。

### 5. 仕様と実装の齟齬: HALT 後の PC 挙動

**場所**:
- [game_spec.md:299](docs/specs/game_spec.md#L299): 「HALT | 実行停止（次 tick で **PC=0 から再開**）」
- [game_spec.md:431](docs/specs/game_spec.md#L431): 「HALT に到達すると当該 tick の実行を終了し、**次 tick で PC=0 から再開する**」
- [vm.ts:425-427](../src/vm/vm.ts#L425-L427): 実装は `pc: wrapPc(pc + 1, memSize), halted: true` — **PC を 0 にリセットしない**

**問題**: 仕様は「次 tick で PC=0 から再開」としているが、実装はそうなっていない（HALT 命令の次のアドレスに進み、ゼロメモリを NOP として走り続ける）。

- 仕様どおりに実装すると: アドレス 0 が絶対的な「再起動点」となる。極めて強い原点バイアス
- 現状の実装: 原点バイアスはむしろ弱い（PC は HALT 後も自然に循環する）

**対応方針**: 位置独立を重視するなら、**仕様を実装に合わせる**（HALT は PC リセットしない）か、または HALT を完全に削除する方向で仕様を修正すべき。

### 6. 「プログラムはアドレス 0 に配置される」という暗黙の前提

**場所**: 仕様書全体を通じて、「プログラムメモリ」「PC」「HALT による再開位置」などの記述がアドレス 0 を始点として語られている。

**問題**: 明示的な記述は少ないが、設計思想として「プログラムは 0 番地から」というメンタルモデルが根付いている。これは現実装にも反映されている（項目 1-3）。

## 残る原点バイアスの分類

| カテゴリ | 該当項目 | 影響 |
|---------|---------|------|
| **初期配置**（Processor 生成時） | 1, 2 | 初期状態・Assembler 生成の新規 Processor が常にアドレス 0 から |
| **複製プロトコル**（レプリケータプログラム側） | 3 | 世代を経ても全ての複製がアドレス 0 基点 |
| **呼び出し規約**（VM 命令） | 4 | JALR は位置独立でない。v7 レプリケータは未使用だが存在 |
| **仕様書の齟齬**（ドキュメント） | 5 | 仕様と実装の不一致。修正方針次第で原点バイアスが強くも弱くもなる |
| **メンタルモデル** | 6 | 設計思想レベル |

## 解決の方向性（再整理）

### 短期的対応: 方式 A（コピー開始オフセットの変動）

[002](002_memory_origin_bias.md) で挙げた方式 A に相当。以下の変更でプロトコル上の原点バイアス（項目 3）を解消できる:

1. レプリケータプログラムが `PMEM_ADDR = 0` を明示設定しない
2. 代わりに「何らかの自然に変動する値」をオフセットとして使う
   - 候補: tick 値（`IN 0x0002`）、I/O レジスタ永続値、自身の PC
3. ソース読み出しカウンタも同じオフセットから開始
4. ループ終了条件は `offset + copySize` で判定

循環メモリなので、ソースとターゲットが同一オフセットから書き出せばプログラムの絶対アドレスは保たれる。ドリフトアウトの切断点だけが分散する。

### 中期的対応: 方式 C（プログラム配置アドレスの分散）

項目 1, 2（初期 PC と配置）に対応:

1. 新規 Processor の PC 初期値をランダム化（または決定的だが分散する値に）
2. プログラム本体はその PC 位置から配置する
3. メソッド B の位置独立コードが前提

ただし、項目 3（複製プロトコル）と協調する必要がある。「コピー先のどこに書くか」と「コピー先の PC 初期値をどこに設定するか」を一致させなければ新しい Processor は起動できない。

### 長期的対応: 項目 4・5 の整合

- 項目 4（JALR）: 位置独立な呼び出し規約への変更。ラベル機構を使えば `JMPL + LABEL` で代替可能なため、JALR を廃止するのも一案
- 項目 5（HALT の PC リセット）: 仕様を実装に合わせ、HALT は単に実行を停止するだけ（PC は維持）とする。あるいは HALT 命令自体を廃止し、プログラムは無限ループで終了しないことを前提とする

## 推奨される次のアクション

1. **項目 3（最優先）**: レプリケータプログラムに方式 A を適用する。`PMEM_ADDR = 0` を可変オフセットに変える。変異実験で切断点の分散を確認する
2. **項目 5（仕様整合）**: HALT の挙動について、仕様と実装のどちらを正とするか判断し、片方を修正する
3. **項目 1-2（構造的）**: 新規 Processor の PC 初期値と配置アドレスを分散可能にする。ただし項目 3 との協調設計が必要

## ステータス

- 方式 B（PC 相対分岐）: **実施済み**
- ラベル機構（LABEL/JMPL/LWL/SWL）: **実施済み**
- 項目 1, 2, 6（初期 PC・プログラムロード・暗黙の前提）: **基準点として解釈し直す形で仕様確定**（7-2a 節に明記）。実装は現状維持で問題なし
- 項目 3（レプリケータの `PMEM_ADDR = 0`）: 仕様上は「対象の基準点からのオフセット」と再定義（8-4 節）。**実効的な分散にはレプリケータ側の変更が別途必要**（未着手）
- 項目 5（HALT 仕様整合）: **仕様を実装に合わせる形で確定**（HALT は PC をリセットしない。7-3 / 7-8 節を修正）
- **項目 4（JALR 廃止）**: **保留**。JALR は絶対 PC を扱う命令として暫定的に存続。理想的ではないが、v7 の範囲では代替が非自明（関数呼び出しの戻り先処理）であり、ラベル機構だけでは直接 1:1 代替できないため

### 今後の課題

- レプリケータプログラム側での方式 A（コピー開始オフセット・ソース読み出し位置の変動）適用
- ドリフトアウト変異の多様化実験（プログラム内の任意位置に切断点を分散させる）
- JALR 廃止の検討（関数呼び出し規約の再設計または代替パターンの確立）
