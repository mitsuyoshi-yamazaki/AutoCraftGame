# v7 実装前に決定すべき事項

`01_goal.md` の内容を前提とする。
v7 はこれまでの「キャラクター＝コンポーネントの集合」モデルを廃し、**コンポーネントが独立した物体として世界に存在するモデル**に移行する。

---

## 1. 世界モデル

### 1-1. 物体の種類

v6 では Character, ResourceNode, EnergyNode, Remains, Wall が存在した。
v7 では「キャラクター」の概念がなくなる。世界に存在する物体の種類を定義する必要がある。

`01_goal.md` から読み取れる候補:
- コンポーネント（Assembler, Processor, ...）
- 原材料（Ore, Crystal）
- 中間生成物（Metal, Circuit）
- エネルギー（物体として漂う？ or ノードから供給？）
- 資源ノード（Ore/Crystal の発生源。残すのか？）
- エネルギーノード（残すのか？）

**決定が必要な点:**

a. **エネルギーの物理的表現**: エネルギーは物体として世界に漂うのか、それとも v6 同様にノードから取得するのか。「コンポーネントが周囲のエネルギーを取り込む」とあるので物体として存在する想定と読めるが、確認が必要。

b. **資源の発生メカニズム**: 原材料（Ore, Crystal）は資源ノードから HARVEST するのか、それとも物体として世界に散在しているのか。「中間生成物とエネルギーが無数に漂っている」とあるので、資源も物体として漂う可能性がある。資源ノードの概念を残すか。

c. **物体の統一的表現**: 全ての物体（コンポーネント、原材料、中間生成物、エネルギー）を同一の型で表現するか、それとも種類ごとに異なる型を持つか。統一型であればシステムがシンプルになるが、種類ごとに振る舞いが異なる場合は型を分ける方が自然。

### 1-2. 力場

「物体をランダムに移動させる力場がある」とある。

**決定が必要な点:**

a. **力場の種類と配置**: 力場は世界全体に一様に存在するのか、それとも局所的なものか。ランダムな方向に物体を移動させるブラウン運動的なものか、特定のパターン（渦、放射等）を持つものか。

b. **力場の対象**: 全物体に作用するのか、特定の物体（コンポーネント以外の小物体のみ等）に限定されるのか。コンポーネント自体も力場で移動するのか。

c. **力場と Actuator の関係**: v6 の Actuator は MOVE アクションで力を加えるコンポーネントだった。力場がある世界では Actuator の役割はどうなるか。Processor が Actuator を制御して能動的に移動する機能は残すのか。

### 1-3. 衝突と相互作用距離

v6 では全物体に半径があり、衝突判定が行われていた。

**決定が必要な点:**

a. **コンポーネント間の「近接」の定義**: 「対象が一定距離内にいる必要がある」とある。この距離は一律か、アクション種別ごとに異なるか。

b. **Assembler の「周囲から取り込む」範囲**: Assembler が原材料・エネルギーを「周囲から回収」する範囲の定義。固定半径か、Assembler のパラメータか。

---

## 2. コンポーネント仕様

### 2-1. Assembler

`01_goal.md` より: 「設定されたレシピをもとに、周囲の原材料とエネルギーを取り込み、材料が充足すると生成物を出力する」

**決定が必要な点:**

a. **レシピの設定方法**: レシピは Assembler の内部状態として保持されるのか。レシピの表現形式は何か（生成物の種類だけ？ 材料リストも含む？）。レシピは変更可能か（Processor が書き換えられるか）。

b. **取り込みの自動性**: Assembler はトリガーされたら自動で周囲の材料を取り込むのか、それとも何らかのトリガー（Processor からの指示、あるいは「材料が近くにある」という条件自体がトリガー）が必要か。`01_goal.md` の記述では「ASSEMBLEをトリガーされると」とあるので、明示的なトリガーが必要と読める。

c. **実行時間**: 「ASSEMBLEを行うにはn tickかかる」とある。n はレシピによって異なるか、固定か。材料の回収期間もこの n に含まれるか、それとも「材料回収完了 → n tick → 生成物放出」か。

d. **生成物の放出**: 生成物はどこに出現するか。Assembler の近傍にランダム方向か、特定方向か。

e. **レシピが未設定の Assembler**: 初期状態の Assembler（想定 e）は「レシピが設定されていない」とある。レシピ未設定の Assembler は何も生産しないのか、それとも何らかのデフォルト動作があるのか。

### 2-2. Processor

`01_goal.md` より: 「レジスタとMemoryCoreを持たずとも、単体で最低限動作するスペックを持つ」

**決定が必要な点:**

a. **「最低限動作するスペック」の定義**: レジスタなし・メモリなしの Processor が実行可能な命令は何か。具体的にどの程度の機能を持つか。
   - v6 の VM は汎用 16bit マシンだった。v7 の最小 Processor はそこまで必要ない
   - 「別のAssemblerやProcessorへアクセスする」「自身のメモリ内容をコピーする」が記載されている
   - 最低限: 近接コンポーネントの検出、対象への書き込み（レシピ設定、メモリコピー）

b. **Processor の内蔵メモリ**: 「レジスタとMemoryCoreを持たずとも」とあるので、Processor 自体に少量の内蔵メモリがある想定か。それは何ワードか。

c. **Processor のアクション**: Processor が実行可能なアクションの一覧。`01_goal.md` から読み取れるもの:
   - 近接コンポーネントの探索（SENSE 相当）
   - 別の Assembler のレシピフィールドへの書き込み
   - 別の Processor のメモリへの自身のメモリ内容のコピー
   - （Actuator 制御は？ 明記なし）

d. **Processor の実行モデル**: 毎 tick プログラムを実行するのか、v6 の VM と同じモデルか。あるいはイベント駆動（近くに対象が来たら発火）か。

e. **プログラムの表現**: Processor のメモリに格納されるプログラムの形式。v5/v6 の 16bit 命令セットを流用するか、新規に設計するか。

### 2-3. その他のコンポーネント

`01_goal.md` では Assembler と Processor のみ言及されている。

**決定が必要な点:**

a. **v6 の他コンポーネントの扱い**: Frame, Actuator, Sensor, Harvester, Charger, Disassembler, MemoryCore のうち、v7 に残すものはどれか。

   - **Frame**: 「durability の概念もなくなる」とあるので、Frame の主機能（耐久値基盤）は不要。コンポーネントの構造体としての役割は？
   - **Actuator**: 力場がある世界での能動移動は必要か
   - **Sensor**: Processor が「近接コンポーネントを探索」するなら、Sensor は Processor に統合されうる
   - **Harvester**: 資源が物体として漂うなら「採取」アクションは不要（Assembler が周囲から取り込む）
   - **Charger**: エネルギーが物体なら Charger も不要（Assembler/Processor がエネルギーを直接取り込む）
   - **Disassembler**: 物体の分解は必要か
   - **MemoryCore**: Processor の外部メモリ拡張。残すなら Processor がメモリ不足時に MemoryCore を使う形

b. **コンポーネント種別の最小セット**: v7 の世界で存在するコンポーネントの最小セットは何か。`01_goal.md` の想定振る舞いからは **Assembler と Processor のみ** で自己複製が回る設計に見える。他のコンポーネントを削るか、将来的な拡張として定義だけ残すか。

## 3. 自己複製のメカニズム

### 3-1. 複製の工程

`01_goal.md` の想定振る舞いでは、4 種の初期コンポーネント（a〜d）が協調して複製サイクルを回す。

```
a: Assembler(レシピ=Assembler)  → e: 空Assembler を生成
b: Assembler(レシピ=Processor)  → f: 空Processor を生成
c: Processor(機能=Assemblerにレシピ設定 + Processorにメモリコピー)
d: Processor(機能=Assemblerにレシピ設定 + Processorにメモリコピー)
```

**決定が必要な点:**

a. **「セット」の概念**: a〜d は物理的に近接している必要があるのか、それとも世界のどこにいても機能するか。「対象が一定距離内にいる必要がある」とあるので近接が条件のはず。これらが散らばらないための仕組みは何か（接続機構？ 力場？ 偶然の近接？）。

b. **c, d が e, f を見つけるメカニズム**: Assembler が生成した空コンポーネント（e, f）を Processor（c, d）が発見し、設定を書き込む流れ。Processor は近傍を探索して「レシピ未設定の Assembler」「メモリ空の Processor」を見つける必要がある。この探索はどう行われるか（SENSE 相当？ 常時スキャン？）。

c. **c と d の区別**: c は「Assembler に Assembler のレシピを設定」、d は「Assembler に Processor のレシピを設定」する。c と d のプログラムは異なるのか、それとも同一プログラムで対象を切り替えるのか。

d. **Processor のメモリコピーの対象**: 「自身のメモリ内容をコピーする」とあるが、c は c 自身のメモリを f にコピーする？ それとも d のメモリを f にコピーする？ c と d が異なるプログラムなら、「自身のメモリ」は c のメモリ = c のプログラムであり、f は c のコピーになる。

e. **変異の発生箇所**: メモリコピー時にビット反転等の変異が起きるのか、Assembler の生成時に起きるのか、両方か。「システム的に提供される複製時の変異」を排除する方針なので、変異は物理法則（コピーノイズ等）として表現されるべき。

### 3-2. 増殖の持続性

**決定が必要な点:**

a. **エネルギー・資源の供給**: 「資源とエネルギーを使い果たすまで」とあるが、持続的な増殖には資源の再生が必要。v6 の GroundGrid + ノード再生メカニズムを残すか、別の方式か。

b. **コンポーネントの寿命**: 「durability の概念もなくなる」とあるが、コンポーネントが永久に存在するとリソースが固定されて循環しない。何らかの「死」に相当する仕組みが必要か。

## 4. Processor の命令セット

### 4-1. 必要な命令

`01_goal.md` の想定振る舞いから、Processor に必要な最低限の能力:

1. **近傍探索**: 一定範囲内のコンポーネントを検出し、種別・状態を判別する
2. **書き込み**: 対象 Assembler のレシピフィールドを設定する
3. **メモリコピー**: 自身のメモリ内容を対象 Processor にコピーする
4. **条件分岐**: 「空の Assembler を見つけたら設定する」等の条件付き動作

**決定が必要な点:**

a. **v5/v6 の VM 命令セットを流用するか**: 既存の 16bit 命令セット + I/O 空間は v7 の Processor にも使えるか。I/O アドレス空間は大幅に変わるが、演算・分岐命令は流用可能。

b. **I/O モデル**: v6 では Character のコンポーネントスロットに対応する I/O アドレス空間があった。v7 では「近接コンポーネントへのアクセス」になるので、I/O モデルが根本的に変わる。対象コンポーネントの発見 → 対象への読み書き、というプロトコルをどう設計するか。

c. **内蔵メモリサイズ**: MemoryCore なしの最小 Processor のメモリサイズ。v6 では MemoryCore 1 個 = 1024 ワード。内蔵メモリは何ワードが適切か。想定振る舞い（近傍探索 + 条件分岐 + 書き込み + メモリコピー）を実現するのに最低限必要なプログラムサイズから逆算する。

## 5. 実装基盤

### 5-1. v6 からの継承

**決定が必要な点:**

a. **物理エンジン**: v6 の物理モデル（力、摩擦、衝突）をそのまま使えるか。物体数が大幅に増加する（コンポーネント＋資源＋エネルギーが全て物体）ため、パフォーマンスが問題になりうる。

b. **空間インデックス**: v6 の SpatialGrid は十分か。物体密度が上がる場合、より効率的な構造が必要か。

c. **UI**: v6 の Renderer は Character を前提としている。コンポーネントが独立物体になると描画対象が根本的に変わる。v6 の UI を改修するか、新規に作るか。

### 5-2. 物体数とパフォーマンス

**決定が必要な点:**

「中間生成物とエネルギーが無数に漂っている」場合、世界の物体数が v6（数十〜数百キャラクター + 数百ノード）から桁違いに増加する可能性がある。

a. **物体数の上限の見積もり**: 初期状態の物体数の目安。数百？ 数千？ 数万？

b. **パフォーマンス上の制約**: 毎 tick の衝突判定・力場計算のコストが物体数の二乗に比例する場合、上限をどこに設定するか。

---

## 6. 検証目標

`01_goal.md` より、目標は「v6 とは異なる仕組みによる制御プリミティブの実装と、それによる自己複製の実現」。

**決定が必要な点:**

a. **最低達成基準**: 自己複製の定義。`01_goal.md` の想定振る舞いが実現すれば達成か、それとも「資源再生を含む持続的な増殖」まで必要か。

b. **v6 の L0〜L5 基準の適用可否**: v7 の世界モデルでは「キャラクター」がないため、L0〜L5 の基準をそのまま適用できない。「個体」をどう定義するか（近接するコンポーネントのクラスタ？ 単一コンポーネント？）。

---

## 決定の優先順

以下の順で決定すると、後続の決定が容易になる。

```
1. 世界モデル（1-1: 物体の種類、1-2: 力場）
   → 2. コンポーネントの最小セット（2-3b）
      → 3. Assembler の詳細仕様（2-1）
      → 4. Processor の詳細仕様（2-2）
         → 5. Processor の命令セット（4）
   → 6. 自己複製の工程詳細（3-1）
7. 実装基盤（5）は上記と並行して検討可能
8. 検証目標（6）は独立
```
