# v7 設計決定事項

v7 は「制御プリミティブによる自己複製」を v6 とは異なる方法で実装するバージョンである。
本文書は実装着手前に決定すべき項目を列挙し、各項目の背景・選択肢・推奨案を記載する。

---

## 背景: v6 の成果と課題

v6 では「条件→アクションのルールリスト」方式で制御プリミティブを実装し、自己複製（L4/L5）を達成した。

### v6 で確認された成果

- 単一条件ルールだけでは自己複製不能（AND 条件が不可欠）
- AND/OR/NOT 複合条件の追加により全 6 コンポーネントのクラフトと ASSEMBLE に成功
- 10 個体 → ピーク 201 個体 → 2000 tick 時点 134 個体（安定複製）
- 変異はルールパラメータの数値変動のみで実装

### v6 の構造的課題

1. **制御がキャラクターの「身体」と分離している**: ルールリストはキャラクターのデータとして格納されるが、コンポーネントとしてクラフト・組み立てされるものではない。original の設計構想（`01_program_robustness.md`）にある「論理ゲートのようなコンポーネント」とは異なる
2. **ルール設計が恣意的**: `can_craft_missing`, `can_assemble` 等の高抽象度な条件型を実装者（人間）が用意した。これらは「プリミティブ」というよりはゲームシステムの特殊支援であり、進化で自然に出現するものではない
3. **変異の範囲が狭い**: パラメータの数値が ±3 変動するだけ。ルールの追加・削除・順序変更・条件型の変更は起きない。進化的探索空間が極めて限定的
4. **ルールリストの転写が「丸ごとコピー」に近い**: ASSEMBLE 時にテンプレートからルールを転写するが、物理的な組み立て工程を経ない
5. **1 tick 1 アクション制約**: VM との差別化としては妥当だが、制御プリミティブ自体の能力を過度に制限している可能性がある

## 決定事項 1: 制御プリミティブのアーキテクチャ

v6 の「ルールリスト」方式と、original 構想の「コンポーネント型」方式のどちらを採用するか。

### 選択肢 A: コンポーネント型（original 構想準拠）

制御機能を持つ新しいコンポーネント型を導入する。各コンポーネントは 1 つの単純機能を持ち、コンポーネント間の結線（Wire）でデータを流す。

```
[Sensor] → [Threshold(energy<300)] → [Trigger(RECHARGE)]
                                    → [Selector(nearest EnergyNode)] → [Actuator(MOVE)]
```

- **利点**: コンポーネントとしてクラフト可能（物理的な実体がある）。変異=コンポーネントの追加/削除/パラメータ変更。original 構想に合致
- **欠点**: 結線（Wire）のデータフロー設計が複雑。結線自体のエンコーディングと変異の表現が難しい

### 選択肢 B: ルールリスト改良型（v6 拡張）

v6 のルールリストを改良する。ルール自体をコンポーネントとして扱う（1 ルール = 1 制御コンポーネント）。

- **利点**: v6 の実績をそのまま活かせる。実装が軽量
- **欠点**: v6 と本質的に同じで「異なる方法」にならない

### 選択肢 C: 有限状態機械（FSM）型

各状態が「条件→アクション」のセットを持ち、状態遷移条件で切り替わる。

```
State 0 (GATHER_ORE):  nearby(Ore) → harvest, Ore≥18 → transition to State 1
State 1 (GATHER_CRYSTAL): nearby(Crystal) → harvest, Crystal≥12 → transition to State 2
State 2 (PROCESS):     can_process → process, else → transition to State 3
State 3 (CRAFT):       can_craft → craft, all done → transition to State 4
State 4 (ASSEMBLE):    energy≥1200 → assemble, else → recharge
```

- **利点**: v6 で困難だったフェーズ管理が自然に表現できる。状態数・遷移条件が変異の対象
- **欠点**: 状態数が増えると複雑。状態遷移の変異がコントロール困難な可能性

## 決定事項 2: プリミティブの物理的実体

制御プリミティブが「コンポーネント」として物理的実体を持つか。

### 選択肢 A: コンポーネントとして存在する

制御プリミティブは Frame や Actuator と同様にクラフト・組み立てされるコンポーネントである。ASSEMBLE 時にインベントリから消費される。基礎代謝・質量に寄与する。

- **利点**: 既存のゲームシステム（クラフト、ASSEMBLE、代謝）に自然に統合される。コストモデルが明快。「より複雑な制御 = より高コスト」が物理的制約として表現される
- **欠点**: 自己複製に必要なコンポーネント数が増える → 複製サイクルが長くなる

### 選択肢 B: 非物理的（v6 方式）

制御ルールはデータとして Character に格納され、コンポーネントとは独立。

- **利点**: コンポーネントを増やさずに制御を複雑化できる
- **欠点**: original 構想から乖離。「制御の複雑さにコストがかかる」という設計原則が失われる

### 選択肢 C: 混合型

基本的な制御機能（移動、収穫トリガー等）は一部のコンポーネントに内蔵。高度な制御（AND条件、状態遷移等）は追加の制御コンポーネントが必要。

- **利点**: 段階的な複雑さのスケーリング。最小構成の個体は少ないコンポーネントで動作
- **欠点**: 「何が基本で何が追加か」の線引きが恣意的になりうる

## 決定事項 3: 条件・アクションの抽象度

v6 では `can_craft_missing`, `can_assemble` などの高抽象度な条件型を用意した。これらをどこまで許容するか。

### 選択肢 A: 低抽象度のみ（プリミティブ原理主義）

提供する条件は `energy < N`, `inventory[X] >= N`, `nearby(type, range)` のような物理的に観測可能な値のみ。`can_craft` 等の複合チェックは条件の組み合わせで表現させる。

- **利点**: 進化の探索空間が広い。人間が設計する余地も残る
- **欠点**: v6 で実証済みの通り、低抽象度のみでは自己複製の実現が極めて困難

### 選択肢 B: 高抽象度を許容（v6 方式）

`can_craft`, `can_assemble`, `can_process` 等の便利な条件型を提供する。

- **利点**: 自己複製が実現可能であることが v6 で実証済み
- **欠点**: 「プリミティブ」の名に反する高機能。進化で偶然これらの条件を「発見」する確率は極めて低い

### 選択肢 C: 低抽象度 + 状態/内部変数

低抽象度の条件のみ提供するが、レジスタ等の内部状態を持たせることで、複合的な判断をフェーズ管理として表現可能にする。

- **利点**: 条件自体は単純だが、状態遷移により複雑な行動パターンを構築可能
- **欠点**: 状態管理の変異表現が別途必要

## 決定事項 4: 変異のメカニズム

自己複製時に子の制御プリミティブがどのように変異するか。

### 選択肢 A: パラメータ変異のみ（v6 方式）

数値パラメータの ±N 変動のみ。構造（ルール数、条件型、アクション型）は不変。

- **利点**: 実装が単純。探索空間が連続的で制御しやすい
- **欠点**: 進化的に到達可能な表現が親の構造に完全に制約される

### 選択肢 B: 構造変異あり

ルール/コンポーネントの追加・削除・順序変更・型変更を含む。

- **利点**: 進化的に新しい行動パターンが創発しうる。真の進化に近い
- **欠点**: 大半の構造変異は致死的。生存可能な変異体の出現確率が極めて低い可能性

### 選択肢 C: 階層的変異

- 高確率: パラメータ変異（閾値 ±N）
- 低確率: 軽微な構造変異（ルール複製、ルール削除）
- 極低確率: 大きな構造変異（条件型変更、アクション型変更）

- **利点**: 現実の生物の変異モデルに近い（点変異 > 欠失 > 転座）
- **欠点**: 確率の調整が難しい

## 決定事項 5: VM（Processor）との関係

v6 では VM を残した。v7 でも維持するか。

### 選択肢 A: VM を維持（v6 方式）

Processor を持つキャラクターは VM で制御される。制御プリミティブと VM は並存する。

- **利点**: 比較実験が可能。既存テスト資産を継承
- **欠点**: コードベースが大きくなる。VM 関連のメンテナンスコスト

### 選択肢 B: VM を削除

制御プリミティブのみに一本化する。

- **利点**: コードベースが小さくなる。検証対象が明確
- **欠点**: VM ベースの進化実験との比較ができなくなる

### 選択肢 C: VM をコードとして残すが機能を無効化

コンパイラ・VM のコードは残すが、Processor コンポーネントをクラフトレシピから除外する等で事実上使用不能にする。

- **利点**: 将来の復活が容易
- **欠点**: 中途半端

## 決定事項 6: 自己複製の方式

v6 では「テンプレートからの一括転写」で子の制御を構成した。これは実質的に SELF_REPLICATE 命令に近い。

### 選択肢 A: テンプレート転写（v6 方式）

ASSEMBLE 時にテンプレートから子のルール/構造を一括コピー。

- **利点**: 実装が単純。動作実績あり
- **欠点**: 恣意的（original 構想の「プレイヤーが物理的に組み立てる」とは異なる）

### 選択肢 B: コンポーネント組み立て型

子の制御コンポーネントもインベントリに入れて ASSEMBLE する。親が自分と同じ制御構成の子を作るには、同じ制御コンポーネントをクラフトしてインベントリに揃える必要がある。

- **利点**: 完全に物理的。original 構想に合致。制御の「コピー」が物理的コストを持つ
- **欠点**: クラフトステップが大幅に増加。自己複製サイクルがさらに長くなる

### 選択肢 C: 混合型

制御コンポーネントは ASSEMBLE 時に親からコピーされるが、コピーにエネルギーコストがかかる（制御の複雑さに比例）。

- **利点**: 物理的コストは存在するがクラフト工程は不要
- **欠点**: 「コピーにコストがかかる」は物理的な直感に反する

## 決定事項 7: v6 からの継承範囲

v7 の実装ベースをどこに置くか。

### 選択肢 A: v6 をコピーして改修

v6 のコードベース（VM 含む）をそのまま持ち込み、制御プリミティブ部分を差し替える。

- **利点**: ゲーム基盤（物理、資源、代謝、UI）を再利用。テスト資産の継承
- **欠点**: v6 の制御プリミティブ実装（primitives.ts, seeds.ts）との混在リスク

### 選択肢 B: v5 をコピーして再構築

VM・ゲーム基盤のみを持ち込み、v6 の制御プリミティブは持ち込まない。

- **利点**: v6 の実装に引きずられない。クリーンな再設計
- **欠点**: v6 で得た知見（AND 条件の必要性、エネルギー管理等）を活かすには再度実装が必要

## 決定事項の依存関係

```
決定 1 (アーキテクチャ)
  ├→ 決定 2 (物理的実体)
  ├→ 決定 3 (抽象度)
  │    └→ 決定 4 (変異)
  ├→ 決定 6 (自己複製方式)
```
